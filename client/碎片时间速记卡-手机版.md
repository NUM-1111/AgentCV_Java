## 🃏 卡片1：Token 到底是什么

**一句话**：Token 是 LLM 处理文本的**最小单元**，不是"字"也不是"词"。

**BPE 切分算法**（Byte Pair Encoding）：
- 从字符开始 → 统计最高频相邻对 → 合并为新 token → 循环到预设词汇量
- "人工智能"可能被合并为 1 个 token，而不是 4 个

**中文 token 估算**：
- 实际：1 中文字 ≈ 0.5-0.7 token（约 1.5-2 字/token）
- 工程保守估算：1 字 ≈ 1 token（高估 30%，宁可误拦不可漏拦）

**不同模型 tokenizer 不同**：
- GPT → tiktoken
- DeepSeek → 自研 tokenizer
- 同一文本在不同模型上 token 数不同

## 🃏 卡片2：主流模型上下文窗口

| 模型 | 上下文窗口 | 输出上限 |
|------|-----------|---------|
| GPT-4o | 128K | 16K |
| Claude 3.5 Sonnet | 200K | 8K |
| **DeepSeek-V4-Flash** | **1M (1,000,000)** | 8K |
| DeepSeek-V4-Pro | 1M | 8K |
| DeepSeek-R1 | 128K | 8K |
| Gemini 1.5 Pro | 1M | 8K |

**Lost in the Middle**：
- 模型对长文本**中间位置**的信息提取能力显著下降
- 有效注意力：前 25% 和后 25% 最好，中间 50% 容易被遗忘
- 所以即使窗口很大，输入也不宜塞满

## 🃏 卡片3：Temperature / Top-P / Max_Tokens

| 参数 | 控制什么 | 低值 | 高值 |
|------|---------|------|------|
| **Temperature** | 输出**随机性/创造性** | 0=确定（每次一样） | 1=按概率采样 |
| **Top-P** | 候选 token **范围** | 只从高概率 token 选 | 更多候选 |
| **Max_Tokens** | 输出**长度硬上限** | 短回复 | 长回复 |

**我项目里的配置**：
- Writer：Temperature=0.5（表达生动但不跑偏）
- Critic：Temperature=0.2（审查判定稳定一致）
- 经典组合：Temperature=0.3 + Top-P=0.9 = "稳定但不僵硬"

> ⚠️ Temperature 管随机性，Max_Tokens 管长度，两个不同！

## 🃏 卡片4：DeepSeek V4 速记

| 维度 | DeepSeek-V4-Flash |
|------|-------------------|
| 上下文 | **1M (1,000,000)** |
| 输出上限 | 8K |
| API名称 | `deepseek-v4-flash` |
| 特点 | 轻量快速，1M上下文 |

> DeepSeek-R1：128K上下文，推理模型（思维链），用于需要深度推理的场景

**项目配置位置**：`application.yml` → `langchain4j.open-ai.chat-model` → 环境变量 `OPENAI_MODEL_NAME`

**面试必须记住的 3 个数字**：
- 上下文 **1M Token**（= 1,000,000） ← 一面说成4096，二面绝不能再错
- 我设的阈值 **10,000 Token**（不是模型限制，是业务合理性+成本控制+Lost in the Middle）
- TokenEstimator 公式：中文 1:1 + 固定开销 400

**为什么1M上下文我仍只设1万？**
> 三个原因：① Lost in the Middle——模型对中间位置信息提取能力下降，1万保证所有内容在最佳注意力窗口内；② 业务合理性——JD+简历正常不超过1万token；③ 成本控制——API按token计费。

## 🃏 卡片5：Agent 架构概念树

```
Agent（智能体）— 自主决策的角色
  ├─ 有 SystemMessage 定义身份/边界
  ├─ 能自主选择工具和决定执行顺序
  └─ 我的代码：Writer、Critic

Skill（技能）— Agent 可调用的功能模块
  ├─ 被动执行（被调用才干活）
  ├─ 无状态（输入→输出）
  └─ 类比：Agent 是医生，Skill 是检查设备

Tool / Function Calling — LLM 主动调用的外部函数
  ├─ LLM 自己决定何时调用 + 传什么参数
  └─ 示例：查数据库、搜知识库、发邮件

Role（角色）— Agent 的身份定位
  └─ 通过 SystemMessage 定义

Orchestration（编排）— 调用逻辑
  ├─ 链式→DAG→动态规划（LangGraph）
  └─ 我的：RewriteCoordinatorService 硬编码 for 循环

Memory（记忆）— 跨轮/跨会话信息保持
  └─ 我不用：每轮独立调用，靠 feedback 参数传递
```

## 🃏 卡片6：Agent vs Skills 一句话区分

| 维度 | Agent | Skill |
|------|-------|-------|
| 决策权 | ✅ 有（调用什么、什么顺序） | ❌ 无（被调用才执行） |
| 身份 | 有 SystemMessage | 有功能描述 |
| 状态 | 管理上下文 | 无状态 |
| 通信 | 可直接通信 | 需要编排者串联 |

**面试标准回答（15秒）**：
> "Agent 有自主决策权，Skill 是工具。Skills 之间不能直接通信，需要编排者——这编排者本质上就是一个 Agent。选 Agent 还是 Skill 看：是否需要独立的角色身份和判定边界？"

## 🃏 卡片8：输出侧四层 Pipeline

```
L1: extractJsonObject     → 剥离 Markdown ```json``` 包裹
L2: FieldNameNormalizer   → 归一化 25+ 种字段名变体
L3: Jackson 宽松解析      → 4 个开关（注释/尾逗号/单引号/未知字段忽略）
L4: Bean Validation       → matchScore∈[0,100]、skills 非 null
```

**关键设计**：
- Jackson `FAIL_ON_UNKNOWN_PROPERTIES=false` → 模型多输出未知字段不报错
- 四层任一层失败都有明确错误码，不是黑盒崩

## 🃏 卡片9：AOP 双切面速查

| | WebLogAspect | AiCallLogAspect |
|------|-------------|----------------|
| 切点 | `@within(RestController)` | `execution(* evaluate(..))` |
| 日志前缀 | `[WEB]` | `[AI-CALL]` |
| 入参策略 | JSON 序列化 + 200 字符截断 | 只记长度，不记全文 |
| 出参策略 | 只记 HTTP 状态码 | 记 score + 技能数 |
| 为什么拆 | HTTP 维度 | AI 业务维度 |

**为什么 AiCallLogAspect 用 execution 不用 @within？**
> @AiService 是接口注解 + JDK 动态代理，@within 匹配不到接口上的注解，execution 匹配方法签名更可靠。

## 🃏 卡片10：violationType 四分类 + severity

| 类型 | severity | 示例 |
|------|----------|------|
| FAKE_DATA | 4-5 | 捏造 QPS 数据"提升 30%" |
| FAKE_TECH | 4-5 | 没用过的技术栈写成用过 |
| EXAGGERATION | 3 | "参与开发"→"主导设计" |
| MINOR_EMBELLISHMENT | 1-2 | "优化了"→"提升了"措辞润色 |

**Coordinator 决策**：
- maxSeverity ≤ 2 → WARN 日志 + 直接通过
- maxSeverity ≥ 3 → 触发重写循环
- 3 轮后不达标 → 强制输出 + 告知用户

## 🃏 卡片11：成本三维框架

```
减量（一次开发终身省钱）
  └─ TextTrimmer 砍输入 + TokenEstimator 超限拦截

提效（有风险需验证）
  └─ 小模型做 Critic + max_tokens 硬上限

扩容（成本最高）
  └─ 异步化 202+taskId → MVP 阶段不做
```

**顺序 = 按边际收益递减曲线排的，不是拍脑袋。**

## 🃏 卡片12：Spring AI vs LangChain4j

| | Spring AI | LangChain4j |
|------|-----------|-------------|
| 定位 | Spring 原生 AI 集成 | Java 版 LangChain |
| 优势 | 与 Spring Boot 无缝（ChatClient 可注入 Bean） | Agent 编排原语丰富（@AiService/@SystemMessage/@UserMessage） |
| 结构化输出 | 基础支持 | @Description 自动生成 JSON Schema |
| 适用场景 | 现有 Spring 应用加对话功能 | 多 Agent 复杂编排 |

**为什么这个项目选 LangChain4j**：
> 需要两个 Agent 做编排 + 结构化输出（CriticReport），LangChain4j 的 @AiService 注解体系更自然。
