# 长文本上下文溢出问题探测报告

**测试日期**：2026-04-12  
**测试接口**：`POST /api/v1/match/evaluate`  
**测试类**：`ContextWindowOverflowTest`  
**测试结论**：当前代码**完全没有**长文本保护机制，超长输入会被原样透传给模型

---

## 一、背景

`StageOneYH.md` 将"长文本上下文溢出"列为 **P0** 问题，具体表现为：

1. JD + 简历总长度超过模型 token 上限
2. 框架/模型自动黑盒截断，关键信息丢失
3. 超长文本直接导致报错或结果错乱

本次测试通过 `InputCapturingStub` 替换真实 LLM，记录 `MatchEvaluationFacadeService` 实际透传给模型的输入长度，验证上述问题是否真实存在。

---

## 二、调用链路

```
POST /api/v1/match/evaluate
  └─ MatchController.evaluate(jdText, resumeText)
       └─ MatchEvaluationFacadeService.evaluate(jdText, resumeText)
            └─ MatchEvaluatorService.evaluate(jdText, resumeText)  ← 直接透传，无任何裁剪
                 └─ LangChain4j → DeepSeek API
```

**关键发现**：从 Controller 到 LLM 调用，`jdText` 和 `resumeText` 全程未经任何长度检查或裁剪。

---

| 场景 | JD 字数 | 简历字数 | 合计字数 | 估算 token | 测试结果 | 风险等级 |

## 四、问题详细分析

### 4.1 无 token 预估逻辑

```java
// MatchEvaluationFacadeService.java
public MatchReport evaluate(String jdText, String resumeText) {
    // ❌ 直接调用，没有任何长度检查
    String raw = matchEvaluatorService.evaluate(jdText, resumeText);
    ...
}
```

当前代码对输入长度完全无感知，无论 `jdText` 和 `resumeText` 有多长，都会直接透传给 LangChain4j，再由 LangChain4j 发送给 DeepSeek API。

### 4.2 无业务层裁剪

`MatchEvaluatorService` 的 `@UserMessage` 模板直接将 `{{jdText}}` 和 `{{resumeText}}` 插入 prompt：

```java
// MatchEvaluatorService.java
@UserMessage("""
        ...
        【岗位 JD】
        {{jdText}}          ← 原样插入，无长度限制

        【简历纯文本】
        {{resumeText}}      ← 原样插入，无长度限制
        """)
String evaluate(@V("jdText") String jdText, @V("resumeText") String resumeText);
```

### 4.3 Prompt 模板固定开销不可见

`@SystemMessage` + `@UserMessage` 模板固定文本约 **400 字 ≈ 400 token**，这部分开销在业务代码中完全不可见，导致 token 预算计算天然不完整。

### 4.4 application.yml 无 max-tokens 配置

```yaml
langchain4j:
  open-ai:
    chat-model:
      api-key: ${OPENAI_API_KEY}
      base-url: ${OPENAI_BASE_URL}
      model-name: ${OPENAI_MODEL_NAME}
      log-requests: true
      log-responses: true
      # ❌ 没有 max-tokens、max-context-length 等任何限制配置
```

## 五、真实场景下的失败模式

当真实调用 DeepSeek API 时，超长输入会触发以下两种失败模式：

### 失败模式 A：API 报错（context_length_exceeded）

```json
{
  "error": {
    "message": "This model's maximum context length is 65536 tokens. 
                However, your messages resulted in 68000 tokens.",
    "type": "invalid_request_error",
    "code": "context_length_exceeded"
  }
}
```

LangChain4j 会将此错误包装为运行时异常，`MatchEvaluationFacadeService` 的 `catch (Exception ex)` 会捕获并抛出 `IllegalStateException("模型输出解析失败: ...")`，**错误信息具有误导性**（实际是输入过长，而非输出解析失败）。

### 失败模式 B：黑盒截断（更危险）

部分模型/API 不报错，而是静默截断输入，导致：
- 简历后半段（通常是项目经历、技能清单）被丢弃
- 模型基于不完整信息给出评分，结果不可信
- 业务层无法感知截断，正常返回 `MatchReport`，**静默错误**

## 六、影响范围

| 维度 | 当前状态 |
|------|---------|
| 真实简历长度 | 通常 2000~8000 字，复杂简历可达 15000+ 字 |
| 真实 JD 长度 | 通常 500~3000 字，详细 JD 可达 5000+ 字 |
| 合计典型长度 | 3000~20000 字 |
| DeepSeek-chat 上下文窗口 | 32K~64K token（视版本） |
| 当前安全边界 | 无（0 保护） |
| 触发溢出的概率 | 中高（复杂简历 + 详细 JD 场景必现） |

## 七、待解决方案（待实现）

根据 `StageOneYH.md` 的规划，后续需要实现：

1. **业务层裁剪**：只保留核心片段（职责、要求、经历、项目），丢弃冗余内容
2. **Token 长度预估**：在调用模型前估算 token 数，超过阈值主动拦截并返回明确错误
3. **不依赖框架截断**：保证输入可控，避免黑盒行为
4. **超长内容分段处理**：分段抽取 + 合并匹配（可选，复杂度较高）
