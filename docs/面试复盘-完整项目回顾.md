## 1. 项目整体定位

### 一句话概括

> 这是一个基于 **Spring Boot 3.2 + LangChain4j** 的 AI 求职辅助后端服务，核心能力是用大模型把「非结构化文本」变成「可消费的结构化结果」，并围绕 AI 输出的**概率性不可靠**问题，构建了多层工程防御体系。

### 三个核心接口

| 接口 | 职责 | 核心挑战 |
|------|------|---------|
| `POST /api/v1/jd/analyze` | JD 解析 → 结构化 `JdInfo` | 最简单的单步调用 |
| `POST /api/v1/match/evaluate` | 人岗匹配 → 结构化 `MatchReport` | **格式漂移**（工程化最重） |
| `POST /api/v1/resume/rewrite` | 简历重写 → 结构化 `RewriteReport` | **语义幻觉**（双智能体兜底） |

### 面试话术（开场介绍）

> 这个项目是一个 AI 驱动的求职辅助系统，用大模型做 JD 解析、人岗匹配评估、简历重写。
> 技术栈是 Spring Boot 3.2 + Java 17 + LangChain4j。
> 项目的核心挑战不是"怎么调大模型"，而是"怎么让大模型的概率性输出变得可靠"——我围绕这个问题做了三层防御：输入层做裁剪和 Token 预估，输出层做宽容解析和字段归一化，业务层做双智能体事实核查。

## 2. 人岗匹配（Match）— 工程化最完整的接口

### 2.1 背景与痛点

`/api/v1/match/evaluate` 接收 JD 和简历纯文本，返回结构化的人岗匹配报告（分数、匹配技能、缺失技能、改进建议）。

**原始问题**：模型输出不可控，存在三类问题：
1. **格式问题**：JSON 前后有自然语言、Markdown 代码块、注释、单引号、尾逗号
2. **字段漂移**：字段名变成 snake_case、大小写变体、语义相近词
3. **业务无效**：分数超出 0-100、技能列表为 null、建议为空白

### 2.2 技术方案 — Facade 六步流水线

```
MatchController
    └── MatchEvaluationFacadeService（编排层）
            ├── Step 1: TextTrimmer.trimJd/trimResume  → 业务层裁剪
            ├── Step 2: TokenEstimator.assertWithinLimit → Token 预估拦截
            ├── Step 3: MatchEvaluatorService.evaluate   → 调用模型（返回原始字符串）
            ├── Step 4: extractJsonObject                 → 提取 JSON 主体
            ├── Step 5: FieldNameNormalizer.normalize     → 字段名归一化
            └── Step 6: objectMapper.readValue + validateReport → 反序列化 + Bean 校验
```

**关键设计决策**：`MatchEvaluatorService` 返回 `String` 而非 `MatchReport`

```java
// 改造前：框架内部 Gson 反序列化，项目无法介入
MatchReport evaluate(String jdText, String resumeText);

// 改造后：拿原始文本，解析权交给项目自己
String evaluate(String jdText, String resumeText);
```

这个决策是整个 match 接口工程化的基石——把解析控制权从框架黑盒中解放出来，让项目可以自己处理模型输出的各种"意外"。

### 2.3 面试话术

> Match 接口是项目里工程化最重的一个接口。我设计了一个六步流水线：
>
> 第一步是业务层裁剪，用正则识别 JD 的"职责/要求"段落和简历的"工作/项目经历"段落，丢弃公司介绍、福利待遇这些冗余内容，从源头减少 Token 消耗。
>
> 第二步是 Token 预估，在调用模型前做保守估算，超过阈值主动拦截并返回明确错误，避免依赖模型的黑盒截断。
>
> 第三步到第六步是输出处理：先提取 JSON 主体去掉自然语言包裹，再用正则做字段名归一化覆盖各种漂移变体，然后用配置了宽容模式的 Jackson 反序列化，最后用 Bean Validation 做业务约束校验。
>
> 核心思路是：**不让框架替我做解析，把控制权握在自己手里**。`MatchEvaluatorService` 返回原始字符串而不是直接映射到 `MatchReport`，这样我可以在反序列化之前做预处理，在反序列化之后做校验。

### 2.4 可追问的深度点

- **Q**：为什么不用 LangChain4j 的 Structured Output？→ 答：不是所有模型都支持，且即使支持也有偶发不遵守的情况，后端兜底是必须的。
- **Q**：六步流水线的顺序为什么这么排？→ 答：裁剪在 Token 预估之前，因为裁剪后可能就不超限了；Token 预估在调用模型之前，是最后一道防线。
- **Q**：`extractJsonObject` 用首尾 `{}` 截取，遇到嵌套 JSON 怎么办？→ 答：当前场景下模型输出的是扁平 JSON，嵌套概率低。如果要更精确可以用栈匹配，但当前方案在 99% 场景下够用。

## 3. Actor-Critic 双智能体审查流（消灭幻觉）

### 3.1 背景与痛点

原 `ResumeRewriteService` 的 System Prompt 是"化腐朽为神奇"，模型被激励去**发明数据**：
- 原文没有量化数据 → 模型自行填入"QPS 提升 200%"
- 原文没有 K8s 经验 → 模型主动写入"熟练运用 Kubernetes 编排"
- 没有任何事实核查机制，生成结果的真实性完全依赖模型自律

### 3.2 技术方案

**核心思路**：引入**事实边界**——`originalProjectText`（候选人原始项目经历）是唯一可信的事实来源。Writer 只能在这个边界内扩写，任何超出原文的技术或数据均视为幻觉。

**架构设计**：

```
ResumeController
    └── RewriteCoordinatorService（普通 @Service，负责编排）
            ├── ResumeWriterAgent（@AiService）
            │     职责：根据 JD 和原始经历生成简历要点草稿
            └── FactCriticAgent（@AiService）
                  职责：对照原始经历，逐条核查草稿中的 bullet points
                  返回 CriticReport（通过/打回 + 具体原因）
```

**编排逻辑**（最多 3 轮循环）：

```java
for (int round = 0; round < MAX_ROUNDS; round++) {
    RewriteReport draft = writerAgent.rewrite(jd, original, feedbackPrompt);
    CriticReport criticism = criticAgent.check(original, formatBulletPoints(draft));
    if (criticism.approved()) {
        return new RewriteResult(draft, round + 1);  // 提前返回
    }
    criticFeedback = criticism.feedback();  // 传给下一轮
}
return new RewriteResult(lastDraft, MAX_ROUNDS);  // 超出轮次返回最后一版
```

### 3.3 三个关键设计决策

**决策一：Context 策略 — 只传 feedback，不传历史草稿**

每轮 Writer 接收的 context：`jdText + originalProjectText + criticFeedback（精华摘要）`

原因：历史草稿全文会导致 context 线性增长，3 轮后可能超出模型窗口；Critic 的 feedback 已包含修正所需的全部信息。

**决策二：响应时间劣化 — 用同步实现，通过响应头透出轮次**

最多 6 次 LLM 调用（3 轮 × 2 次），单次请求可能长达 40+ 秒。当前方案：
- 配置 `timeout: 60s` 防止永久挂起
- 响应头加 `X-Review-Rounds: N` 告知调用方实际循环轮次
- 文档中明确说明这是 trade-off

**决策三：超出最大轮次后返回最后一版，不抛异常**

即使 Critic 认为草稿仍有问题，最后一版也是经过多轮修正后"最接近合格"的版本，返回它比直接报错更有业务价值。

### 3.4 面试话术

> 简历重写接口是幻觉的重灾区。单靠 Prompt 约束是"自我承诺"，模型在面对"匹配高阶 JD"和"不得捏造"两个冲突指令时，往往会优先满足生成质量目标。
>
> 我的方案是引入一个独立的 Critic Agent，专门做"原文 vs 草稿"的交叉比对。Critic 不关心 bullet point 写得好不好，只做二元判断：能不能在原文找到依据。这个任务有明确的客观输入，不是让模型主观评判另一个模型，工程上更可靠。
>
> 三个设计决策：第一，打回重写时只传 Critic 的 feedback，不传历史草稿，防止 context 爆炸；第二，同步实现但通过响应头透出轮次，让调用方感知 trade-off；第三，超出最大轮次后返回最后一版，不抛异常，保证业务连续性。

### 3.5 可追问的深度点

- **Q**：Critic 本身也是 LLM，它会不会误判？→ 答：有可能，但 Critic 的任务比 Writer 简单得多——它只需要做"原文有没有"的二元判断，不需要创造性输出。而且即使误判，也只是多一轮循环，不会产生错误数据。
- **Q**：3 轮循环的响应时间怎么接受？→ 答：面试阶段是 trade-off，生产环境应该改为异步（202 + taskId 轮询），但当前同步实现已足够展示架构思路。
- **Q**：为什么 MAX_ROUNDS 是 3 不是 5？→ 答：经验值。3 轮后 Writer 的修正收益递减，且 3 轮 × 2 次调用 = 6 次已经是响应时间的上限了。

## 4. 上下文窗口优化（TextTrimmer + TokenEstimator）

### 4.1 背景与痛点

原始代码对输入长度完全无感知，超长 JD/简历会被原样透传给模型，导致：
- **静默截断**：模型丢弃后半段内容，结果不可信，且业务层无法感知
- **API 报错**：超过模型上下文窗口，返回 `context_length_exceeded`
- **Token 浪费**：大量无关内容（公司介绍、福利待遇）占用 Token 预算

### 4.2 技术方案

**TextTrimmer — 业务层裁剪**

核心策略：从 JD/简历纯文本中提取核心片段，丢弃冗余内容。

```java
// JD 裁剪：只保留"岗位职责"和"任职要求"段落
public static String trimJd(String jdText) {
    // 1. cleanText：统一换行符、合并连续空行
    // 2. extractSections：正则识别目标段落
    // 3. 找不到目标段落时 fallbackTrim：过滤垃圾行后截断
}

// 简历裁剪：只保留"工作经历"和"项目经历"段落
public static String trimResume(String resumeText) { ... }
```

**关键改进**（从 10 个测试用例扩展到 31 个）：
1. **标题判定严格化**：含句子标点的行不判为标题，避免"代码质量高。"被误切
2. **支持"标题+内容同行"**：如"岗位职责：负责开发..."，整行纳入段落
3. **智能截断**：在 `[70%limit, limit]` 窗口内找句子结束符，不切在汉字中间
4. **兜底策略**：找不到目标模块时，先过滤垃圾行再截断，保证 AI 读到有效信息

**TokenEstimator — 轻量级 Token 预估**

```java
// 保守估算规则
// 中文：1字 ≈ 1 token
// ASCII：4字符 ≈ 1 token
// Prompt 模板固定开销：400 token
// 安全阈值：10,000 token（基于 DeepSeek-chat 64K 窗口保守设定）
```

### 4.3 面试话术

> 上下文窗口优化分两层：业务层裁剪和 Token 预估拦截。
>
> 裁剪层我用正则识别 JD 的"职责/要求"段落和简历的"工作/项目经历"段落，丢弃公司介绍、福利待遇这些无关内容。这里有一个关键改进：原来的标题判定太粗糙，内容里的短句会被误判为标题导致段落被截断。我加了一个严格判定——含句子标点的行不判为标题，同时支持"标题+内容同行"的紧凑格式。
>
> Token 预估层我用保守估算规则，宁可误报也不漏报。安全阈值 10000 的来源是 DeepSeek-chat 的 64K 上下文窗口，减去模型输出预算和 Prompt 模板开销后留有余量。
>
> 两层的关系是：裁剪先压缩输入，如果裁剪后仍然超限，Token 预估再主动拦截。裁剪是"优化"，Token 预估是"兜底"。

### 4.4 可追问的深度点

- **Q**：为什么安全阈值是 10000 不是 20000？→ 答：基于 DeepSeek-chat 64K 窗口，减去输出预算（约 1000 token）和模板开销（400 token），保守设定为 10000，留有充足余量。
- **Q**：换模型了怎么办？→ 答：`TokenEstimator` 的估算规则和阈值需要按新模型的 tokenizer 重新校准，`TextTrimmer` 和异常处理可以复用，只改常量。
- **Q**：兜底策略中过滤后内容少于 50 字符就退回原文，这个阈值怎么来的？→ 答：经验值。50 字符以下的信息量不足以支撑有效评估，退回原文让模型自己判断比过度过滤更好。

## 5. 结构化输出 & 反序列化治理

### 5.1 背景与痛点

模型返回的 JSON 存在三类问题，每类问题对应一层解决方案：

| 问题 | 现象 | 解决方案 |
|------|------|---------|
| 非标准 JSON | 注释、单引号、尾逗号、Markdown 包裹 | Jackson 宽容配置 + JSON 提取 |
| 字段漂移 | snake_case、大小写变体、语义相近词 | `FieldNameNormalizer` + `@JsonAlias` |
| 业务无效 | 分数超范围、列表为 null、建议为空白 | Bean Validation + `AiOutputValidationException` |

### 5.2 技术方案

**第一层：Jackson 宽容配置**

```java
@Bean
public ObjectMapper objectMapper() {
    return JsonMapper.builder()
        .enable(ALLOW_JAVA_COMMENTS)     // 允许 // 注释
        .enable(ALLOW_YAML_COMMENTS)     // 允许 # 注释
        .enable(ALLOW_TRAILING_COMMA)    // 允许尾逗号
        .enable(ALLOW_SINGLE_QUOTES)     // 允许单引号
        .disable(FAIL_ON_UNKNOWN_PROPERTIES) // 忽略多余字段
        .build();
}
```

**第二层：`FieldNameNormalizer` + `@JsonAlias` 双层兜底**

- `FieldNameNormalizer`：在反序列化之前用正则把 JSON key 统一映射到标准字段名，覆盖大小写变体、语义相近词、无分隔符变体
- `@JsonAlias`：作为 Jackson 层的精确兜底，处理已知的固定别名

**第三层：Bean Validation 业务校验**

```java
public record MatchReport(
    @Min(0) @Max(100) int matchScore,
    @NotNull List<String> matchedSkills,
    @NotNull List<String> missingSkills,
    @NotBlank String improvementAdvice
) {}
```

反序列化后手动触发校验，失败时抛出 `AiOutputValidationException`，返回 HTTP 500 并附带具体字段和原因。

### 5.3 面试话术

> 模型输出的 JSON 有三类问题，我用了三层方案来兜底。
>
> 第一层是 Jackson 宽容配置，允许注释、单引号、尾逗号，忽略未知字段。这解决的是"格式不标准"的问题。
>
> 第二层是字段名归一化。模型输出的字段名可能千奇百怪——snake_case、大小写变体、语义相近词。我用 `FieldNameNormalizer` 在反序列化之前用正则把 key 统一映射到标准字段名，`@JsonAlias` 作为精确兜底。两层分工：`FieldNameNormalizer` 覆盖模糊变体，`@JsonAlias` 覆盖已知别名。
>
> 第三层是业务校验。反序列化只保证"结构合法"，不保证"业务有效"。我用 Bean Validation 做约束校验——分数必须在 0-100、技能列表不能为 null、建议不能是空白——校验失败时抛出专用异常，附带具体字段和原因。
>
> 核心思路是：**从"能解析"到"满足业务约束"，每一层都有明确的职责和失败信号**。

### 5.4 可追问的深度点

- **Q**：`FieldNameNormalizer` 为什么在反序列化之前用正则，而不是解析成 JsonNode 再改 key？→ 答：因为此时 JSON 可能还带有注释、单引号等非标准语法，Jackson 还没处理，不能先解析再改 key。正则直接操作字符串，不依赖 JSON 合法性，能更早介入。
- **Q**：解析失败和校验失败都返回 500，前端怎么区分？→ 答：当前确实没有区分，这是可以改进的地方。可以给 `AiOutputValidationException` 加错误码（如 `AI_OUTPUT_INVALID`），给解析失败加另一个错误码（如 `AI_OUTPUT_PARSE_ERROR`），让前端可以细分处理。
- **Q**：遇到未知的字段漂移怎么办？→ 答：当前 `FAIL_ON_UNKNOWN_PROPERTIES = false` 会静默丢弃。可以加一个 `DeserializationProblemHandler` 在发现未知字段时打印告警日志，让开发者感知到漂移发生，便于持续完善规则表。

## 6. AOP 全链路日志系统

### 6.1 背景与痛点

原始系统出问题只能靠猜——不知道是哪个请求触发的，不知道 AI 调用花了多久，不知道是 token 超限还是解析失败。

### 6.2 技术方案

**三个组件：**

| 组件 | 职责 | 技术要点 |
|------|------|---------|
| `TraceIdFilter` | 每个请求生成唯一 traceId，写入 MDC 和响应头 | `OncePerRequestFilter` + `finally` 清理 MDC |
| `WebLogAspect` | 记录 HTTP 层入参摘要、耗时、状态 | `@within(RestController)` 切点 |
| `AiCallLogAspect` | 记录 AI 调用关键指标 | 精准 `execution` 切点，不打印全文 |

**日志链路示例**（同一请求的所有日志带相同 traceId）：

```
12:34:56.001 DEBUG [a1b2c3d4] MatchEvaluationFacadeService : 裁剪前 JD=1200字 简历=2000字
12:34:59.458  INFO [a1b2c3d4] AiCallLogAspect         : [AI-CALL] evaluate | cost=3456ms | score=85
12:34:59.459  INFO [a1b2c3d4] WebLogAspect            : [WEB] POST /api/v1/match/evaluate | cost=3521ms | status=OK
```

**关键设计原则**：
- **零侵入**：Controller 和 Service 代码无需修改
- **分层控制**：INFO 级别记关键指标，DEBUG 级别记详细内容
- **不打印敏感信息**：只记录字符数，不记录全文

### 6.3 面试话术

> 我用 Spring AOP 做了两个切面：一个切 HTTP 层，记录每个接口的入参摘要、耗时、状态；一个精准切 AI 调用入口，记录 JD/简历字符数、AI 耗时、评分结果、异常类型。
>
> 配合 MDC 的 traceId，每个请求产生的所有日志都带同一个 ID，出问题时一条 grep 命令就能过滤出完整链路。
>
> 整套方案零侵入——Controller 和 Service 的代码完全没有改动，日志逻辑全部在切面里，符合开闭原则。
>
> 有一个细节：AI 调用切面不打印完整 Prompt，只记录字符数和关键指标。原因有三：一是防止日志文件爆炸，一次 Prompt 可能 2000 字；二是简历内容涉及个人信息；三是完整 Prompt 由 LangChain4j 框架在 DEBUG 级别输出，需要时打开即可。

### 6.4 可追问的深度点

- **Q**：为什么用 `@within(RestController)` 而不是 `execution`？→ 答：`@within` 可以覆盖所有 Controller 类，新增接口自动生效，不需要改切面。AI 调用层用精准 `execution` 是因为我只关心 `evaluate` 这一个入口，不想切到工具类产生噪音日志。
- **Q**：MDC 为什么要用 `finally` 清理？→ 答：Tomcat 用线程池，线程会被复用。不清理的话上一个请求的 traceId 会污染下一个请求的日志，排查时会被误导。
- **Q**：`@Around` 和 `@Before`/`@After` 有什么区别？→ 答：`@Around` 可以同时拿到方法执行前后的状态，还能捕获异常、修改入参和返回值。`@Before`/`@After` 做不到这些。

## 7. JD 解析接口

### 7.1 背景

`/api/v1/jd/analyze` 是最简单的接口，接收 JD 纯文本，返回结构化的 `JdInfo`（岗位名、核心职责、硬性技能）。

### 7.2 技术方案

```java
@AiService
public interface JdAnalyzeService {
    @SystemMessage("你是一个资深的 HR 和技术架构师。...")
    @UserMessage("请解析以下岗位描述：\n\n{{jdText}}")
    JdInfo analyzeJd(String jdText);
}
```

`JdInfo` 使用 `@Description` 注解给模型提供字段级语义说明，框架底层会将其翻译成 JSON Schema 约束模型输出。

### 7.3 面试话术

> JD 解析接口是最简单的单步调用，但它展示了 LangChain4j 的核心能力——用 `@AiService` 注解声明一个接口，框架自动生成实现，把 Java Record 翻译成 JSON Schema 约束模型输出。
>
> 这个接口没有像 match 接口那样做完整的防御体系，因为 JD 解析的输出结构简单（三个字段），模型格式漂移的概率低。但如果要生产化，应该加上同样的裁剪和校验逻辑。

### 7.4 可追问的深度点

- **Q**：为什么 JD 解析没有做输入裁剪和 Token 预估？→ 答：这是已知的差距。JD 解析的输入通常较短（500-3000 字），超限概率低，所以优先级低于 match 和 rewrite 接口。如果要生产化，应该补上。

## 8. 全局异常处理与防御体系

### 8.1 异常分类与 HTTP 状态码

| 异常 | HTTP 状态码 | 触发场景 |
|------|------------|---------|
| `IllegalArgumentException` | 400 | 参数为空、超长 |
| `ContextWindowExceededException` | 400 | 输入 Token 超限 |
| `AiOutputValidationException` | 500 | 模型输出校验失败 |
| 其他 `Exception` | 500 | 未预期的错误 |

### 8.2 面试话术

> 全局异常处理遵循一个原则：**调用方的问题返回 4xx，服务内部的问题返回 5xx**。
>
> 参数错误（空值、超长）和 Token 超限都是调用方的问题，返回 400 并附带明确错误信息。模型输出校验失败是服务内部的问题，返回 500。
>
> 有一个修复值得一提：原来 `IllegalArgumentException` 没有单独映射，会落入兜底逻辑返回 500。我加了一个专门的 `@ExceptionHandler`，把它映射到 400，语义更准确。

## 附录：面试常见问题速查

### Q：这个项目你最大的技术亮点是什么？

> 两个亮点：一是 match 接口的六步防御流水线，从输入裁剪到输出校验，把模型输出的概率性不可靠变成了工程可控；二是 rewrite 接口的 Actor-Critic 双智能体架构，用独立的 Critic Agent 做事实核查，从工程层面兜底 LLM 的幻觉问题。

### Q：遇到过什么难点，怎么解决的？

> 最大的难点是模型输出的不可预测性。即使 Prompt 里写了"只输出标准 JSON"，模型仍然有概率输出注释、单引号、尾逗号、Markdown 包裹。我的解决思路是：**不依赖模型自律，用工程手段兜底**。具体来说，把解析控制权从框架黑盒中解放出来，自己处理原始字符串，做 JSON 提取、字段归一化、业务校验三层兜底。

### Q：如果让你重新设计，会怎么做？

> 三个改进方向：第一，rewrite 接口的双智能体流改为异步，先返回 202 + taskId，前端轮询结果，解决响应时间问题；第二，给 JD 解析接口补上同样的裁剪和校验逻辑，消除接口间的防御水平差距；第三，构建一个黄金测试集，用 LLM-as-a-Judge 量化评估双智能体架构的收益，用数据说话。

### Q：这个项目离生产环境还差什么？

> 主要差在四个方面：一是没有认证鉴权，接口完全公开；二是没有限流熔断，高并发下可能被打垮；三是没有数据库，所有数据都是瞬态的；四是没有集成测试，当前只有单元测试，没有 Mock LLM 的端到端测试。
