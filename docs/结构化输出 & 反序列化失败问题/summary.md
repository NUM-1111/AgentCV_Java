# 结构化输出问题治理总结（汇报 / 面试版）

## 1. 项目背景

在 `POST /api/v1/match/evaluate` 这个接口里，我之前遇到的核心问题是：AI 输出不稳定，导致后端反序列化容易失败，或者更危险的是“表面成功、实际上字段丢失”，最终把错误数据带进业务流程。

典型问题包括：

- 字段名漂移：`camelCase` 和 `snake_case` 混用；
- 模型乱加字段，比如 `summary`、`strengths`、`weaknesses`；
- JSON 带注释、尾逗号、单引号等非标准格式；
- 列表字段可能被模型输出成错误结构；
- 严重时直接反序列化报错，接口不可用。

我把这个问题定义为：

**AI 输出不确定性，已经突破了后端接口的稳定边界。**

---

## 2. 我的治理思路

我没有继续依赖框架黑盒反序列化，而是把整条链路改成“可控解析 + 校验兜底 + 统一异常”。

### 具体做法

#### 第一层：收紧模型输出契约

在 `MatchEvaluatorService` 里加强 Prompt 约束，明确要求模型：

- 只能返回 4 个字段：
  - `matchScore`
  - `matchedSkills`
  - `missingSkills`
  - `improvementAdvice`
- 禁止返回额外字段；
- `matchScore` 必须是 0-100 整数；
- 列表字段必须返回数组；
- 不允许 Markdown、注释、解释文字。

#### 第二层：后端可控反序列化

我把模型返回值先改成原始字符串，再由 `MatchEvaluationFacadeService` 统一处理：

- 先提取 JSON 主体；
- 再使用项目自己的 Jackson `ObjectMapper` 做宽松反序列化；
- 宽松支持注释、尾逗号、单引号，并忽略未知字段。

#### 第三层：字段级校验

我在 `MatchReport` 上补充了约束，确保“能解析”不等于“业务有效”：

- `matchScore`：限制 0-100；
- `matchedSkills`：`@NotNull`；
- `missingSkills`：`@NotNull`；
- `improvementAdvice`：`@NotBlank`；
- 同时通过 `@JsonAlias` 兼容 `score`、`matched_skills`、`missing_skills`、`advice` 等别名字段。

#### 第四层：统一异常出口

如果模型输出不合规：

- 解析失败，统一抛解析异常；
- 字段缺失或值不合法，统一抛校验异常；
- 最终都通过全局异常处理器返回统一 JSON 错误结构。

这样前端和调用方不会拿到错误业务值，而是拿到明确失败信号。

---

## 3. 我做了哪些验证

### 自动化测试

我补了 `MatchEvaluationFacadeServiceTest`，覆盖了 6 类回归场景：

1. 注释、单引号、尾逗号、前后噪声 JSON；
2. `score`、`matched_skills`、`missing_skills`、`advice` 等别名映射；
3. `matchScore` 越界；
4. `improvementAdvice` 为空白；
5. `missingSkills = null`；
6. 完全错误 schema 的输出。

结果：

- `Tests run: 6`
- `Failures: 0`
- `Errors: 0`

### 真实接口测试

我还对真实接口做了两轮回归：

#### 第一轮测试结论

一开始我发现：

- 后端解析链路已经稳定很多；
- 但模型偶尔仍会返回旧结构，比如 `strengths / weaknesses`；
- 好消息是，后端不会再静默返回错误业务值，而是会直接拦截并返回统一错误。

这说明：

**后端防线已经建立，但模型输出契约还需要加强。**

所以我又进一步收紧了 Prompt。

#### 第二轮测试结论

收紧 Prompt 后，我针对多种干扰场景再次测试，包括：

- 强制改成 `snake_case`；
- 强制加额外字段；
- 强制加入注释和尾逗号；
- 强制把数组改成字符串；
- 强制不返回 JSON；
- 强制把列表改成对象数组；
- 强制把数组字段改成单个对象。

结果：

- 所有请求都成功返回；
- 返回内容仍然稳定符合目标结构；
- 没有复现字段乱变、脏 JSON、结构错乱、非 JSON 输出等问题。

---

## 4. 最终效果

这次改造的关键收益有 3 个：

### 1）解决了“静默错误”问题

以前最危险的是：接口返回 200，但关键字段已经变成 `0`、`null`，业务层还以为成功了。

现在不会了。

如果模型输出不合法，会被显式拦截，而不是悄悄污染业务结果。

### 2）提升了结构化输出稳定性

即使我在请求里故意诱导模型输出错误结构，它最终仍然大概率回到目标 JSON Schema。

说明 Prompt 约束 + 后端治理已经形成联动防线。

### 3）把 AI 不确定性纳入了工程边界

以前这是“模型出错，框架报错，接口不可控”；
现在变成“模型输出先进入治理层，再决定是放行还是拦截”。

这本质上是把 AI 的不确定性纳入后端可控范围。

> 我在项目里遇到过一个典型的 AI 工程化问题：模型返回的 JSON 不稳定，既可能语法不规范，也可能字段漂移，最危险的是反序列化看起来成功，但核心字段已经丢了，导致业务静默出错。
>
> 我做的改造不是只修一个报错，而是重构了整条链路：先把模型输出改成原始字符串，再通过 Facade 层统一做 JSON 提取、Jackson 宽松反序列化、Bean Validation 校验和统一异常处理；同时在 DTO 层加字段别名和必填约束，在 Prompt 层严格限制输出 Schema。
>
> 最终效果是：即使模型偶发输出异常，也不会再悄悄污染业务数据，而是被明确拦截；而在多轮真实接口测试里，字段漂移、脏 JSON、数组变对象、非 JSON 输出这些问题都没有再复现。这个改造本质上是把 AI 的不确定输出，纳入了后端可治理的工程边界。
