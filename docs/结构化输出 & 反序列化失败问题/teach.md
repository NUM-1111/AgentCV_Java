# 教材：结构化输出与反序列化失败治理（求职实战版）

## 1. 你将学到什么（适合只学过 Java 基础）

这份教材围绕一个真实项目改造展开：`POST /api/v1/match/evaluate` 接口在接入 AI 后，出现“解析失败”和“静默丢字段”问题。  
学完后你应该能掌握：

- 为什么 AI 返回的 JSON 在生产里不可靠；
- 如何把“黑盒解析”改成“可控解析”；
- 如何用 Jackson + Bean Validation 建立“解析成功 != 业务有效”的防线；
- 如何设计统一异常返回，让前端和调用方可稳定处理；
- 面试时如何把这次改造讲成一个有技术深度的项目亮点。

---

## 2. 问题场景：这类 bug 为什么危险

项目中原本由框架内部直接反序列化模型输出，主要有两类问题：

1) **非标准 JSON**
- 模型可能输出注释、尾逗号、单引号等“人能看懂、程序不一定能解析”的内容；
- 结果：接口直接抛解析异常，调用失败。

2) **字段命名漂移**
- 例如后端期待 `matchScore`，模型却返回 `match_score` 或 `score`；
- 结果：反序列化“看起来成功”，但关键字段变成 `0`/`null`，业务产生错误结论。

> 关键认知：  
> **在 AI 场景下，最可怕的不是“报错”，而是“悄悄错”。**

---

## 3. 改造目标（工程化表达）

这次改造不是只修一个报错，而是建立一整条可靠链路：

- **目标 1：可控反序列化**  
  不再依赖框架内部黑盒 Gson，改为项目自管的 Jackson 解析流程。

- **目标 2：字段完整性保障**  
  反序列化后强制做 Bean Validation，防止“解析成功但字段无效”。

- **目标 3：统一错误输出**  
  解析异常和校验异常都走全局异常处理，返回统一 JSON 结构。

---

## 4. 核心设计：从黑盒到可观测、可治理

### 4.1 分层职责重构

- `MatchEvaluatorService`：只负责拿到模型原始文本（`String`）；
- `MatchEvaluationFacadeService`：负责“提取 JSON -> 反序列化 -> 校验 -> 抛统一异常”；
- `MatchController`：保持接口入口和输出职责；
- `GlobalExceptionHandler`：统一对外错误格式。

这是一种常见的工程做法：  
**把复杂且脆弱的流程收敛到一个 Facade 层统一治理。**

### 4.2 Jackson 宽松配置（提升容错）

在 `JacksonConfig` 中启用：

- `ALLOW_JAVA_COMMENTS`
- `ALLOW_YAML_COMMENTS`
- `ALLOW_TRAILING_COMMA`
- `ALLOW_SINGLE_QUOTES`
- `FAIL_ON_UNKNOWN_PROPERTIES = false`

意义：

- 对 AI 常见“非严格 JSON”有更高兼容性；
- 模型新增无关字段时，后端不至于立刻炸掉；
- 让系统从“脆弱失败”变为“可控处理”。

### 4.3 字段别名（应对命名漂移）

在 `MatchReport` 中做字段别名映射，例如：

- `matchScore` 接受 `match_score` / `score`
- `matchedSkills` 接受 `matched_skills`
- `missingSkills` 接受 `missing_skills`
- `improvementAdvice` 接受 `improvement_advice` / `advice`

意义：

- 把模型输出的“轻微格式漂移”吸收在 DTO 层；
- 避免每次 prompt 细调都牵动后端大改。

### 4.4 Bean Validation（拦截“静默错误”）

仅靠 JSON 解析成功还不够，还需要约束业务字段：

- `matchScore`：`@Min(0)` + `@Max(100)`
- `matchedSkills`：`@NotNull`
- `missingSkills`：`@NotNull`
- `improvementAdvice`：`@NotBlank`

在 Facade 中手动调用 `Validator`：

- 校验失败时抛 `AiOutputValidationException`；
- 由全局异常处理器统一返回 500 结构化错误。

意义：

- 防止 `null`、空字符串、越界分值进入下游流程；
- 让错误尽早暴露在边界层，缩短排查链路。

---

## 5. 这次改造体现了哪些“可面试的能力”

### 5.1 可靠性工程思维

不是“让 happy path 跑通”，而是优先治理异常输入与不确定输出。

### 5.2 分层设计能力

把 AI 调用、解析、校验、异常处理拆分成职责清晰的层次，代码可维护性更高。

### 5.3 兼容性与演进能力

通过字段别名和宽松解析降低对 prompt 稳定性的依赖，减少线上脆弱点。

### 5.4 可观测错误面

统一异常出口使日志、告警、前端处理方式一致，便于 SLA 保障。

---

## 6. 面试怎么讲（可直接复述）

你可以按 STAR 简化版来讲：

- **S（场景）**：AI 评估接口经常因非标准 JSON 和字段漂移不稳定；
- **T（任务）**：我要把链路改造成“可控解析 + 严格校验 + 统一异常”；
- **A（行动）**：
  - 把服务改成先拿原始文本；
  - 新增 Facade 统一做 JSON 提取、Jackson 反序列化、Bean Validation；
  - DTO 加别名映射和约束注解；
  - 新增专用异常并接入全局异常处理；
  - 增加 `spring-boot-starter-validation` 依赖；
- **R（结果）**：
  - 非标准 JSON 不再直接导致不可控失败；
  - 字段缺失/空值可被明确拦截，不再静默污染业务；
  - 对外错误结构统一，前后端联调效率提升。

## 7. 你可以立刻动手的练习

### 练习 1：构造脏数据输入

模拟以下模型输出并观察系统行为：

- 带注释 JSON；
- 尾逗号 JSON；
- `match_score` / `score` 字段替代；
- `improvementAdvice` 为空字符串；
- `matchScore = 120`。

预期：

- 能解析的尽量解析；
- 违反校验规则的统一抛校验异常并返回标准错误 JSON。

### 练习 2：增强列表元素校验

把 `List<String>` 升级为元素级校验（如每个技能不为空），避免列表里出现空字符串。

### 练习 3：补齐集成测试矩阵

按“输入类型 x 期望行为”补测试用例，形成回归保护网。

---

## 8. 进阶建议（从初级走向中级）

- 在异常中区分“解析失败”和“校验失败”错误码；
- 给模型输出增加版本字段（如 `schemaVersion`），便于灰度演进；
- 在日志中记录“原始输出摘要 + 失败原因”，提升排障效率；
- 对高风险字段增加业务语义校验（如建议文案最小字数）。

---

## 9. 一句话总结

这次改造的本质是：  
**把 AI 的不确定输出，纳入后端可治理的工程边界。**  
这类能力在求职中非常加分，因为它直接体现了你对“生产可用性”的理解。
