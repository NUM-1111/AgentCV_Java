# AI 协作指南：项目审视、问题挖掘与需求立项

## 文档用途（给其他 AI 的阅读说明）

本文件**不是**传统意义上的产品说明书，而是为 **人类或其他 AI 助手**准备的**协作上下文包**。使用方式：

1. **把本文件与** `docs/项目说明.md` **一并作为附件或上下文**，要求对方基于仓库事实做「差距分析 / 风险清单 / 改进需求草案」。
2. 要求对方**优先引用具体路径、类名、行为**（可对照 `src/main/java`、`src/test/java`、`src/main/resources`），避免泛泛而谈。
3. 输出应区分为：**已观察到的问题**、**根因假设**、**建议需求**（含验收标准），见下文模板。

若仓库有更新，以代码为准；本文件只规定**分析维度与产出格式**。

## 审视维度（检查清单）

要求分析者**逐维扫描**，没有发现问题也要标注「暂无」或「未深入」。

### A. 接口与契约

- REST 资源命名、版本前缀（`/api/v1`）是否一致；错误时状态码是否符合语义（例如参数错误是否应为 **4xx**）。
- 请求/响应是否缺少 **OpenAPI/Swagger**、示例、字段长度限制说明。
- `IllegalArgumentException` 等校验失败在全局处理中的**最终 HTTP 码**是否与调用方预期一致。

### B. 可靠性与 AI 特性

- **JD 解析、简历重写**是否与**人岗匹配**同等级的输入控制（裁剪、Token 预估、解析兜底）；若否，差距是否构成风险。
- 模型超时、重试、熔断、**幂等**（若未来引入写操作）是否缺失。
- `TokenEstimator` 为**启发式**：误杀/漏杀场景是否需可配置阈值或真实 tokenizer。

### C. 安全与合规

- 日志与 DEBUG 下是否可能输出 **JD/简历全文、API Key**（`application.yml` 中 `log-requests`/`log-responses` 等）。
- 接口是否**无认证**即暴露；生产环境是否需要网关、鉴权、限流、审计。

### D. 可观测性与运维

- 健康检查是否仅有 `/ping`；是否需要 **readiness/liveness**、依赖（模型服务）探测。
- `X-Trace-Id` 与日志是否足够关联分布式追踪（若未来多实例）。

### E. 测试与质量

- 单元测试覆盖：**工具类** vs **Controller 集成测试** vs **端到端** 的比例；是否需 **Testcontainers** 或 **WireMock** 模拟 LLM。
- 回归场景：模型输出恶意或畸形 JSON、空响应、超长响应。

### F. 产品与工程一致性

- `pom.xml` / `项目说明` 中的描述是否与真实能力一致（例如「scaffold」与生产就绪的差距）。
- 国际化、多语言 JD/简历是否未考虑。

## 问题 → 需求 转化模板

对每一条**确认的问题**（或高概率风险），建议按下列结构产出需求草稿（可复制到 Issue / PRD）。

```markdown
### REQ-编号 〈短标题〉

- **现象 / 证据**：〈文件/类/行为，1～3 句〉
- **影响**：〈用户、运维、安全、成本〉
- **根因假设**：〈技术或流程原因，可多条〉
- **建议方案（概要）**：〈1～2 种，说明取舍〉
- **验收标准（可测试）】**：
  1. …
  2. …
- **非目标**：〈本需求不做什么〉
- **依赖 / 风险**：〈例如需运维配合、模型供应商 SLA〉
```

## 维护说明

- 本文件侧重**方法论与协作格式**；具体缺陷列表会随提交变化，**不宜**把临时结论写死在本文件中（例外：团队确认的「已知限制」可单独维护一节，并注明日期）。
- 若新增模块（例如异步任务、计费、多租户），应在本文件的「审视维度」中增补对应小节。
