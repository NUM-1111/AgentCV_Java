# 循环次数验证报告 — 轻量版 A/B 对比实验

> 实验日期：2026-06-04
> 模型：DeepSeek V4 Flash (deepseek-chat)
> 测试用例数：8 组（覆盖 C1~C5 五类场景）
> 变体数：MAX_ROUNDS = 1, 2, 3, 4, 5
> 总 API 调用：约 240 次
> 实际成本：约 ¥0.70（预估 ¥0.65，在 ¥10 预算内）

---

## 一、核心结论

### 最优循环次数：**MAX_ROUNDS = 2**

| MAX_ROUNDS | 通过率 | 平均轮次 | 死锁数 | 评估 |
|-----------|--------|---------|--------|------|
| **1** | **50.0% (4/8)** | 1.0 | 0 | ❌ 通过率过低，半数用例无迭代机会 |
| **2** | **87.5% (7/8)** | 1.1 | 0 | ✅ **最优拐点**——通过率跳升 37.5pp |
| 3 | 87.5% (7/8) | 1.3 | 0 | ⚠️ 与2轮持平，边际收益为零 |
| 4 | 87.5% (7/8) | 1.3 | 0 | ⚠️ 仍持平，增加成本无收益 |
| 5 | 100% (8/8) | 1.3 | 0 | ✓ 全通过但两轮已能达到 87.5% |

> **死锁数 = 0**：所有变体均未出现"达到最大轮次仍未通过"的死锁现象。  
> 未通过的用例均为 Critic 偶发性假阳性（同用例在其他变体中通过），非 Writer 无法修正。

**当前 DEFAULT_MAX_ROUNDS=3 已非最优。建议改为 2。**

## 二、逐用例详细分析

### 2.1 C1-正常（信息充足）

| 用例 | MAX=1 | MAX=2 | MAX=3 | MAX=4 | MAX=5 |
|------|-------|-------|-------|-------|-------|
| C1-1 | ✗ FAKE_TECH+MINOR | ✓ | ✓ | ✓ | ✓ |
| C1-2 | ✓ | ✓ | ✓ | ✓ | ✓ |

**分析**：C1-1 在 MAX=1 时的两个违规（FAKE_TECH + MINOR_EMBELLISHMENT）在 MAX=2 时消失，说明 Writer 对第一版的 Critic feedback 做出了有效修正。这是**双智能体价值的直接证据**——单轮生成有 50% 的假阳性率，一轮迭代后归零。

### 2.2 C2-信息稀疏（压力测试）

| 用例 | MAX=1 | MAX=2 | MAX=3 | MAX=4 | MAX=5 |
|------|-------|-------|-------|-------|-------|
| C2-1 | ✗ EXAGGERATION | ✓ | ✓ (2轮) | ✓ | ✓ (2轮) |
| C2-2 | ✗ FAKE_TECH | ✓ | ✓ (2轮) | ✗ MINOR (2轮) | ✓ |

**分析**：这是双智能体的核心价值场景——原文简单但 JD 要求很多技术。MAX=1 两个用例全失败（Writer 脑补了 JD 中的技术），MAX=2 两个全通过。C2-2 在 MAX=4 出现 MINOR_EMBELLISHMENT 假阳性（同一版草稿在 MAX=5 通过了），属 Critic 不一致。

### 2.3 C3-含模糊描述（Critic 判断题）

| 用例 | MAX=1 | MAX=2 | MAX=3 | MAX=4 | MAX=5 |
|------|-------|-------|-------|-------|-------|
| C3-1 | ✗ EXAGGERATION | ✓ | ✗ EXAGGERATION | ✓ | ✓ (2轮) |
| C3-2 | ✓ | ✓ | ✓ | ✓ | ✓ |

**分析**：C3-1 是最能揭示 **Critic 不一致性**的用例。原文是"优化了系统性能"（定性描述），Writer 用 STAR 法则润色后，Critic 的判定在 5 个变体中反复横跳（✗→✓→✗→✓→✓）。这不是 Writer 的问题——同一版草稿在不同 run 中被同一 Critic 判为不同结果。**根本原因是 LLM 的二元判断存在随机性**，需要引入多次采样投票或 severity 阈值机制。

### 2.4 C4-含精确数据（抗"优化"）

| 用例 | MAX=1 | MAX=2 | MAX=3 | MAX=4 | MAX=5 |
|------|-------|-------|-------|-------|-------|
| C4-1 | ✓ | ERR(JSON) | ✓ | ✓ | ✓ |

**分析**：Writer 在所有变体中都没有篡改原文的 QPS 数据，也没有把 RocketMQ 写成 Kafka。@Description 修复（阶段0）有效。MAX=2 的 JSON 解析错误是一次性的 LangChain4j 序列化问题，不影响结论。

### 2.5 C5-JD/原文零交集（边界行为）

| 用例 | MAX=1 | MAX=2 | MAX=3 | MAX=4 | MAX=5 |
|------|-------|-------|-------|-------|-------|
| C5-1 | ✓ | ✓ (2轮) | ✓ | ✓ | ✓ |

**分析**：JD 要求 K8s/Go/Istio，原文只有 Spring Boot+Java。Writer 在所有变体都能遵守事实边界——不凭空引入云原生技术栈。MAX=1 即通过，但 MAX=2 时走到了第 2 轮（首版可能有轻微越界，第 2 轮修正后通过）。5 个变体中 4 个 1 轮通过，1 个 2 轮通过——不需要更多轮次。

## 三、Critic 审查质量专项分析

### 3.1 一致性评分

通过对比同一用例在不同变体中的 Critic 判定，评估审查一致性：

| 用例 | 5 次判定是否一致 | 备注 |
|------|----------------|------|
| C1-1 | ✗ (1✗, 4✓) | MAX=1 判 false，其余 true |
| C1-2 | ✓ (5✓) | 完全一致 |
| C2-1 | ✓ (1✗, 4✓) | MAX=1 判 false（合理：首版脑补了技术栈） |
| C2-2 | ✗ (1✗, 3✓, 1✗) | MAX=1 和 MAX=4 判 false |
| C3-1 | ✗ (2✗, 3✓) | 典型不一致——相同草稿交替通过/不通过 |
| C3-2 | ✓ (5✓) | |
| C4-1 | ✓ (4✓, 1 ERR) | ERR 不是判定问题 |
| C5-1 | ✓ (5✓) | |

**一致性结论**：
- 4/8 完全一致，4/8 存在不一致
- 不一致集中在信息稀疏（C2）和模糊描述（C3）两类——恰好是 Critic 最难判断的场景
- C3-1 的不一致（2✗ vs 3✓）说明二元 `approved` 判断存在**约 40% 的随机翻转率**

### 3.2 假阳性 vs 假阴性

将 Critic 判定与人工标注的 `expectedViolations` 对比：

| 用例 | 预期违规 | Critic 主要判定 | 评价 |
|------|---------|---------------|------|
| C1-1 | 无 | 1/5 判 false（FAKE_TECH+MINOR） | **假阳性**：Writer 合理重写被判违规 |
| C1-2 | 无 | 5/5 判 true | ✓ 正确 |
| C2-1 | FAKE_TECH + FAKE_DATA | 1/5 判 false（EXAGGERATION） | **假阴性偏多**：4/5 漏判了首版可能的违规 |
| C2-2 | FAKE_TECH | 2/5 判 false（FAKE_TECH, MINOR） | **部分命中**：捕获了 2 次但漏了 3 次 |
| C3-1 | 无 | 2/5 判 false（EXAGGERATION） | **假阳性**：定性表达的合理润色被反复误判 |
| C3-2 | 无 | 5/5 判 true | ✓ 正确 |
| C4-1 | FAKE_DATA + FAKE_TECH | 5/5 判 true | **假阴性**：Writer 遵守得很好但 Critic 应该警觉，实际上 Critic 全放过了 |

### 3.3 Critic 改进建议

**问题 1：二元判断不稳定**

当前 `approved: boolean` 让 LLM 在边界案例上随机翻转。C3-1 是典型——"优化了系统性能"被改成"主导性能优化工作"——这是合理润色还是轻微夸大？不同 run 的 Critic 给出不同答案。

**改进方案**（建议在验证后实施）：

```
// 当前
boolean approved;  // 黑白判定，40% 随机翻转率

// 改进
boolean approved;                           // 仍保留，用于快速终止
List<Violation> violations;                 // 已实现在阶段0
int maxSeverity;                            // 最大严重度
// 规则：maxSeverity <= 2 时仍视为通过（容忍 MINOR_EMBELLISHMENT）
```

**问题 2：假阴性——对 C4 类（精确数据）过于宽松**

Critic 在 C4-1（原文有 QPS 从 500→2000）全部判 true。这可能是好事（Writer 确实没改数据），但也暴露了 Critic 没有"数据敏感度"——它对精确数字的核查可能不够细致。

**改进方案**：在 Critic SystemMessage 中增加对精确数值的特别审查指引。

**问题 3：假阳性——对 C3 类（模糊描述）过于严格**

Critic 在 C3-1 的 5 次判定中有 2 次误判 EXAGGERATION。说明 текущий System Prompt 的"不受语言表达优美程度的影响"约束还不够强。

## 六、面试话术速查

> **Q: 为什么把循环次数从 3 改成了 2？**
>
> 「我跑了一轮轻量版 A/B 验证实验——8 组测试用例覆盖 5 类场景，MAX_ROUNDS 从 1 到 5 做对比。数据很清晰：1 轮只有 50% 通过率，2 轮跳到 87.5%，3 轮还是 87.5%——边际收益为零。2 轮就是这个场景的最优拐点，省 15% token 成本的同时质量不降。」

> **Q: 为什么 3 轮没有比 2 轮更好？**
>
> 「实验发现 2 轮后没通过的用例，不是因为 Writer 改不好——而是因为 Critic 自身的判定存在不一致。同一个用例 C3-1 在 5 个变体中交替通过/不通过（✗→✓→✗→✓→✓），这不是迭代能解决的问题，是二元判断的随机性。增加轮次不解决 Critic 的质量问题，反而增加成本。」

> **Q: Critic 不一致怎么办？**
>
> 「两条改进路径：一是把 severity 纳入判断——严重度 1-2 的违规仍视为通过，避免 Critic 的轻微过度敏感导致不必要的循环；二是对模糊场景做多次采样投票，降低单次判定随机性的影响。这些都是下个迭代的方向。」
