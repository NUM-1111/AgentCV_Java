# F1 — 多维评分系统设计

> **对应需求**：从单一 `matchScore` 扩展为三维评分（JD匹配40% + 内容质量35% + 格式规范25%）
> **涉及代码**：`ResumeScoringAgent.java`, `OptimizationReport.java`, `ResumeOptimizationService.java`

---

## 一、架构全景：三个 Agent 的分工

```
ResumeController
  └── ResumeOptimizationService（普通 @Service，三阶段编排）
        ├── Phase 1: ResumeScoringAgent（@AiService，无 Tool）
        │     输入：JD + 简历文本
        │     输出：ScoreResult（三维评分 JSON）
        │     职责：评估匹配度，纯 LLM 判断
        │
        ├── Phase 2: ResumeWriterAgent（@AiService，无 Tool）
        │     输入：JD + 原文 + Critic 反馈
        │     输出：WriterDraft（改写后的 bullet points）
        │     职责：以原文为事实边界，用 STAR 法则改写
        │
        └── Phase 3: FactCriticAgent（@AiService，注册了 FactCheckTool）
              输入：原文 + 草稿
              输出：CriticReport（通过/打回）
              职责：交叉比对原文 vs 草稿，核查事实准确性
```

**关键事实：Scoring 和 Writer 没有 Tool，Critic 有 Tool。**

## 二、从一维到三维：为什么要拆？

### 现状（一维）

```json
{
  "matchScore": 78,
  "matchedSkills": ["Java", "Spring Boot"],
  "missingSkills": ["Redis"],
  "improvementAdvice": "补充 Redis 与高并发项目经验。"
}
```

**问题**：78 分到底代表什么？是技能不匹配扣了 20 分，还是格式扣了 20 分？不可解释。

### 目标（三维）

```json
{
  "overallScore": 78,
  "jdMatch": {
    "score": 85,
    "matchedSkills": ["Java", "Spring Boot"],
    "missingSkills": ["Redis"]
  },
  "contentQuality": {
    "score": 70,
    "highlights": ["有量化成果"],
    "improvements": ["缺少 STAR 结构中的 Action 描述"]
  },
  "format": {
    "score": 80,
    "issues": ["信息密度偏低，部分段落过于冗长"]
  },
  "advice": "建议在项目经历中补充具体技术决策过程，使用 STAR 句式重写关键段落。"
}
```

**权重公式**：`overallScore = jdMatch.score × 0.4 + contentQuality.score × 0.35 + format.score × 0.25`

拆解后的价值：
- **可解释**：用户知道自己在哪个维度丢分
- **可行动**：`improvements` 和 `issues` 给出了具体的修改方向
- **可对比**：改写前后两次评分可以 diff，量化改进幅度

## 三、评分精度问题：诚实的 trade-off

### 核心问题：评分靠 LLM 一次性判断，没有外部验证，靠谱吗？

**直接回答：不靠谱，但它是当前阶段的最优解。**

### 为什么没有更好的方案？

| 方案 | 可行性 | 问题 |
|------|--------|------|
| LLM 自评 | ✅ 当前方案 | 既当运动员又当裁判，分数不可信 |
| 人工标注 ground truth | ❌ | 需要大量 HR 标注数据，超出现阶段范畴 |
| ATS 系统模拟 | ❌ | 不存在可集成的真实 ATS API |
| 关键词匹配算法 | ⚠️ | 可以算技能覆盖率，但无法评估"写得好不好" |

### 那评分有什么用？

**评分不是学术评估，是产品体验**：
- 用户需要的是"告诉我哪里不好，怎么改"，不是"绝对精确的分数"
- 三维拆解的价值在于 `missingSkills`、`improvements`、`issues` 这些**具体反馈**
- `overallScore` 的数字本身只是摘要，不是结论

### 面试话术

> "评分系统用的是 LLM 一次性判断，它不像 Critic 有 FactCheckTool 做交叉验证。这是有意识的设计 trade-off——简历评分的本质是主观评估，不存在 ground truth。我们用三维拆解 + 具体反馈来让评分可解释、可行动，而不是追求数字本身的精确度。"

## 四、评分结果是否影响改写？（当前答案：不影响）

### 现状

Writer 的 `rewrite()` 方法签名只接收三个输入：

```java
WriterDraft rewrite(
    @V("jdText") String jdText,
    @V("originalProjectText") String originalProjectText,
    @V("criticFeedback") String criticFeedback
);
```

**评分结果没有传进 Writer。** 在 `ResumeOptimizationService.optimize()` 里：

```java
ScoreResult score = scoringAgent.score(...);  // Phase 1
log.info("matchScore={}", score.matchScore()); // 打了个日志就被丢弃了
runActorCritic(jdText, originalProjectText);   // Phase 2: Writer 不知道评分
```

### 改写"有效性"靠什么保证？

| 防线 | 保证的是 | 不能保证的是 |
|------|---------|-------------|
| Writer System Prompt | 不捏造数据、不虚构技术 | 改完后是否更匹配 JD |
| Critic（+ FactCheckTool）| 事实准确性（91% 精确率） | 改完后是否更有竞争力 |
| Actor-Critic 循环（最多 2 轮） | 修正事实错误 | 语义质量的提升 |

**缺失的一环**：没有人回答"这个改写版本比原始版本好在哪里"。

### 未来扩展方向

1. **把评分结果喂给 Writer**：让 Writer 知道"你缺失了 Redis"，针对性强化相关表述
2. **before/after 评分对比**：改写前后各评分一次，展示分数变化——比一次评分更有说服力
3. **A/B 测试**（远期）：收集用户对改写结果的 accept/reject 行为，隐性反馈比 LLM 自评可信

### 面试话术

> "当前架构下 Writer 和评分是解耦的——评分是给用户看的，Writer 只依赖 JD + 原文 + Critic 反馈。改写有效性靠的是两道防线：Writer 的 prompt 约束（不捏造）+ Critic 的事实核查（91% 精确率），而不是评分引擎的反馈。这是有意识的设计选择——与其让不精确的评分去污染改写方向，不如先确保安全性和事实准确性。有效性验证留给未来的 before/after 评分对比。"
