| 层 | 定义 | 判断标准 | 执行方式 |
|----|------|---------|---------|
| **改进层** | 需要实际优化技术/设计的项目改造 | 回答"没做过""没有数据"时无法靠背话术弥补 | 写代码、加功能、跑实验 |

## 一、改进层 — 需要实际优化技术/设计的项目改造

> **说明**：不是背诵能解决的，需要改代码、加功能、跑实验才能填补的短板。这些是项目层面的"硬伤"。

### I-1. 效果验证量化体系 🔴 最高优先级

**来源**：真实二面段六（P1）+ 模拟面试Q3四层追问

**问题**：AgentCV系统的核心输出质量完全没有自动化度量——10个样本人工评审，无标准化打分规则。面试官在模拟中已给出完整改进方案（"维度分+相似度分+ATS覆盖率"三位一体）。

**改进方案**：

| 维度 | 实现方式 | 产出 |
|------|---------|------|
| **维度分** | JD核心要求拆成结构化评分维度（技术匹配度/项目经验相关性）→ Critic按维度打分 | 每个改写输出附带5维度雷达图 |
| **相似度分** | JD采分点向量化 → 与改写后简历计算余弦相似度 | 0-1浮点数 |
| **覆盖率分** | ATS关键词匹配测试 → 统计JD核心关键词在改写后简历中的覆盖率 | 百分比 |

**实施步骤**：
1. 手动标注10-20组JD的采分点做ground truth
2. 实现采分点向量化+余弦相似度计算（复用Ollama Embedding或DeepSeek Embedding）
3. 实现ATS关键词匹配（复用TextTrimmer的正则能力）
4. 改造Critic Agent输出结构，增加`QuantitativeScore`字段
5. 在golden-test-set上跑全量对比（改写前 vs 改写后的三维分数变化）

**参考文档**：模拟面试L131 — 面试官补充的完整方案，已有设计蓝图。

---

### I-2. RAG项目Chunking策略补齐 🟠 高优先级

**来源**：模拟面试Q2 overlap逻辑矛盾追问

**问题**：TokenTextSplitter默认切分，无overlap；用IVF_FLAT追求精度+双检索阈值追求召回率，但chunk边界语义断裂可能让两者打折扣。

**改进方案**：
- 用RecursiveCharacterTextSplitter替代（或与TokenTextSplitter做A/B对比）
- 设置overlap=100 token（候选人在模拟中自己提出的数值）
- 跑10个测试query的A/B：TokenTextSplitter无overlap vs RecursiveCharacterTextSplitter有overlap，对比Top-8召回质量

**实施步骤**：
1. Spring AI的TokenTextSplitter默认构造不支持overlap → 换用自定义splitter或在切分后手动拼接overlap
2. 在Milvus中建两个collection做A/B：`intellivault_chunks_v1`（旧）vs `intellivault_chunks_v2`（新）
3. 用10个测试query分别检索，人工标注Top-8相关性
4. 跑完A/B后决定是否全量迁移

### I-3. 产品合规免责声明 🟠 高优先级

**来源**：模拟面试Q4合规性辩论

**问题**：AgentCV系统完全没有关于"简历真实性"的任何提示或声明。候选人当时把免责声明斥为"制造需求"——暴露了产品思维盲区。

**改进方案**：
- 在最终输出页面/API响应中加一行："本优化基于用户提供的原始内容，建议确保经历真实有效"
- 在系统输入页面加用户须知："请提交真实、准确的个人履历信息"

**实施步骤**：
1. API响应模型增加`disclaimer`字段
2. 前端（如有）在最终输出卡片底部加提示行
3. 成本：1个字段 + 1行前端代码，边际成本几乎为零

### I-4. 成本基准数据测算 🟠 高优先级

**来源**：真实二面段六 + 模拟面试Q5成本讨论

**问题**：单/多Agent无成本对比数据，100份批量成本无测算。面试中被问到"I-100份同时进系统，单份平均成本能控制在什么范围"时无法回答。

**改进方案**：
- 取10份不同长度的简历跑现有流程（3轮迭代+双Agent配置）
- 记录每次API调用的token消耗（prompt_tokens + completion_tokens）
- 按DeepSeek V4-Flash官方定价计算单份平均成本
- 对比单Agent方案（仅Writer、无循环）vs 双Agent方案（Writer+Critic+3轮）的成本差异

**产出**：可脱口而出的成本数据——"单份简历平均消耗XX token，成本约¥X.XX，相比单Agent方案增加X%但是换来了87.5%的通过率提升"

**实施步骤**：
1. 在日志AOP中增加token计数（已有AI-Call日志，可复用）
2. 跑10份测试简历，收集token数据
3. 算平均值和P99
4. 准备15秒话术

### I-5. Token阈值10K数据文档化 🟡 中等优先级

**来源**：复习计划4模块1已有Golden Set 8组token分布数据（实验3）

**问题**：数据已经有了（8组Golden Set token分布 486-604，10K是实测最大值的16.6倍），但候选人从未在面试中完整抛出过数据链。

**改进方案**（非代码改动，是数据整理）：

- 确保面试时能15秒讲清这个数据链

### I-6. "通过率"精确定义 + 实验数据标注 🟡 低优先级

**来源**：模拟面试Q5发现

**问题**：从未明确87.5%是Critic自动评分的通过率还是人工评审的通过率。面试官如果追问"通过率怎么定义的"需要有精确回答。

**改进方案**：
- 在循环次数验证报告中增加一行定义说明："通过率 = Critic评分通过率（maxSeverity ≤ 2）——自动评分，非人工评审"

### C-2. Actor-Critic评分逻辑矛盾修正 🔴 最高优先级

**来源**：一面已有标记为P1，二面仍然出现同样逻辑矛盾

**问题**："权重从重往轻"+"取最大评分"构不成完整逻辑链——没说清楚为什么取最大值，没说maxSeverity阈值为什么≤2是通过。

**修复话术（15秒）**（来自复习计划4模块5.2）：
> "Critic输出四个维度的违规判定——FAKE_DATA/FAKE_TECH/EXAGGERATION/MINOR_EMBELLISHMENT，每个违规有自己的严重程度（severity 1-5）。Coordinator取所有违规中的maxSeverity做决策——≤2说明只有轻度措辞问题，直接放行；≥3说明存在事实性违规，触发重写。四类违规中FAKE_DATA和FAKE_TECH是致命的，severity初始值就在4-5；EXAGGERATION是3；MINOR_EMBELLISHMENT是1-2。所以maxSeverity策略本质上就是'有致命违规就拦，没致命就放'。"

**禁止再说**："权重从重往轻"。

### C-3. 消除"大概/可能"措辞 🔴 最高优先级

**来源**：模拟面试Q1-Q7全场统计7次"大概/可能"

**问题**：在面试官耳中，"大概"会系统性降低所有回答的可信度——即使"87.5%"本身是一个精确数字，"大概是从50%、80%再到87.5%"的说法也会让面试官怀疑这个数字是否经过严格测试。

**修复方案**：
- 以后所有模拟面试强制禁止使用"大概/可能/应该"
- 每个数字必须有确定值，如果不确定就说"我不确定具体数字，但我可以说明我当时的设计逻辑是……"
- 87.5%不能说"大概是从50%、80%再到87.5%"，要说"实验数据是50%、80%、87.5%"

### C-11. Function Calling基础概念 🟠 高优先级

**来源**：复习计划4模块2遗留问题

**问题**：问两次都说"不熟悉"，面试官放弃追问

**修复话术（20秒）**（来自复习计划4模块2）：
> "Function Calling是让LLM在运行时自主决定调用外部函数的能力。比如用户问'今天北京天气？'，模型不瞎编，而是输出一个函数调用请求`getWeather('北京')`，我的代码执行真实API查询，结果返回模型生成准确回答。和Skill的区别：Skill由代码决定何时调用，Function Calling由模型自己决定。我的项目输入完全预知（JD+简历），不需要模型动态获取外部信息，所以没用。StageThree规划了Tool Calling——比如让Writer自动搜索目标公司的JD数据库来增强改写建议。"

| 机制 | 用途 | 关键API | 一句话 |
|------|------|---------|--------|
| **CountDownLatch** | 等待N个线程完成 | `new CountDownLatch(N)` → `countDown()` → `await()` | 计数器归零时唤醒等待线程，一次性使用 |
| **Thread.join()** | 等待单个线程结束 | `thread.join()` / `thread.join(timeout)` | 调用方阻塞直到目标线程执行完毕 |
| **CyclicBarrier** | N个线程互相等待 | `new CyclicBarrier(N, runnable)` → `await()` | 所有线程到达屏障后一起继续，可循环使用 |
| **ExecutorService.awaitTermination()** | 等待线程池所有任务完成 | `shutdown()` → `awaitTermination(timeout, unit)` | 先关闭线程池再等待 |
| **CompletableFuture.allOf()** | 等待多个异步任务完成 | `CompletableFuture.allOf(f1, f2).join()` | 现代异步编程首选 |
| **wait()/notify()** | 线程间通信（低级） | `obj.wait()` / `obj.notifyAll()` | 必须在synchronized块内使用 |
| **Semaphore** | 控制并发数量 | `acquire()` / `release()` | 许可证机制 |
| **Phaser** | 多阶段屏障 | `register()` / `arriveAndAwaitAdvance()` | JDK7+，更灵活的CyclicBarrier |

**A-1.2 主线程等待所有子线程完成——话术（30秒）**：
> "最常用三种方案。CountDownLatch——构造时设计数器为子线程数，主线程await()阻塞，每个子线程finally块里countDown()，计数器归零主线程继续。Thread.join()——主线程for循环对每个子线程调join()。线程池方案——executor.shutdown()后awaitTermination(60, TimeUnit.SECONDS)。选型上CountDownLatch最干净——不需要持有线程引用，适合线程由线程池管理无法直接join()的场景。"

**A-1.3 扩展学习**：
- 线程池参数（corePoolSize/maxPoolSize/keepAliveTime/BlockingQueue/RejectedExecutionHandler）
- volatile vs synchronized vs Lock vs Atomic
- ThreadLocal原理与内存泄漏

### A-2. HashMap / Java集合框架 🔴 最高优先级

**来源**：真实二面段十六（P0致命）

**盲区**：hashCode/equals口误、哈希冲突原因说不出、线程不安全场景不全

**A-2.1 HashMap哈希原理速记卡**：

```
put(key, value)流程：
1. key.hashCode() → 获取32位原始hash值 h
2. (h = key.hashCode()) ^ (h >>> 16) → 高16位与低16位异或扰动
3. (n - 1) & hash → 取模定位桶（n是桶数，2的幂）
4. 桶为空 → 直接放入
5. 桶非空 → equals()判断是否同key
   - 同key → 覆盖
   - 不同key → 链表追加 / 红黑树插入
```

**A-2.2 哈希冲突的原因（15秒）**：
> "哈希冲突是数学必然。哈希函数把任意对象映射到有限个桶中——从无限域到有限域的映射，抽屉原理保证必然冲突。HashMap通过扰动函数(h ^ h>>>16)降低冲突概率，通过链表+红黑树解决已发生的冲突。"

**A-2.3 线程不安全三场景（30秒）**：
> "HashMap线程不安全有三个典型场景。一是JDK7扩容resize时的头插法导致环形链表——两个线程同时扩容，一个线程的next指针被另一个线程修改，形成环，get()时死循环CPU 100%。二是put操作中size++非原子——多线程同时put可能导致实际size小于元素数，数据丢失。三是扩容期间读写并发——一个线程在transfer迁移数据，另一个线程get可能读到null。解决方案：ConcurrentHashMap用分段锁+CAS、Collections.synchronizedMap用包装器锁。"

**A-2.4 hashCode与equals口诀**：
> "hashCode相等不一定equals（哈希碰撞）。equals相等hashCode必须相等（契约）。重写equals必须重写hashCode，否则HashMap/HashSet行为异常。"

**A-2.5 扩展学习**：
- ConcurrentHashMap分段锁演进（JDK7 Segment → JDK8 CAS+synchronized）
- ArrayList vs LinkedList / TreeMap / LinkedHashMap

- 幻觉治理手段体系：RAG / System Prompt约束 / Self-Consistency / Actor-Critic / RLHF

**话术（45秒）**（来自复习计划4段十）：
> "从Transformer架构层面看，幻觉有三个来源。第一是概率采样——模型输出是对下一个token的概率分布做采样，temperature>0时每次都可能有不同的选择，当模型对某些事实不确定时概率分布平坦，更容易采样到错误token。第二是训练数据的局限——模型学到的是训练语料中的统计相关性而非真正的因果关系，比如训练数据中'QPS提升'经常和'优化'共现，模型就可能在没有真实数据的情况下也生成'QPS提升30%'。第三是位置编码的近似——Transformer用固定位置编码，长文本中间位置的信息提取能力下降（Lost in the Middle）。我的Critic就是针对第二种——事实幻觉——做专门的事实核查。"
