# 超纲问题答题框架

> **定位**：当面试官问到一个你完全没准备过的问题时，这份文档提供"结构化的不知道怎么回答"的模板。
>
> **核心原则**：不是所有问题都要有答案，但每个"不知道"都要有框架。
>
> **用法**：面试前通读一遍每个话题的框架要点，不求记住全部，但求慌乱时能抓住一个骨架。

---

## 通用技巧：三个级别的答题策略

### Level 1：拆解框架（首选，适用于任何问题）

当大脑空白时，**先说维度，再往里填内容**：

> 「这个问题我会从 [X] 和 [Y] 两个方向思考。首先在 [X] 方面...」

边说边想——你不需要事先知道 X 和 Y 的具体内容，常见的万能维度：

| 拆解维度 | 适用的话题 |
|---------|-----------|
| 减量 / 提效 / 扩容 | 成本优化、性能优化、高并发 |
| 预防 / 检测 / 恢复 | 可靠性、容错、安全 |
| 数据层 / 业务层 / 展示层 | 架构设计、系统拆分 |
| 短期（MVP）/ 中期 / 长期 | 任何"你怎么规划"的问题 |
| 用户侧 / 服务端 / 模型侧 | AI 应用优化 |

### Level 2：承认 + 给思路（适用于明显超纲的话题）

> 「这块我目前实践不够深，但我的理解是...」（降预期）
> → 给出 2~3 个思路要点
> → 「这是我现在能想到的方向，如果有机会深入我会...」（留余地）

### Level 3：用已知推导未知（适用于有关联性的话题）

> 「类比我们项目里做过的 [已知方案]...其实这个问题的核心挑战也是...所以我觉得可以从 [已知经验] 推导...」

## 话题一：高并发 & 成本优化

> 这是 2026-06-03 模拟面试中崩盘的话题。当前项目确实没做，但框架式回答完全够用。

### 答题骨架

```
维度一：减量 — 减少不必要的调用
  ├─ 输入层：TextTrimmer 裁剪噪声 + TokenEstimator 精确控制（已实现 ✓）
  ├─ 缓存层：高频 JD 改写结果 Redis 缓存（规划中）
  └─ 限流层：单用户 QPS 限制（规划中）

维度二：提效 — 降低单次调用成本
  ├─ 模型侧：小模型做 Critic（二元判断任务不需要大模型）
  ├─ 策略侧：动态终止条件（feedback 连续重复 → 提前停止）
  └─ 量化侧：INT8 量化降低推理成本

维度三：扩容 — 支撑高并发
  ├─ 异步化：ThreadPoolExecutor + RabbitMQ，请求先入队
  ├─ 前端：SSE 推送结果（不阻塞 HTTP 连接）
  └─ 部署：模型服务独立扩缩容
```

### 防御要点

| 可能追问 | 回答 |
|---------|------|
| 「为什么不现在就做？」 | 「MVP 阶段我先验证核心架构——幻觉治理、token 管理、输出校验、可观测性。这些跑通后再补高并发和成本优化，属于有意识的排列。」 |
| 「小模型做 Critic 比大模型差多少？」 | 「二元判断的准确率差不了太多——判断"数字是否存在原文"比"生成好内容"简单得多。」 |
| 「Redis 缓存命中率怎么保证？」 | 「JD 的关键词提取后做相似度匹配，相似 JD 复用同一套改写模板。」 |

## 话题二：系统可靠性 & 容错

### 答题骨架

```
维度一：输入防护
  ├─ 长度校验：ResumeController 3000 字符上限
  ├─ Token 预估：超限提前拦截，不依赖模型报错
  └─ 异常映射：IllegalArgumentException → 400（用户问题），AiOutputValidationException → 500（模型问题）

维度二：输出校验（已有 ✓）
  ├─ extractJsonObject → FieldNameNormalizer → Jackson 宽松解析 → Bean Validation
  └─ 任何一层失败都有明确的异常和日志

维度三：兜底策略
  ├─ 3 轮循环后强制输出（不报错）
  ├─ 全局异常处理统一返回格式
  └─ MDC traceId 全链路追踪，一个 grep 定位问题
```

## 话题三：Agent 可观测性

### 答题骨架

```
维度一：日志层（已有 ✓）
  ├─ AOP 切面：WebLogAspect + AiCallLogAspect 零侵入记录
  ├─ MDC traceId：TraceIdFilter 注入，全链路关联
  └─ grep traceId 一键还原请求全貌

维度二：Agent Trace（规划中）
  ├─ Langfuse / LangSmith 记录每轮 Prompt + 响应 + token
  └─ 面试时有可视化面板展示

维度三：监控告警（规划中）
  ├─ 平均循环轮次、幻觉拦截率、P99 延迟
  └─ 超出阈值自动告警
```

## 话题四：AI 应用的安全问题

### 答题骨架

```
维度一：Prompt 注入防护
  ├─ 用户输入的简历文本直接注入 UserMessage → 需做输入清洗
  └─ 当前 MVP 未做（单人使用场景风险可控）

维度二：输出安全
  ├─ 结构化输出 + Bean Validation 确保数据格式合法
  └─ 但未做内容安全审核（模型可能输出有害内容）

维度三：数据安全
  ├─ 简历数据不落库（Stateless），降低泄露风险
  └─ API Key 通过环境变量注入，不硬编码
```

## 话题五：Prompt 工程

### 答题骨架

```
维度一：System Prompt 设计原则
  ├─ 身份定义：「你是一位...」
  ├─ 硬约束：「禁止...」「只能...」—— 不是"请尽量"的软约束
  ├─ 角色隔离：Writer 和 Critic 用不同的 SystemMessage 切换角色

维度二：UserMessage 设计原则
  ├─ 结构化输入：{{变量名}} 占位，清晰标注「事实边界」
  ├─ 反馈驱动：首轮指令式，后续轮纠正式

维度三：Prompt 版本管理（当前短板）
  ├─ 目前硬编码在 Java 类里（MVP 迭代快，直观）
  └─ 后续抽到外部配置，做 A/B 测试
```

## 话题六：评测 & 质量保证

> 这是 2026-06-03 模拟面试中暴露的短板。

### 答题骨架

```
维度一：离线评测
  ├─ 黄金测试集：20 组「原文 + 刻意捏造的草稿」
  ├─ 统计 Critic 的召回率和精确率
  └─ LLM-as-Judge 做三方评判

维度二：在线对比
  ├─ 同一个输入跑单步 vs 双智能体
  └─ 对比幻觉率、循环通过率、token 消耗

维度三：业务指标
  ├─ 循环通过率分布（第一轮 X%、第二轮 Y%）
  └─ 用户满意度（如有反馈入口）
```
