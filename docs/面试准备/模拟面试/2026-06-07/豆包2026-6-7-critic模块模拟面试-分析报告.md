## 一、逐题分析

### Q1：日志系统能记录哪些信息？

**面试表现**：区分了常规日志和 AI 调用日志两个维度，提到会记录"模型调用参数、回答、各维度评分"。⭐⭐⭐⭐

**问题**：回答偏笼统，没有给出具体对照：
- **WebLogAspect**：HTTP 层 — 请求方法、URL、参数、响应、耗时
- **AiCallLogAspect**：AI 调用层 — 模型名称、Prompt/token 估算、响应内容、各维度评分详情

**改进**：练习"二维区分"话术：「我们有两套日志切面，WebLogAspect 管 HTTP 层，AiCallLogAspect 管 AI 调用层。一个 grep traceId 能还原完整请求链路，从 Filter 拦截到 AI 调用结束。」

### Q2：「参与开发」→「主导核心模块」属于哪种 violationType？severity 几分？

**面试表现**：绕了一圈讲"定性到定性""可大可小"，没有第一时间给出标准答案。⭐⭐

**标准答案**（见 `Violation.java` 第 12 行注释 + `FactCriticAgent.java` 第 58 行规则）：

> **violationType = EXAGGERATION，severity = 3**

理由：
- 原文"参与/负责" → bullet"主导/设计" = EXAGGERATION（不是 FAKE_DATA，因为没有捏造数字；不是 FAKE_TECH，因为没有引入新技术栈）
- severity=3 代表"明显的夸张，需要修正"
- 和 FAKE_DATA（severity=4-5）的本质区别：EXAGGERATION 是对已有事实的**程度放大**，FAKE_DATA 是**凭空捏造**不存在的事实

**改进**：violationType 四分类 + severity 档位必须能**脱口而出**，这是高频追问点。

### Q3（追问）：根据 severity 规则，maxSeverity≥4 才打回重写，那 severity=3 Coordinator 会直接通过吗？

**面试表现**：说"特殊情况特殊处理""可能通过也可能不通过""根据用户是否接受"。⭐ —— **这是本次面试最大的问题**。

**问题本质**：你给出的答案与代码实现**严重不一致**，且暴露出一个**设计缺口**。

#### 实际代码逻辑（RewriteCoordinatorService.java 第 115 行）

```java
if (criticism.approved()) {
    return new RewriteResult(draft, round + 1);
}
```

Coordinator **只检查 `criticism.approved()` 这个布尔值**，从未读取 `violations` 列表或计算 `maxSeverity`。

#### "severity 阈值容忍"在代码中的现状

| 位置 | 有没有提到 severity 阈值？ | 是代码还是注释？ |
|------|--------------------------|----------------|
| Violation.java Javadoc（第 13-17 行） | ✅ 提到 severity≤2 仍视为通过 | **注释** |
| FactCriticAgent.java SystemMessage（第 67-71 行） | ✅ 定义了 severity 1-5 分档 | **Prompt 中的指令** |
| RewriteCoordinatorService.java | ❌ 只检查 approved 布尔值 | **代码逻辑缺失** |

**结论**：severity 阈值容忍是一个"设计意图"但从未落地为代码。面试官追问 severity=3 的决策时，代码答案是「取决于 Critic 把 approved 设成 true 还是 false」，而你的回答是「灵活处理」——**两者都暴露了这个设计缺口**。

> 面试官敏锐地捕捉到了这个问题：「但这样就和之前设定的"根据 severity 最大值决策"的规则矛盾了。你觉得该如何解决这种规则与灵活性的冲突？」

### Q4（追问）：规则与灵活性的冲突怎么解决？

**面试表现**：承认问题存在，表示需要"重新明确产品定位"。⭐⭐⭐

> 「这个问题我会留意的」——这句话本身是诚实的，但面试官期望的是一个**有逻辑的解决思路**。

**参考回答**（应该给出的）：

> 这是一个好问题。本质上，`approved` 布尔值和 `maxSeverity` 阈值是两套决策逻辑：
> - `approved` 是 Critic 的**主观二分类判决**（LLM 容易出现边界随机翻转）
> - `maxSeverity` 是 Coordinator 的**客观阈值判决**（基于 severity 数字，更可解释）
>
> 我应该在 Coordinator 中**同时引入 maxSeverity 计算**作为第二道决策依据：
> ```java
> int maxSeverity = criticism.violations().stream()
>     .mapToInt(Violation::severity).max().orElse(0);
> 
> // approved=true 或 maxSeverity≤2 → 通过
> if (criticism.approved() || maxSeverity <= 2) {
>     return new RewriteResult(draft, round + 1);
> }
> // maxSeverity≥4 → 必须重写
> // maxSeverity=3 → 进入「人工确认」模式，由前端提示用户决定是否保留
> ```
>
> 这样把灵活性的决策权从代码逻辑转移到**用户**——severity=3 的 EXAGGERATION，让用户自己判断"参与→主导"能不能接受，而不是系统替用户决定。这既保持了规则一致性，又保留了灵活性。
