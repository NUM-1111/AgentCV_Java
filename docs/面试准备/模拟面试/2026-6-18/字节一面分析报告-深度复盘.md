**🎯 问题诊断**：这是全场最长、最详细的回答，也是候选人最熟悉的模块。但**阿里一面分析报告已明确标记的"权重+取最大值"逻辑矛盾在字节一面中再次出现**——这说明候选人要么没认真看分析报告中对这个问题的标注，要么理解了但在面试紧张中表述再次走形。

**候选人回答要点**：

### 段十九：🔴 算法题 — 循环依赖检测 (33:04 - 41:08) 🔴

**题目**：给定二元组列表（如[A,B]表示A依赖B），构建依赖关系图，判断是否存在循环依赖。

**候选人回答过程**：

4. 沉默约1分半后："暂时想不出来可以AC的方法，不耽误您时间了"

**🔍 逐字分析**：

这本质是**有向图判环**——LeetCode 207 Course Schedule / 拓扑排序 / DFS三色标记 / BFS Kahn算法。是后端面试的高频算法题。

| 候选人的尝试 | 缺失的 |
|-------------|--------|
| 提到了"链表"构建——靠近了图的邻接表表示 | 没有意识到这是图问题 → 没有提出DFS/BFS/拓扑排序 |
| 意识到"需要构建可遍历的东西" | 没有写出任何伪代码或思路框架 |
| | 没有提到"检测环 = DFS找back edge"或"拓扑排序节点数≠总节点数则有环" |

**🎯 问题诊断**：候选人没有识别出这是图论基础问题。对于一个简历优化项目的后端开发者来说，这个算法题考察的是"能否将业务依赖关系抽象为数据结构并解决"。字节一面出这道题说明岗位对基础算法有硬性要求。

**📊 严重程度**：🔴 P0（致命）——算法题完全没解出来，对后端实习岗位是严重扣分项。

**正确思路（30秒版）**：
> "这是有向图判环问题。我用邻接表构建图——Map<String, List<String>>，Key是服务名，Value是它依赖的服务列表。然后拓扑排序：维护每个节点的入度，BFS从入度为0的节点开始消除，每消除一个节点就把它的邻居入度减1。最后如果消除的节点数≠总节点数——有环。时间O(V+E)，空间O(V+E)。或者用DFS三色标记——0未访问/1访问中/2已完成——DFS时遇到状态1的节点就是环。"

### 模块B：Critic评分逻辑修正 🟠 高优先级

> 第三次出现"权重+取max"矛盾——必须彻底修正

#### B.1 正确的逻辑表述

不是"从高到低排序后取最高分"——这在面试官耳中听起来像是多个分数的某种聚合。

**正确的说法**：
- Critic对每条违规给出severity（1-5分）
- 取所有违规中**最大的severity**作为本次审查的总体判定
- 如果max severity ≤ 2 → 所有违规都在可接受范围内 → 通过
- 如果max severity ≥ 3 → 至少有一条严重违规 → 打回重写
- 这类似"一票否决"——重点看最严重的那个违规

#### B.2 为什么取max而不是加权加总

> "取max而不是加权加总的原因：一个简历可能有多处轻微措辞不当，但有一处假数据捏造。加权加总可能让'多处小问题'的总分超过'一个致命问题'——导致假数据被放行。取max保证：只要有一条致命违规，整个审查就不能通过。"
