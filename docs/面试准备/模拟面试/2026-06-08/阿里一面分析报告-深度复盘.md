### 段二：双Agent细节追问 (3:12 - 6:18)

### 段十：Agent间上下文传递机制 (17:38 - 19:07)

**面试官追问**：两个智能体之间的上下文传递是怎么传递的？包括传递哪些上下文？怎么传递？

**候选人回答要点**：
- Writer→Critic：改写后的文本内容 → 数组(编号+内容) → 拼接为常文本 → 交给Critic入参
- Critic→Writer：评分+改写建议 → 拼接 → 作为Writer下一轮入参

**🔍 逐字分析**：

回答本身框架是正确的（数据流方向+载体+拼接方式），但表述混乱：
- "初参""常文本""凭借"多处口误
- "数组构成的report"未提Violation/CriticReport等具体数据结构名
- 串联框架问题："你是用LangChain吗还是纯自己写的？"→回答反复拉扯

**正确表述（15秒版）**：
> "两个Agent之间通过结构化Java对象传递。Writer输出RewriteReport（bulletPoints+reasons），Coordinator提取bulletPoints拼接为编号文本传给Critic。Critic输出CriticReport（approved+violations+feedback），Coordinator提取feedback作为下一轮Writer的criticFeedback参数。全程是方法调用级别的数据流，不涉及中间存储或消息队列。串联编排在RewriteCoordinatorService.evaluate()内——一个for循环内串行调用两个Agent。"

**📊 严重程度**：P2（中度）——核心逻辑是对的，但表述不精练不自信，容易被面试官降级评价。

### 段十一：Spring AI vs LangChain4j 区别 (19:07 - 21:09)

**面试官追问**：Spring AI跟LangChain复杰（LangChain4j）它俩之间的区别是什么？为什么你有的时候用Spring AI，有的时候用LangChain？

**候选人回答要点**：
- LangChain是从Python迁移来的，更多主攻agent开发
- Spring AI更多考虑原生Spring环境
- 使用场景：Spring AI用在原先Spring框架下的Java应用做agent拓展，LangChain可能一开始就是仿照Python的LangChain去做agent智能体开发

**🔍 逐字分析**：

回答是**正确但不说服人**的教科书式区分。面试官想听到的是实践体感，比如：
> "我在两个项目里分别用了它们。Spring AI的优势是与Spring Boot生态无缝集成——比如它的ChatClient可以直接注入Spring管理的Bean。LangChain4j的优势是更丰富的Agent编排原语——@AiService/@SystemMessage/@UserMessage这套注解体系让定义Agent接口像写Java接口一样自然，而且对结构化输出的支持更成熟（@Description自动生成JSON Schema）。在这个简历优化项目中，我需要两个Agent做复杂编排+结构化输出，所以选了LangChain4j。如果我只需要在现有Spring应用中加一个简单的对话功能，我会选Spring AI。"

**📊 严重程度**：P1（严重）——回答显得像背诵而非实践体感，这是"项目经验不够深"的又一证据。

### 模块A：LLM基础认知补齐 🔴 最高优先级

> **目标**：建立LLM核心概念体系，能回答任何基础追问

#### A.1 Token & Tokenization

**当前状态**：完全空白，面试中沉默70秒

**需要掌握的内容**：

1. **Token的本质**：模型处理文本的最小语义单元，不是"字"也不是"词"
2. **BPE (Byte Pair Encoding)**：最常见的子词切分算法——从字符开始，统计频率最高的相邻对，合并为新token，循环到预设词汇量（如50257）
3. **中文Tokenization的特点**：
   - 一个中文字≈1.5-2个token（比英文略高）
   - 常见中文词汇（如"人工智能"）可能是一个token
   - 标点符号也是token
4. **Token ↔ 字符的估算关系**：
   - 中文：1字≈0.5-0.7 token（DeepSeek/千问实测约1.5-2字/token）
   - 英文：1单词≈1.3 token
   - 代码：波动极大，关键字短但变量名长

**话术准备（45秒版）**：

> "Token是LLM处理文本的最小单元，通过BPE子词切分算法生成。BPE从字符级别开始，循环合并高频字符对直到达到预设的词汇量。比如'人工智能'可能被BPE合并为一个token，而不是两个字分开。不同模型有不同tokenizer——GPT用tiktoken，DeepSeek用自研tokenizer——所以同一个文本在不同模型上的token数不一样。工程上做估算时，中文我用1字≈1 token的保守规则——实际大概是0.5-0.7 token/字——高估30%保证不误拦。"

#### A.2 上下文窗口 (Context Window)

**当前状态**：对自己用的DeepSeek V4上下文窗口完全不知

**需要掌握的内容**：

1. **定义**：LLM一次能处理的最大token数（输入+输出）
2. **主流模型窗口**：
   - GPT-4o: 128K
   - Claude 3.5 Sonnet: 200K
   - DeepSeek V2: 128K
   - DeepSeek V3/R1: 128K
   - DeepSeek V4（面试中提到的）: **需查证**，但你在面试中用的可能是V3/R1系列——需要搞清楚
3. **Lost in the Middle现象**：模型对长文本中间位置的信息提取能力显著下降
4. **上下文利用率与效果**：填满≠用好。大多数模型的"有效注意力"在前25%和后25%最好，中间50%容易被遗忘

**话术准备（30秒版）**：

> "DeepSeek V3的上下文窗口是128K。但我们设1万token的保守阈值，不是因为模型能力不够，而是基于'有效注意力'的概念——即使用128K的上下文，模型对中间位置的信息提取能力也会下降。1万token保证所有内容都在最佳注意力窗口内。另外就是成本——token消耗和上下文长度呈线性关系，业务上JD+简历的正常规模不会超过1万token，超过就说明用户输入了不合理的超长文本。"

#### A.3 Temperature & Top-P 等采样参数

**当前状态**：之前模拟面试中有temperature/max_tokens混淆（已在复习冲刺中修正）

**需要补充掌握的**：
- Top-P (Nucleus Sampling) vs Top-K
- Temperature与Top-P的交互效应
- Frequency Penalty / Presence Penalty
- max_tokens = 输出token上限（你已掌握）

**话术准备（20秒版）**：

> "Temperature控制输出分布的平滑度——0=确定性输出（每次都选最高概率token），1=按原始概率采样。Top-P是核采样——只从累积概率前P%的token中选。两者配合使用：Temperature=0.3 + Top-P=0.9 产生'稳定但不僵硬'的输出。我的项目里Writer用0.5让表达更丰富，Critic用0.2让审查判定更稳定。"

### 模块D：代码深度理解 — TextTrimmer正则预处理 🟠 高优先级

> **目标**：面试被问"具体截取什么"时，能脱口而出代码细节

#### D.1 你的代码做了什么（逐方法）

**TextTrimmer.trimResume(String text)**：
1. `extractSections(text, "工作经历", "项目经历", "工作经验", "项目经验", ...)` —— 14种关键词变体匹配
2. 返回拼接后的核心段落字符串
3. 如果没匹配到任何段落 → `fallbackTrim(text, 4000)` 兜底

**extractSections 内部逻辑**：
1. 按 `\n` 分行
2. 逐行匹配标题正则（支持序号前缀+中文/英文/数字序号+关键词+冒号）
3. 匹配到标题后收集该标题下的所有内容行
4. 遇到下一个合法标题 → 停止收集
5. 单段截断到1500字

**smartTruncate 内部逻辑**：
1. 如果文本长度 ≤ limit，直接返回
2. 在 `[70%limit, limit)` 窗口内从后往前找句子结束符（。！？！？\n）
3. 找到 → 在句子边界截断 + 加 `…[已截断]`
4. 找不到 → 硬截断（hardTruncate）

**fallbackTrim 兜底逻辑**：
1. 过滤垃圾行（福利/五险一金/联系方式/公司介绍）→ `NOISE_LINE_PATTERN`
2. 过滤纯标题行（短且无实质内容）
3. 如果过滤后内容 < 50字 → 退回原文（宁多勿少）
4. smartTruncate 截断

### 模块F：已有优势的主动出击话术 🟡 中优先级

> **目标**：面试中主动引导面试官到你准备最充分的模块

#### F.1 结构化输出四层Pipeline（在Critic回答中引出）

**触发时机**：当面试官问"Critic输出是什么格式？"或"怎么处理LLM输出的JSON不稳定？"

**30秒话术**：
> "LLM输出的JSON有三层不稳定：Markdown包裹（```json```）、非标准语法（注释/尾逗号/单引号）、字段漂移（match_score / MatchedScore）。我设计了四层防御pipeline：第一层extractJsonObject用indexOf找最外层花括号剥离Markdown；第二层FieldNameNormalizer用正则归一化25+种字段名变体；第三层Jackson开四个宽松开关（注释/尾逗号/单引号/未知字段忽略）；第四层Bean Validation做字段值合法性拦截（matchScore必须在0-100）。四层下来，即使LLM输出格式很差也不会让系统崩——返回明确错误码而不是黑盒报错。"

#### F.2 AOP双切面设计（在日志/可观测性话题中引出）

**触发时机**：当面试官问"你怎么做日志？"或"怎么追踪一次请求？"

**40秒话术**：
> "日志系统用了AOP双切面+MDC全链路追踪。两个切面各司其职：WebLogAspect用@within(RestController)拦截所有Controller——记录HTTP层（URL/方法/IP/响应时间/状态码）。AiCallLogAspect用execution精准切入evaluate()方法——记录AI调用层（入参长度/评分/技能匹配数/token趋势）。
>
> 为什么拆两个？单一职责——Web层关心HTTP维度，AI层关心业务维度。合在一起也能跑，但排查时grep '[WEB]'和grep '[AI-CALL]'没法分离。拆分后每条日志只包含自己层的关注点，但共享同一个traceId，grep还原全链路即可。
>
> 两个切面的入参策略也不同：Web层入参DTO序列化为JSON+200字符截断，AI层入参是完整JD+简历，只记长度不记全文——防日志爆炸+防敏感信息泄露。"

#### F.3 成本三维框架（在"怎么控制成本"话题中主动出击）

**30秒话术**：
> "成本控制我用三维框架——减量、提效、扩容，按边际收益递减曲线排优先级。
> 第一维减量——在数据进LLM前砍输入。TextTrimmer把JD从5000字裁剪到1500字，TokenEstimator在预处理阶段拦截超长输入。这两个组件让每次调用从源头被控制。
> 第二维提效——让便宜模型干更多活。Writer用主力模型（强语义），Critic做封闭域事实匹配可替换小模型。模型参数上Writer高temperature让表达生动，Critic低temperature让审查稳定，max_tokens设硬上限防冗长。
> 第三维扩容——前两维到极限后的架构兜底（异步化202+taskId），MVP阶段明确不做。
> 顺序很重要——先做减量一次开发终身省钱，再做提效有风险需验证，最后扩容成本最高。"

#### G.1 问题驱动版自我介绍（45秒）

> "面试官你好，我叫蒋毅武，哈尔滨工程大学22届毕业生。
>
> 我在做一个Agent简历优化系统，起因是发现通用LLM改简历时有一个典型问题——它会脑补不存在的技术和数据，比如把'参与支付模块开发'扩写成'主导设计支付系统，QPS提升30%'。这些幻觉对求职者是致命的。
>
> 我的解决方案是用Actor-Critic双智能体架构——Writer负责按JD优化表达，Critic做严格事实核查。Critic不是简单判过/不过，而是输出结构化违规报告——每条违规有类型（假数据/假技术/夸大/过度润色）和严重程度（1-5分）。Coordinator基于severity阈值做智能决策——轻度措辞不当容忍放行，严重捏造触发重写。实验验证3轮循环达到87.5%通过率且边际收益递减。
>
> 另外在输入输出两侧做了完整的防护工程——输入侧上下文裁剪+Token预估防溢出，输出侧四层容错pipeline防JSON格式漂移，AOP双切面+MDC做全链路日志。整个项目用Spring Boot + LangChain4j + DeepSeek实现。"
