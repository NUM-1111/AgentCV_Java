**📊 严重程度**：P1（严重）——如果面试官是一面的同一个人或能看到一面记录，这个问题会被标记为"上次指出的问题没有改进"。

### 段六：写简历怎么保证写得好 (10:38 - 13:30)

**面试官**：你写的这部分怎么保证他写的好呢？

**候选人回答要点**：
- 诚实承认"主要是靠Critic去约束，还是看人工评审——没有设计内部可量化的指标"
- 然后提出了一个改进方案：用另一个Agent做两维度评分——JD-简历向量相似度计算 + 技术栈/场景维度评分

**🔍 逐字分析**：

| 亮点 | 问题 |
|------|------|
| ✅ **诚实承认不足**——"可能没有设计一个内部比较能量化的指标，还是由模型自主评分" | 🔴 但这个诚实暴露了一个严重的设计缺陷——一个Agent系统的核心输出质量竟然**没有自动化度量** |
| ✅ 临场提出改进方案（相似度+多维度评分）展现了思考能力 | 🔴 改进方案存在概念缺陷——JD和简历做向量相似度是信息检索领域的做法，但简历优化场景中JD和简历本身就是不同体裁的文本，直接做similarity匹配意义有限 |
| ✅ 有"可以追踪的办法"的意识 | 🔴 如果面试官追问"你这个向量相似度方案在工程上怎么实现"——候选人可能会卡住，因为这个方案显然没有真正实现过 |

**🎯 问题诊断**：这个回答是典型的"诚实但不加分"类型。面试官问"怎么保证写得好"——这是在考察你对输出质量的工程思考。你直接承认没有量化指标，然后又给了一个没有被验证过的方案，面试官的结论会是"这个系统在质量保障上还停留在demo阶段"。

**正确的回答**（结合项目实际）：
> "我们有三层质量保障。第一层是Critic的自动审查——四个维度的违规检测，实验数据显示能拦截87.5%的幻觉性改写。第二层是循环修正机制——最多3轮，不满意就重写，每轮都有历史feedback作为约束。第三层是我们在golden-test-set上做了端到端验证——用20组真实JD+简历对做测试，人工标注通过率。目前最大的短板是缺乏自动化的量化评分——这也是我在StageThree规划中要引入的方向。"

**📊 严重程度**：P1（严重）——暴露了项目在质量度量上的工程短板。

### 段十五：🔴 Java多线程 — 子线程全部完成再继续主线程 (25:56 - 27:37)

**面试官**：我有一个主线程，起了很多子线程，要求子线程全部运行结束过后主线程才能往下走。如果让你实现的话，你有几种实现方式？

**候选人回答**（经过约30秒思考）：
> "第一种——给子线程和父线程做一个锁的竞争，子线程完毕之后释放锁，父线程继续。第二种——主动休眠父线程，子线程全部跑回来再唤醒。"

**候选人**："嗯……嗯……行那关于这方面可能对这个深度还不够深。"

**🔍 逐字分析**：

这是全场**技术最硬的一道题**，也是候选人回答最差的一道。正确答案和候选人的回答对比：

|-------------|---------|---------|

| "休眠父线程再唤醒" | 方向对但实现方式不对 | **Thread.join()**——主线程对每个子线程调用join()，阻塞直到子线程结束。或者**CyclicBarrier**（所有线程到达屏障后一起继续） |
| 未提及 | — | **ExecutorService + awaitTermination**——线程池关闭后等待所有任务完成 |
| 未提及 | — | **CompletableFuture.allOf().join()**——现代Java异步编程方案 |
| 未提及 | — | **Phaser**——更灵活的屏障同步 |

更致命的是：
1. 候选人说"锁竞争"——这个概念在Java中是synchronized/Lock机制，用于互斥访问共享资源，不是用于"等待所有线程完成"的场景
2. "休眠父线程再唤醒"——Thread.sleep() + 怎么唤醒？候选人说不出具体API（notify/notifyAll需要配合wait使用，而且这也是用于线程间通信而非"等待所有完成"）
3. 当面试官追问"怎么判断子线程执行完了"——候选人直接缴械投降

**📊 严重程度**：🔴 P0（致命）——Java多线程基础空白，对后端开发岗位来说这是核心能力缺失。

**正确回答（30秒版）**：
> "至少有四种方式。第一种CountDownLatch——初始化时设置计数器为子线程数，主线程await()阻塞，每个子线程执行完调用countDown()，计数器归零主线程自动唤醒。第二种Thread.join()——主线程遍历所有子线程调用join()，每个join()阻塞到对应子线程结束。第三种ExecutorService的awaitTermination——shutdown()后等待指定时长。第四种CompletableFuture.allOf().join()——更现代的异步编程方式。实际场景中CountDownLatch最简单直接，join()最常用。"

### 段十六：🔴 HashMap源码 + 线程不安全 (27:43 - 31:44)

**面试官追问链**：
1. "你有去看过一些JDK的代码或者Java框架的代码吗？" → "看过HashMap"
2. "HashMap在什么情况下会出现不安全的这个问题？" → "多线程同时操作、没做锁隔离、ConcurrentHashMap"
3. "你能举个例子吗？多个线程操作它的时候它怎么就出问题了？" → "扩容时一个线程扩容一个线程插入产生冲突"
4. "除了扩容以外其他场景会出现吗？" → "两个线程哈希后位置一样时产生冲突"
5. "HashMap里面它是怎么去做哈希的？为什么会出现冲突？" → **卡住，记忆模糊**

**🔍 逐字分析**：

| 环节 | 表现 | 评价 |
|------|------|------|
| 看过HashMap源码 | 确认 | ✅ 有源码阅读意识 |
| 线程不安全原因 | "扩容冲突"+"哈希位置冲突" | ✅ 扩容场景是正确的，"哈希位置一样"表述模糊但方向对 |
| 扩容以外的场景 | 提到了哈希碰撞 | ⚠️ 没有提到**JDK7头插法死循环**（经典面试题）、没有提到**put时size++的非原子性导致数据丢失** |
| HashMap怎么哈希 | "按地址做哈希处理……点哈式……点一块……可以重写点哈式" | 🔴 **严重口误+概念混乱**。"点哈式"=".hashCode()"，"点一块"=".equals()"。候选人想说的是"如果不重写hashCode()，默认用Object的hashCode()——基于内存地址"，但"点哈式""点一块"这种表述在面试官耳中极度不专业 |

**面试官追问**："为什么会出现冲突？"

**候选人**：（约40秒思考）"可能在这方面我有点记忆模糊了。"

**🎯 问题诊断**：
1. **"点哈式"和"点一块"的口误**——面试官听到的是"这个人连hashCode和equals的方法名都说不清楚"。这是基础不扎实的最直接证据。
2. **哈希冲突的原因**——这是HashMap最基础的原理：不同的key可能计算出相同的hash值（因为hash是一个从无限域到有限域的映射），当两个key的hash值一样且不equals时发生冲突，用链表/红黑树解决。候选人连这个都回答不出来，说明所谓的"看过HashMap源码"是极其浅层的浏览。

**📊 严重程度**：🔴 P0（致命）——"点哈式""点一块"是全场最严重的口误，HashMap哈希冲突原理不会更是基础问题。

**正确回答（45秒版）**：
> "HashMap的哈希分两步。第一步调key的hashCode()获取原始哈希值，第二步用(h = key.hashCode()) ^ (h >>> 16)做高16位与低16位的扰动——目的是让高位也参与低位运算，减少哈希碰撞。冲突的原因很简单——哈希函数是从大空间到小空间的映射，不同key可能算出相同hash。HashMap用链地址法解决——冲突的entry挂到同一个桶的链表上，链表长度≥8且桶数≥64时转为红黑树提升查询效率。
>
> 线程不安全有三个典型场景。一是JDK7扩容时的头插法导致环形链表死循环（经典问题）。二是put操作中size++不是原子操作，多线程同时put可能丢数据。三是扩容期间一个线程在迁移数据另一个线程在读取，可能读到null。解决方案是用ConcurrentHashMap——分段锁+CAS保证线程安全。"

## 第四部分：重点突破待办项专题

### 模块A：Java并发编程补齐 🔴 最高优先级

> **目标**：能流利回答任何Java多线程基础问题

#### A.1 线程等待/同步机制速记卡

| 机制 | 用途 | 关键API | 一句话描述 |
|------|------|---------|-----------|
| **CountDownLatch** | 等待N个线程完成 | `new CountDownLatch(N)` → `countDown()` → `await()` | 计数器归零时唤醒等待线程，一次性使用 |
| **Thread.join()** | 等待单个线程结束 | `thread.join()` / `thread.join(timeout)` | 调用方阻塞直到目标线程执行完毕 |
| **CyclicBarrier** | N个线程互相等待 | `new CyclicBarrier(N, runnable)` → `await()` | 所有线程到达屏障后一起继续，可循环使用 |
| **ExecutorService.awaitTermination()** | 等待线程池所有任务完成 | `shutdown()` → `awaitTermination(timeout, unit)` | 先关闭线程池再等待 |
| **CompletableFuture.allOf()** | 等待多个异步任务完成 | `CompletableFuture.allOf(f1, f2).join()` | 现代异步编程首选 |
| **wait()/notify()** | 线程间通信（低级） | `obj.wait()` / `obj.notifyAll()` | 必须在synchronized块内使用 |
| **Semaphore** | 控制并发数量 | `acquire()` / `release()` | 许可证机制 |
| **Phaser** | 多阶段屏障 | `register()` / `arriveAndAwaitAdvance()` | JDK7+，更灵活的CyclicBarrier |

#### A.2 主线程等待所有子线程完成 — 话术（30秒版）

> "最常用三种方案。CountDownLatch——构造时设计数器为子线程数，主线程await()阻塞，每个子线程finally块里countDown()，计数器归零主线程继续。Thread.join()——主线程for循环对每个子线程调join()。线程池方案——executor.shutdown()后awaitTermination(60, TimeUnit.SECONDS)。选型上CountDownLatch最干净——不需要持有线程引用，适合线程由线程池管理无法直接join()的场景。"

### 模块B：HashMap深度补齐 🔴 最高优先级

#### B.1 HashMap哈希原理速记卡

```
put(key, value)流程：
1. key.hashCode() → 获取32位原始hash值 h
2. (h = key.hashCode()) ^ (h >>> 16) → 高16位与低16位异或扰动
3. (n - 1) & hash → 取模定位桶（n是桶数，2的幂）
4. 桶为空 → 直接放入
5. 桶非空 → equals()判断是否同key
   - 同key → 覆盖
   - 不同key → 链表追加 / 红黑树插入
```

#### B.2 哈希冲突的原因

> "哈希冲突是数学必然。哈希函数把任意对象映射到有限个桶中——从无限域到有限域的映射，抽屉原理保证必然冲突。HashMap通过扰动函数(h ^ h>>>16)降低冲突概率，通过链表+红黑树解决已发生的冲突。"

#### B.3 线程不安全三场景 — 话术

> "HashMap线程不安全有三个典型场景。一是JDK7扩容resize时的头插法导致环形链表——两个线程同时扩容，一个线程的next指针被另一个线程修改，形成环，get()时死循环CPU 100%。二是put操作中size++非原子——多线程同时put可能导致实际size小于元素数，数据丢失。三是扩容期间读写并发——一个线程在transfer迁移数据，另一个线程get可能读到null。解决方案：ConcurrentHashMap用分段锁+CAS、Collections.synchronizedMap用包装器锁、或者直接用Hashtable（全表锁性能差）。"

#### B.4 hashCode与equals口诀

> "hashCode相等不一定equals（哈希碰撞）。equals相等hashCode必须相等（契约）。重写equals必须重写hashCode，否则HashMap/HashSet行为异常。"
