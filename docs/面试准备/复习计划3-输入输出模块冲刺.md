## 二、五个短板 → 五个标准回答（今晚背这五个即可）

### 短板1：模型输出未知字段（如"项目风险点"），系统怎么处理？

> "Jackson 第 22 行配了 `FAIL_ON_UNKNOWN_PROPERTIES=false`——未知字段在反序列化时被静默忽略，不会导致解析失败。配合 L4 Bean Validation 只校验业务必须的字段（matchScore 0-100、matchedSkills 非 null），模型额外输出的字段不影响核心业务。如果后续需要监控未知字段出现频率，可以在 L3 和 L4 之间加一个 diff 检查——比较 JSON 的 key 集合和 MatchReport 的字段列表，差异写入日志预警。"

### 短板2：模块内部如何精准提取技术点？（当前 TextTrimmer 不够细）

> "当前 TextTrimmer 是按段落级别提取——识别'项目经历'标题后整段保留。段落内部的技术点识别依赖 LLM 语义理解，没有规则级提取。如果需要更进一步，可以在 extractSections 之后加一层正则——提取技术栈关键词（Java/Spring/Redis 等）、量化数据（QPS/百分比）、动词（主导/优化/设计）。但我的判断是：技术点识别让 LLM 做更准——正则对 '使用了一款高效的缓存中间件' 这种没有明确技术名词的表述无能为力。TextTrimmer 的职责是'压缩到 LLM 能读的范围'，不是'替代 LLM 做语义理解'。"

### 短板3：科研类超长简历怎么处理？

> "fallbackTrim（第 196-214 行）会过滤垃圾行后截断到 4000 字符，过滤后内容太少则退回原文。针对科研简历的特殊性，改进方向是在 NOISE_LINE_PATTERN 的基础上加一个学术关键词白名单——保留包含 'SCI''一作''专利''影响因子''引用次数' 等关键词的行。这样在相同字符预算下保留更多有效信息。"

### 短板4：多语言简历的 token 管理

> "TokenEstimator 中文 1:1、英文 4:1 的比值是语言自适应的。英文简历按这个公式算出的 token 数自然会偏高，会被更早触发 10000 的拦截阈值。如果需要更精准的控制，可以在 TokenEstimator.estimate() 里先判断文本语言比例——ASCII 占比 > 70% 则切换为 1 词 ≈ 1.3 token 的英文公式。当前 MVP 阶段用统一的保守公式已经够用——宁可多拦，也不漏拦。"

### 短板5：线上排查经验

> "日志已写入 `logs/app.log`。JSON 解析失败会抛 IllegalStateException 并记录异常信息，grep 'ERROR' 就能找到。字段校验失败抛 AiOutputValidationException 时附带 violations 详情——具体哪个字段不符合什么约束。LangChain4j 的 `log-requests: true` 和 `log-responses: true`（application.yml 第 11-12 行）也开启了框架层的 Prompt/响应日志。三层日志（框架层 + AOP层 + Facade层）都挂在同一个 traceId 下，grep 即可还原完整链路。"

## 四、自我介绍（45 秒版）

> "我设计了一个面向求职场景的 AI-Native 后端服务，核心用 LangChain4j 的 @AiService 驱动三个 LLM Agent：JD 解析、人岗匹配评估、简历重写。
>
> 技术重点在两个方向。**可靠性**：输入侧 TextTrimmer + TokenEstimator 做预处理和超限拦截，输出侧四层防御 pipeline 应对 JSON 格式漂移。**幻觉治理**：Actor-Critic 双智能体审查架构——Writer 生成草稿，Critic 以原始经历为事实边界逐条核查，Coordinator 用 severity 阈值做三层决策。经过 8 组测试用例 × 5 变体的 A/B 验证，240 次调用确认 2 轮迭代达到 87.5% 通过率。"

---

## 五、项目难点（60 秒版）

> "核心难点是 LLM 在简历重写时主动捏造数据——把 QPS 2000 写成 50000、把 RocketMQ 换成 Kafka。只靠 Prompt 不够——同一个模型在创作模式下会本能脑补。
>
> 我拆成两个独立 Agent：Writer 在事实边界内扩写，Critic 以原始经历为唯一边界逐条核查。但 Critic 也不稳定——早期二元 approved 判断在边界场景有 40% 随机翻转率。所以升级为结构化 Violation——每条违规包含 violationType（四分类）和 severity（1-5）。Coordinator 计算 maxSeverity：≤2 打 WARN 直接通过，≥3 才触发重写。
>
> 整个架构经 8 组测试用例 × 5 种循环上限的 A/B 验证——1 轮 50% 通过率，2 轮 87.5%，确认了最优循环次数。代码已落地在 `RewriteCoordinatorService.evaluate()` 第 120-132 行，测试日志可直接还原决策链。"
