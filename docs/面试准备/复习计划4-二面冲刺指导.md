## 模块1：LLM生死线 🔴（3小时）

> **目标**：Token/上下文窗口/模型参数 三个问题全部15秒内脱口而出
> **一面痛处**：Token概念沉默70秒、上下文窗口说成4096、Lost in the Middle完全空白
> **参考材料**：碎片时间速记卡 卡片1+2+3+4（修正版）、《上下文窗口优化/03-面试深度解析.md》

### 阶段A：背诵（45min）

集中背三件事：

**1. Token & BPE（卡片1）**
- Token = LLM处理文本的最小语义单元，不是"字"也不是"词"
- BPE (Byte Pair Encoding) = 从字符开始，循环合并高频字符对，直到预设词汇量
- 中文：1字≈0.5-0.7 token（实际），工程保守用1字≈1 token（高估30%）
- 不同模型不同tokenizer（GPT用tiktoken，DeepSeek自研）

**2. DeepSeek V4核心参数**
- DeepSeek V4-Flash：1,000,000 Token（1M）上下文窗口，轻量级旗舰
- 输出上限：8K Token
- 我的项目里设的拦截阈值：10,000 Token —— 不是模型限制，是业务合理性

**3. Lost in the Middle**
- 模型对长文本**中间位置**的信息提取能力显著下降
- 有效注意力：前25%和后25%最好，中间50%易被遗忘
- 这是为什么即使1M上下文，也要控制在最佳注意力窗口内的原因

### 阶段A2：深度追问储备（面试官视角）（30min）

> 以下5个追问是面试官听完基础回答后最可能深挖的方向。每个追问都附带面试官真实意图和标准回答要点。

**追问1："1万Token有什么科学依据？为什么不是8000或12000？设2-3倍余量有什么讲究？"**

面试官意图：测试阈值是否拍脑袋决定的，有没有数据支撑。

标准回答（⬆️ 已升级为硬数据版）：
> "我专门跑过压力测试。Golden Test Set 8组用例——覆盖正常简历/信息稀疏/角色错位各种场景——每组JD+简历经TextTrimmer裁剪后，用TokenEstimator估算。8组token分布从486到604，最大的一组（C4-2极端角色错位场景）只有604 token。1万阈值是实测最大值的**16.6倍**——安全余量巨大。
>
> 为什么不是更大？因为正常JD约500-1500字、简历约2000-4000字，两者合计加上Prompt固定开销撑死也不到1万。2万以上的文本量已远超正常JD+简历范畴，设更大只增加成本边际没有业务收益。
>
> 测试数据全在 `docs/面试准备/测试分析/二面冲刺验证报告-2026-06-17.md`，8组用例的token明细和P99都有。"

**追问2："1M上下文不需要拦截，1万token丢进去模型不会崩。你是不是为了项目故意制造困难、创造需求？"**

面试官意图：测试工程判断力——你是否在过度设计。

标准回答：
> "拦截阈值解决的不是'模型能不能处理'，而是'这个输入是否合理'。如果JD+简历超过1万token——约1万中文字——意味着用户在简历里贴了长篇小说、或在JD里塞了整个公司官网。这种异常输入即使模型能处理，产出的改写质量也必然很差——有效信息密度被稀释了。
>
> 拦截本质是**输入校验**，和Web表单校验'手机号必须是11位'一样——不是系统不能处理12位数字，而是12位就不是手机号。超过1万token的输入不是正常的简历优化场景，应该在边界拦掉。"

**追问3："关键词完全匹配不到怎么办？比如简历用了'我的工作经验'或英文'Work Experience'？怎么兜底？"**

面试官意图：测试异常处理设计的完备性。

标准回答：
> "三层兜底。第一层：extractSections支持14种标题关键词变体，覆盖中英文混合、序号前缀（1. / （一）/ ①）、CRLF和CR换行。第二层：如果全部匹配不到，走fallbackTrim——过滤垃圾行（福利待遇、五险一金、联系方式、公司介绍等纯噪声），保留所有实质内容。第三层：过滤后如果内容 < 50字，退回原文——宁多勿少，至少不丢信息。
>
> 所以最坏情况：用户简历格式极不规范，TextTrimmer退化为智能'去噪声+截断'工具——效果打折但绝不失效。"

**追问4："你怎么保证改写效果是正面的？有什么验证机制？"**

面试官意图：测试是否有量化验证思维，而不是凭感觉说"效果好"。

标准回答：
> "有独立验证机制——Critic Agent。改写好坏的判定不是主观的，Critic拿着JD原文逐项比对改写后的简历，检测是否出现假数据/假技术栈/过度夸大/过度润色，输出结构化违规报告。
>
> 实验验证：3类dirty draft（故意掺假）、9次调用、Critic达到100%召回率——所有假数据和假技术栈全部检出。循环次数A/B测试：8用例×5变体=240次API调用——2轮循环达到87.5%通过率。正向改写效果是有数据支撑的，不只靠感觉。"

**追问5："Token估算为什么不用第三方库（如tiktoken），而是自己写？你的保守策略到底多保守？"**

面试官意图：测试技术选型能力和"保守估算"的具体含义。

标准回答：
> "不是不想用tiktoken之类的库，而是DeepSeek自研tokenizer没有官方Java SDK——用别人的tokenizer算出来和DeepSeek实际token数有偏差，反而更不准。所以干脆自己写：中文1字=1 token（高估约30%），英文/其他字符4字符=1 token，加上Prompt模板固定开销400 token。
>
> 保守策略的核心原则是**宁可误拦不可漏拦**——高估30%意味着有些实际不到10000的请求也会被拦截。但误拦的代价是用户收到400错误可重试；漏拦的代价是API调用被截断导致数据损坏——前者可逆，后者不可逆。设计选择偏向安全侧。"

### 阶段A：背诵（30min）

背熟概念树（卡片5）：

```
Agent（智能体）— 有自主决策权，SystemMessage定义边界，管理对话上下文
Skill（技能）— 被动执行的功能模块，无状态，被Agent调用
Tool / Function Calling — LLM自主决定调用时机和参数
Role（角色）— 通过SystemMessage定义
Orchestration（编排）— 调用逻辑（链式→DAG→动态规划）
Memory（记忆）— 跨轮信息保持（我的项目：不用，靠feedback参数传递）
```

背熟Agent vs Skills对比表（卡片6）：

| 维度 | Agent | Skill |
|------|-------|-------|
| 决策权 | ✅ 有 | ❌ 无 |
| 身份 | SystemMessage | 功能描述 |
| 状态 | 管理上下文 | 无状态 |
| 通信 | 可直接通信 | 需编排者串联 |

**关键论断**："两个Skills不能直接通信，需要一个编排者串联——这个编排者本质上就是一个Agent。选Agent还是Skill看：是否需要独立的角色身份和判定边界？"

#### 追问1：RecursiveCharacterTextSplitter vs TokenTextSplitter 区别

| 维度 | TokenTextSplitter（你的项目） | RecursiveCharacterTextSplitter |
|------|---------------------------|------------------------------|
| 切分依据 | 按 token 数量，800 个到了就切 | 按语义边界：先段落→再行→再句→最后才字符硬切 |
| 优点 | 行为确定、chunk 大小均匀、对中文友好 | 每个 chunk 更可能是完整语义单元，检索相关性高 |
| 缺点 | 可能把一句话切在两个 chunk 里 | chunk 大小不均匀，token 消耗可能更多 |
| 典型场景 | MVP 快速上线、行为可预期要求高 | 生产优化阶段、检索精度要求高 |

**面试话术（15秒对比）**：

#### 追问3：IVF_FLAT 索引类型详解

**三层理解**：
1. **IVF**（Inverted File）——**聚类加速**：用 K-means 把 3584 维向量聚成 1024 个簇（nlist=1024）。检索时先和 1024 个聚类中心算距离，只搜最近的几个簇，避免全量扫描。1万条向量 → 只搜 ~200 条
2. **FLAT**——**精确搜索**：在选中的簇内做精确暴力计算，算出 query 和每条向量的余弦相似度，保证簇内结果最优
3. **为什么不用 HNSW**：场景下文档量不大（<百万级），精度比极致速度重要——用户等 0.1 秒和 0.5 秒感知不大，但"检索结果不准确"是致命的

**面试话术（15秒）**：
> "IVF_FLAT 分两步——IVF 把向量聚成 1024 个簇做快速倒排，FLAT 在候选簇内做精确余弦搜索。选它是因为场景下文档量不大但精度要求高——用户对检索准确性比检索速度敏感得多。HNSW 更快但有近似误差，在这个场景下不值得。"

#### 追问4：Collection 是什么 + 向量维度的作用

**Collection**：Milvus 里相当于"表"的概念，存储一个知识库的所有文档 chunk 的 3584 维向量 + metadata（docId/baseId/fileName/chunkIndex/isEnabled）。

**向量维度（3584）是 Embedding 转换的结果，不是转换方式**：
- Chunk→向量**怎么转的**：代码把 chunk 文本发给 Ollama 的 `/api/embed` 端点，qwen2.5:7b 模型把文本映射到向量空间
- **3584 维**是 qwen2.5:7b 输出向量的维度，由模型本身决定，不可修改
- 类比：快递包裹（chunk）→ 快递单号（3584 维向量）。维度是单号长度，转换方式是生成单号的算法

**维度校验逻辑**（`EmbeddingDimensionValidator`）：
1. 启动时检查 collection 是否存在
2. 存在 → 读取 collection 的 embedding 字段维度，和配置值 3584 比较
3. 不匹配 → 说明换过 Embedding 模型 → 自动 drop + 重建 + 创建 IVF_FLAT 索引
4. 读取失败 → 保护已有数据，不操作

**面试话术（20秒）**：
> "Collection 是 Milvus 里的表，存文档 chunk 的向量和 metadata。启动时自动校验维度是否和 qwen2.5:7b 输出一致——不一致说明换过模型，自动重建。向量维度是 Embedding 转换的结果，转换方式是把 chunk 文本发给 Ollama Embedding API，qwen2.5:7b 输出 3584 维向量。"

#### 追问5：Top-K 数值的含义和作用

- Top-8：检索时返回最相似的 8 个文档片段
- K 太小（如 Top-3）：可能遗漏相关信息，召回率低
- K 太大（如 Top-20）：无关噪声混入，降低回答质量且浪费 token
- Top-8 + 主阈值 0.45 过滤：先取相似度最高的 8 个，再用 0.45 卡掉低质量的

## 模块5：项目叙事精修 🟠（3小时）

> **目标**：修正一面4个P1级表述问题
> **参考材料**：复盘报告 模块G（自我介绍）、段二（Critic逻辑）、段四（新开会话）、段十一（Spring AI vs LangChain4j）

### 5.1 自我介绍重写（30min背诵）

**新版45秒脱稿**：

> "面试官你好，我叫蒋毅武，哈尔滨工程大学22届毕业生。
>
> 我在做一个Agent简历优化系统，起因是发现通用LLM改简历时有一个典型问题——它会脑补不存在的技术和数据，比如把'参与支付模块开发'扩写成'主导设计支付系统，QPS提升30%'。这些幻觉对求职者是致命的。
>
> 我的解决方案是用Actor-Critic双智能体架构——Writer负责按JD优化表达，Critic做严格事实核查。Critic不是简单判过/不过，而是输出结构化违规报告——每条违规有类型（假数据/假技术/夸大/过度润色）和严重程度（1-5分）。Coordinator基于severity阈值做智能决策——轻度措辞不当容忍放行，严重捏造触发重写。实验验证2轮循环达到87.5%通过率且边际收益递减。
>
> 另外在输入输出两侧做了完整的防护工程——输入侧上下文裁剪+Token预估防溢出，输出侧四层容错pipeline防JSON格式漂移，AOP双切面+MDC做全链路日志。整个项目用Spring Boot + LangChain4j + DeepSeek V4实现。"

### 5.2 Critic表述精修（30min）

**一面错误**："权重从重往轻"+"取最大评分"=逻辑矛盾

**修正表述（15秒）**：

> "Critic输出四个维度的违规判定——FAKE_DATA/FAKE_TECH/EXAGGERATION/MINOR_EMBELLISHMENT，每个违规有自己的严重程度（severity 1-5）。Coordinator取所有违规中的maxSeverity做决策——≤2说明只有轻度措辞问题，直接放行；≥3说明存在事实性违规，触发重写。四类违规中FAKE_DATA和FAKE_TECH是致命的，severity初始值就在4-5；EXAGGERATION是3；MINOR_EMBELLISHMENT是1-2。所以maxSeverity策略本质上就是'有致命违规就拦，没致命就放'。"

### 5.3 "新开会话"纠正（15min）

**一面错误**："每次都是新开一个agent会话"

**修正表述**：

> "每次调用Agent接口是独立、无状态的API请求——不共享任何会话上下文。第二轮把上一轮Critic的反馈作为参数传入，但这不是'同一个会话'的延续——每个请求都是全新的。我用'无状态调用+feedback参数传递'的模式，而不是依赖框架的会话管理。"

### 5.4 Spring AI vs LangChain4j 实践体感版（30min）

**一面问题**：教科书式背诵，没有实践体感

**修正表述（30秒）**：

> "我在两个项目里分别用过它们。Spring AI的优势是与Spring Boot生态无缝集成——它的ChatClient可以直接注入Spring管理的Bean，在已有Spring应用中加对话功能非常快。LangChain4j的优势是更丰富的Agent编排原语——@AiService/@SystemMessage/@UserMessage这套注解体系让定义Agent接口像写Java接口一样自然。它的@Description注解自动生成JSON Schema，对结构化输出（比如我的CriticReport）支持更成熟。
>
> 在这个简历优化项目中，我需要两个Agent做复杂编排+结构化输出，所以选了LangChain4j。如果我只需要在现有Spring应用中加一个简单的对话功能，我会选Spring AI——这就是选择的标准。"

### 6.1 四层Pipeline（触发词：JSON输出/结构化输出/Critic格式）

**30秒话术**：

> "LLM输出的JSON有三层不稳定：Markdown包裹、非标准语法（注释/尾逗号/单引号）、字段漂移（match_score vs MatchedScore）。我设计了四层防御pipeline：第一层extractJsonObject用indexOf找最外层花括号剥离Markdown；第二层FieldNameNormalizer用正则归一化25+种字段名变体；第三层Jackson开四个宽松开关；第四层Bean Validation做字段值合法性拦截。四层任一层失败都有明确错误码，不是黑盒崩。"

### 6.2 AOP双切面（触发词：日志/可观测性/怎么追踪请求）

**40秒话术**：

> "日志系统用了AOP双切面+MDC全链路追踪。WebLogAspect用@within(RestController)拦截所有Controller——记录HTTP层。AiCallLogAspect用execution精准切入evaluate()方法——记录AI调用层。
>
> 为什么拆两个？单一职责——Web层关心HTTP维度，AI层关心业务维度。拆开后grep '[WEB]'和grep '[AI-CALL]'分离清晰。共享同一个traceId，grep还原全链路即可。
>
> 入参策略也不同——Web层DTO序列化为JSON+200字符截断，AI层入参是完整JD+简历，只记长度不记全文——防日志爆炸+防敏感信息泄露。"

### 6.3 成本三维框架（触发词：成本/怎么省钱/API费用）

**30秒话术**：

> "成本控制我用三维框架——减量、提效、扩容，按边际收益递减曲线排优先级。减量——TextTrimmer+TokenEstimator砍输入。提效——小模型做Critic+max_tokens硬上限。扩容——异步化202+taskId，MVP阶段先不做。顺序很重要——减量一次开发终身省钱，提效有风险需验证，扩容成本最高。"

### 6.4 violationType四分类 + 决策逻辑（触发词：Critic怎么判断/四个维度）

**20秒话术**：

> "FAKE_DATA和FAKE_TECH是致命的（severity 4-5），EXAGGERATION是中等（3），MINOR_EMBELLISHMENT是轻度（1-2）。Coordinator取maxSeverity——≤2通过，≥3触发重写。3轮后不达标强制输出+告知用户。这个阈值是经过240次API调用实验验证的。"
