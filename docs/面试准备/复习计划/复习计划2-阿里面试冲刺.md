## 二、今晚必补硬伤 #1：temperature/max_tokens 区分

### 面试官会怎么纠正你
> "temperature 其实主要影响输出随机性，对 token 量的直接影响不大。"

### 标准回应（30 秒）

> "我刚才表述不精确——temperature 控制的是输出的随机性和创造性，不是 token 量。Writer 用高 temperature 是为了让表达更生动，Critic 用低 temperature 是为了审查结果更稳定。真正控制 token 量的参数是 `max_tokens`——给 LLM 输出设硬上限。我在配置里给 Writer 设了约 800（输出多条 bullet），Critic 设了约 600（feedback 应该精简），防止模型在反馈中过度冗长。"

### 追问："max_tokens 配在哪？"

> "在 `application.yml` 的 `langchain4j.open-ai.chat-model` 下配置 `max-tokens: 800`。LangChain4j 会把它填入 API 请求的 `max_tokens` 参数。"

### 记忆口诀
> **"temperature 管随机，max_tokens 管长度。Writer 高随机生动，Critic 低随机稳定。"**

## 三、今晚必补硬伤 #2：MDC 异步 traceId 传递

### 面试官会怎么问
> "在异步线程调用 AI 接口时，MDC 里的 traceId 可能会丢失，你怎么解决？"

### 标准回答（20 秒）

> "异步场景下 MDC 不会自动传递，因为子线程不继承父线程的 MDC 上下文。解决方案有两个：
> 1. **简单方案**——自定义 `ThreadFactory`，在 `newThread()` 里从父线程 MDC 获取 traceId，子线程 `run()` 前 `MDC.put("traceId", traceId)`，执行完 `MDC.remove("traceId")`
> 2. **框架方案**——Spring 的 `TaskDecorator` 可以在 `ThreadPoolTaskExecutor` 中自动复制 MDC 上下文，代码更简洁
> 
> 当前 MVP 阶段以同步调用为主，这个场景暂未遇到。但如果引入异步化（如 202 + taskId 轮询的 rewrite 接口），这是我第一个会加的东西。"

### 记忆口诀
> **"ThreadFactory 里拿父线程 MDC，子线程 run 前 put，run 后 remove。Spring 用 TaskDecorator 更简单。"**

```
  防止模型输出冗长浪费 token。"

  "扩容是前两维优化到极致后的架构兜底。具体方向是异步化——先返回

⑤ 收尾（5秒）
  "顺序很重要——先做减量一次开发终身省钱，再做提效有风险需验证，
  最后扩容成本最高。这个顺序不是拍脑袋，是按边际收益递减曲线排的。"
```

**过渡话术**：

### 模块 2：上下文窗口（在成本回答中过渡）

**触发时机**：当你在讲 "减量" 的 TextTrimmer 时

**过渡话术**：
> "减量层里，TextTrimmer 和 TokenEstimator 做了分工——Trimmer 用业务规则提取核心段落（按'项目经历''工作职责'等 14 种关键词变体识别），Estimator 用数学规则算 token 上限（中文 1 字≈1 token，加上固定开销）。超过 10000 token 直接抛 ContextWindowExceededException 返回 400。这个分工的好处是——Trimmer 只管内容相关性，Estimator 只管数量上限，职责清晰，排查问题时能快速定位是裁剪逻辑错了还是预估公式偏了。"

### 9.2 两个切面对比表（面试核心，必须脱稿）

| 维度 | WebLogAspect | AiCallLogAspect |
|------|-------------|----------------|
| **切点表达式** | 第61行 `@within(RestController)` | 第52行 `execution(* ...MatchEvaluationFacadeService.evaluate(..))` |
| **为什么用这个切点** | 类级别注解，一次拦截所有 Controller 方法（`@within` vs `@annotation` 区别写在 Javadoc 第57-59行） | 不用 `@within` 切 service 包——因为 `@AiService` 接口是 JDK 动态代理（Javadoc 第47-50行），`execution` 匹配方法级别更可靠 |
| **入参处理** | 序列化为 JSON（第116行），截断到 200 字符（第117行） | 只记字符数（第73行 `s.length()`），不记全文 |
| **入参策略为什么不同** | Controller 入参是 DTO 对象，JSON 摘要即可看懂请求内容 | AI 调用入参是完整 JD+简历文本，记全文日志爆炸（Javadoc 第58-59行："防日志爆炸 + 防敏感信息泄露"） |
| **出参处理** | 只记录 `status=OK`（第89行），不记录响应体 | 记录业务指标：`matchScore`、`matchedSkills` 数量、`missingSkills` 数量（第82-85行） |
| **异常处理** | 记录异常类名+消息（第93-95行），**重新抛出**（第97行） | 同样记录异常信息，消息截断 150 字符（第97行），**也重新抛出**（第102行） |
| **日志前缀** | `[WEB]`（第89行） | `[AI-CALL]`（第84行） |

### 9.3 代码追问话术卡片（三张）

#### 卡片 D：currentRequest() 为什么包 try-catch（15 秒版）

> "第 79 行 `currentRequest()` 通过 `RequestContextHolder.getRequestAttributes()` 拿 HttpServletRequest。第 103-108 行包了 try-catch——因为在单元测试或非 Web 上下文中，`RequestContextHolder` 可能为 null，不包 try 会让整个切面炸掉。兜底返回 null，调用方用 `request != null` 判断，取不到就退化为方法签名（第 81 行 `joinPoint.getSignature().toShortString()`）。"

#### 卡片 E：AiCallLogAspect 为什么只切 evaluate() 一个方法（15 秒版）

> "第 52 行的切点表达式精准切入 `MatchEvaluationFacadeService.evaluate()`，不切整个 service 包。两个原因：第一，TextTrimmer、TokenEstimator 这些工具方法执行不到 1ms，全切日志全是噪音，真正有用的只有 AI 调用的入口。第二，`@AiService` 接口是 JDK 动态代理，`@within` 匹配不到接口上的注解，`execution` 匹配方法签名才可靠。（Javadoc 第 26-29 行和第 47-50 行有写）。"

#### 卡片 F：两个切面的入参策略为什么不同（15 秒版）

> "Web 层入参是 DTO（几十到几百字节），序列化为 JSON + 200 字符截断足够了。AI 层入参是完整 JD+简历（2000-5000 字），记全文一条日志几百行。我只记 `jdLen` 和 `resumeLen` 两个数字——够排查问题吗？够了。JD 长度异常可能是 TextTrimmer 裁剪失败，简历长度异常可能是 TokenEstimator 边界计算有误。数字就够了，不需要全文。这也是 Javadoc 里明确写了的——"防日志爆炸 + 防敏感信息泄露"。"

### 9.4 设计决策话术（一个问题展示架构思维）

> **面试官问**："为什么拆成两个切面，不写一个统一处理？"
>
> **答**："单一职责原则在 AOP 层的应用。Web 层关心 HTTP 维度（状态码、响应时间），AI 层关心业务维度（评分、技能匹配数、token 消耗趋势）。写在一个切面里也能跑，但切点、字段提取逻辑、日志格式全混在一起，排查时 `grep '[WEB]'` 和 `grep '[AI-CALL]'` 没法分离。拆开后每条日志只包含自己层的关注点——Web 层的日志里不会有 score，AI 层的日志里不会有 HTTP 状态码。两个切面都挂同一个 traceId，grep 还原全链路即可。"
