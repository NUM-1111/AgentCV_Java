## 核心问题

> 很多功能缺少数据优化or数据验证，没有数据就难以证明我是否深入参与了项目。
> —— 手录分析·模块一

三场面试共同指向一个问题：**AgentCV系统的工程能力停留在"能跑"但没有数据验证层面**。面试官追问"怎么保证写得好""怎么判断Critic打得准"时，候选人只能承认"靠人工评审"——这是连续三次面试未修复的短板。

## I-1. 效果验证量化体系 🔴 最高优先级

**来源**：阿里二面段六（P1）+ 字节一面段九（再次承认缺乏量化指标）+ 手录分析 M1-1, M1-2

**问题**：
- Writer Agent的输出质量完全没有自动化度量
- 面试官追问"打分打得准不准"时无法回答
- 手录指出："writeAgent缺乏评分数据，也没有对应的验证实验"

**改进方案**：

| 维度 | 实现方式 | 产出 |
|------|---------|------|
| **维度分** | JD核心要求拆成结构化评分维度 → Critic按维度打分 | 每个改写输出附带5维度雷达图 |
| **相似度分** | JD采分点向量化 → 与改写后简历计算余弦相似度 | 0-1浮点数 |
| **覆盖率分** | ATS关键词匹配测试 → 统计JD核心关键词在改写后简历中的覆盖率 | 百分比 |

**实施步骤**：
1. 手动标注10-20组JD的采分点做ground truth
2. 实现采分点向量化+余弦相似度计算
3. 实现ATS关键词匹配（复用TextTrimmer的正则能力）
4. 改造Critic Agent输出结构，增加`QuantitativeScore`字段
5. 在golden-test-set上跑全量对比

**面试中如何讲**（30秒）：
> "我现在正在推进效果量化体系。三个维度——维度评分、向量相似度、ATS关键词覆盖率。之前Critic只做定性审查（通过/不通过），现在增加定量评分让质量可追踪。数据基础是10-20组JD的采分点标注。"

## I-8. Tool/Function Calling 集成 🔴 最高优先级（开发向）

**来源**：阿里一面段十三（Agent vs Skills P0 致命空白）+ LangChain4j 官方示例 `_10_ServiceWithToolsExample.java`

**问题**：
- 面试被问"Agent vs Skills 区别"时完全空白（沉默45秒）
- AgentCV 的 Agent 是纯 LLM 调用，没有任何 Tool 能力——这是"AI Wrapper"和"Agent 平台"的本质区别
- 你用的 LangChain4j 原生支持 `@Tool` 注解，但项目中从未使用

**改进方案**：

给 Critic Agent 注册一个 `FactCheckTool`，让模型**自己决定**何时调用事实核查：

```java
// 1. 新增工具类
public class FactCheckTool {
    @Tool("核查简历改写中的某项声明是否与原文一致")
    String checkClaim(String originalSegment, String rewrittenClaim) {
        // 用 TextTrimmer 段落匹配 + 关键词对比
        return "一致" / "不一致：原为X，改为Y";
    }
}

// 2. 注册到 Critic Agent
FactCriticAgent critic = AiServices.builder(FactCriticAgent.class)
    .chatModel(model)
    .tools(new FactCheckTool())  // ← Critic 现在有"核查武器"
    .build();
```

**实施步骤**：
1. 创建 `FactCheckTool.java`，用 `@Tool` + `@P` 注解定义工具方法
2. 在 `FactCriticAgent` 的 `AiServices` 构建中注册 `.tools(new FactCheckTool())`
3. 写一个测试验证 Critic 在检测到可疑声明时会自动调用 Tool
4. 可选：再加一个 `SearchWebTool`（查行业术语）、`CalculateMatchTool`（计算匹配度）

**面试中如何讲**（30秒）：
> "面试官问的 Skills，在 LangChain4j 里叫 @Tool。我给 Critic Agent 注册了一个 FactCheckTool——模型检测到可疑声明时，自动调用它做原文对比，而不是等 Coordintor 把整段文本喂给 Critic 做全量审查。这就是 Agent vs Tool 的区别：Agent 有决策权（Judge），Tool 是被调用的能力模块（Checker）。如果你只需要一个检查模块，用 Tool。如果你需要一个独立的角色身份和判定标准——比如 Critic 有 severity 分级决策权——用 Agent。"

**关联 LangChain4j 源码**：`_10_ServiceWithToolsExample.java` — `@Tool` 注解 + `AiServices.tools()` 注册模式

## I-9. PDF/DOCX 简历解析 🔴 高优先级（开发向）

**来源**：阿里一面段九（正则预处理举不出例子，暗示项目深度不够）+ OpenResume（用 PDF.js 做简历解析）+ 真实场景需求（用户上传的是文件而非纯文本）

**问题**：
- 当前 API 接收的是纯文本 `String`，假设输入已被预处理——真实场景下用户上传的是 PDF/DOCX
- 纯文本入口让项目看起来像一个"demo"而非"产品"
- 面试官追问"正则匹配出什么内容"时举不出例子，部分原因是你从未处理过真实格式的简历

**改进方案**：
- 引入 Apache Tika（一个依赖，支持 PDF/DOCX/TXT 等 15+ 格式）
- Controller 新增 `MultipartFile` 入口
- 解析链路：上传文件 → Tika 提取纯文本 → TextTrimmer 裁剪 → 后续管道不变

```java
// 新增工具类
public class DocumentParser {
    public static String parse(MultipartFile file) {
        return new Tika().parseToString(file.getInputStream());
    }
}

// Controller 新端点
@PostMapping("/api/v1/resume/upload")
public MatchReport evaluateFromFile(
        @RequestParam MultipartFile file,
        @RequestParam String jdText) {
    String resumeText = DocumentParser.parse(file);
    return facadeService.evaluate(jdText, resumeText);
}
```

**面试中如何讲**（30秒）：
> "用户上传简历是 PDF，我用 Apache Tika 做格式解析。Tika 能处理 PDF 的无结构文本流、DOCX 的 OOXML、甚至图片 OCR，统一输出纯文本。解析后走正常管道——TextTrimmer 裁剪核心段落、TokenEstimator 做窗口防护。为什么不用 PDFBox 直接读？因为 Tika 是门面模式——换文件格式不需要换解析器。"

**借鉴 OpenResume**：OpenResume 用 PDF.js 做浏览器端解析 + 结构化字段映射。你的后端场景应选 Tika（Java 原生，无浏览器依赖）。

## I-10. TokenEstimator 策略化改造 🔴 高优先级（开发向）

**来源**：阿里一面段五（DeepSeek 上下文窗口完全不知，1万阈值理由薄弱）+ 段六（Token 估算回答缺工程深度）+ LangChain4j `OpenAiTokenCountEstimator`

**问题**：
- 当前 TokenEstimator 是 `final class` + 硬编码公式，无法替换为真实 tokenizer
- 面试中说的"中文1:1估算高估30%"只是口头说法，代码里没有体现"可替换性"
- 如果模型换成 GPT（tiktoken）或 Claude（不同 tokenizer），估算公式完全不适用

**改进方案**：
将 TokenEstimator 从硬编码工具类改为**策略模式**——保留当前手工估算为默认，但支持切换到真实 tokenizer：

```java
// 1. 抽象策略接口
public interface TokenEstimationStrategy {
    int estimate(String text);
}

// 2. 当前手工估算作为默认实现
public class HeuristicTokenEstimator implements TokenEstimationStrategy { ... }

// 3. 配置化选择
// application.yml:
// agentcv:
//   token-estimator: heuristic  # 或 tiktoken / deepseek-api
```

**实施步骤**：
1. 抽取 `TokenEstimationStrategy` 接口
2. 将当前 `TokenEstimator.estimate()` 逻辑移入 `HeuristicTokenEstimator`
3. 在 `application.yml` 加配置项，Spring Boot 按配置注入对应策略
4. 保留 `MAX_INPUT_TOKENS` 和 `PROMPT_TEMPLATE_OVERHEAD` 为全局常量（不随策略变）
5. 更新 `TokenBudgetCalibrationTest` 约束A，验证新策略下约束仍成立

**面试中如何讲**（30秒）：
> "TokenEstimator 我改成了策略模式。默认用启发式算法——中文1:1高估约30%，宁可误拦不可漏拦。但可以通过配置切换到 tiktoken 库或模型 API 返回的真实 token 数。为什么这么做？因为不同模型的 tokenizer 不同——GPT 用 BPE，DeepSeek 用自研 tokenizer——手工估算只能做保守上界，真实上线应该用模型原生 tokenizer。改一行配置就切换。"

**关联 LangChain4j**：`OpenAiTokenCountEstimator` 展示了如何用模型原生 tokenizer 做精确估算

## I-11. SSE 流式输出 🟠 高优先级（开发向）

**来源**：LangChain4j 官方示例 `_04_Streaming.java`（`StreamingChatResponseHandler`）+ Spring Boot 原生 `SseEmitter`

**问题**：
- 当前是全同步调用——用户提交简历后等待 30-60 秒，一次性返回完整结果
- 没有被面试官问过，但"流式输出"是 AI 应用的基本体验——所有竞品都是逐字流式输出
- 技术上成本极低（Spring Boot 原生支持），但面试价值高

**改进方案**：
- Controller 返回值从 `MatchReport` 改为 `SseEmitter`
- 每一轮 Actor-Critic 的结果通过 `emitter.send()` 推给前端
- 前端逐轮显示"改写中…→审查中…→修正中…→完成"

```java
@PostMapping("/api/v1/match/stream")
public SseEmitter evaluateStream(@RequestBody MatchRequest request) {
    SseEmitter emitter = new SseEmitter(120_000L); // 2分钟超时
    // Writer 输出 → emitter.send("正在改写...")
    // Critic 输出 → emitter.send("审查中，发现X条建议...")
    // 最终结果 → emitter.send(SseEmitter.event().name("result").data(report))
    return emitter;
}
```

**面试中如何讲**（20秒）：
> "我用 SSE 做了流式输出。用户提交简历后不是等 30 秒一次性返回，而是看到改写进度——'正在分析JD…→正在优化第1段…→正在审查…→完成'。技术选型上，SSE 比 WebSocket 轻量——这里是单向推送不需要双向通信，SSE 直接用 HTTP 协议无额外连接开销。超时设了 2 分钟，超时自动释放资源。"

## I-12. RAG 集成：AgentCV + IntelliVault 打通 🟠 高优先级（开发向）

**来源**：阿里一面段十五（RAG 项目空洞——记不住 Embedding 模型名/向量维度/存了什么内容）+ LangChain4j `ChatWithDocuments` 示例

**问题**：
- 两个项目（AgentCV + IntelliVault）各说各的，面试中无法展示跨项目整合能力
- Writer 改写简历时遇到不认识的行业术语（如 JD 中的"Seata""Service Mesh"），只能靠 LLM 内部知识猜测——可能猜错
- 面试官看到你有 RAG 项目但简历优化系统不用 RAG——这就是"项目经验不够深"

**改进方案**：
在 Writer 改写流程中嵌入 RAG 检索——遇到不认识的术语时，自动检索 IntelliVault 获取术语解释，辅助 Writer 更准确地改写：

```
原始简历: "参与微服务开发"
JD要求:   "有 Seata 分布式事务经验"

当前行为: Writer 不知道 Seata 是什么 → 可能跳过或脑补
改进行为: Writer 调用 RAG Tool → 检索 Seata 定义 → "Seata是阿里开源的分布式事务解决方案"
         → Writer 理解后改写为 "使用 Spring Cloud Alibaba 实现微服务治理，了解分布式事务概念"
```

**面试中如何讲**（30秒）：
> "我把两个项目打通了。以前 AgentCV 的 Writer 遇到不认识的行业术语只能靠 LLM 内部知识猜——现在它先查 IntelliVault。比如 JD 要求 'Seata 经验'，Writer 通过 RAG 检索到 Seata 的定义和典型使用场景，再改写出更准确的表达。这样两个项目不是孤立的——AgentCV 是应用层，IntelliVault 是知识层，RAG 作为中间桥梁。"
