## A-1. Java并发编程 🔴 最高优先级

**来源**：阿里二面段十五（P0致命）+ 手录分析 M3-8

**问题**：CountDownLatch/join()/awaitTermination什么都说不出，说"锁竞争""休眠"但说不出具体API。

### A-1.1 线程等待/同步机制速记卡

| 机制 | 用途 | 关键API | 一句话描述 |
|------|------|---------|-----------|
| **CountDownLatch** | 等待N个线程完成 | `new CountDownLatch(N)` → `countDown()` → `await()` | 计数器归零时唤醒等待线程，一次性使用 |
| **Thread.join()** | 等待单个线程结束 | `thread.join()` / `thread.join(timeout)` | 调用方阻塞直到目标线程执行完毕 |
| **CyclicBarrier** | N个线程互相等待 | `new CyclicBarrier(N, runnable)` → `await()` | 所有线程到达屏障后一起继续，可循环使用 |
| **ExecutorService.awaitTermination()** | 等待线程池所有任务完成 | `shutdown()` → `awaitTermination(timeout, unit)` | 先关闭线程池再等待 |
| **CompletableFuture.allOf()** | 等待多个异步任务完成 | `CompletableFuture.allOf(f1, f2).join()` | 现代异步编程首选 |
| **wait()/notify()** | 线程间通信（低级） | `obj.wait()` / `obj.notifyAll()` | 必须在synchronized块内使用 |

### A-1.2 话术（30秒）

> "最常用三种方案。CountDownLatch——构造时设计数器为子线程数，主线程await()阻塞，每个子线程finally块里countDown()，计数器归零主线程继续。Thread.join()——主线程for循环对每个子线程调join()。线程池方案——executor.shutdown()后awaitTermination(60, TimeUnit.SECONDS)。选型上CountDownLatch最干净——不需要持有线程引用，适合线程由线程池管理无法直接join()的场景。"

## A-2. HashMap / Java集合框架 🔴 最高优先级

**来源**：阿里二面段十六（P0致命）+ 手录分析 M3-3, M3-9

**问题**："点哈式""点一块"口误，哈希冲突原因说不出，ConcurrentHashMap细节混淆。

### A-2.1 HashMap哈希原理速记卡

```
put(key, value)流程：
1. key.hashCode() → 获取32位原始hash值 h
2. (h = key.hashCode()) ^ (h >>> 16) → 高16位与低16位异或扰动
3. (n - 1) & hash → 取模定位桶（n是桶数，2的幂）
4. 桶为空 → 直接放入
5. 桶非空 → equals()判断是否同key
   - 同key → 覆盖
   - 不同key → 链表追加 / 红黑树插入
```

### A-2.2 哈希冲突的原因（15秒）

> "哈希冲突是数学必然。哈希函数把任意对象映射到有限个桶中——从无限域到有限域的映射，抽屉原理保证必然冲突。HashMap通过扰动函数(h ^ h>>>16)降低冲突概率，通过链表+红黑树解决已发生的冲突。"

### A-2.3 线程不安全三场景（30秒）

> "HashMap线程不安全有三个典型场景。一是JDK7扩容resize时的头插法导致环形链表——两个线程同时扩容，一个线程的next指针被另一个线程修改，形成环，get()时死循环CPU 100%。二是put操作中size++非原子——多线程同时put可能导致实际size小于元素数，数据丢失。三是扩容期间读写并发——一个线程在transfer迁移数据，另一个线程get可能读到null。解决方案：ConcurrentHashMap用CAS+synchronized。"

### A-2.4 hashCode与equals口诀

> "hashCode相等不一定equals（哈希碰撞）。equals相等hashCode必须相等（契约）。重写equals必须重写hashCode，否则HashMap/HashSet行为异常。"

### A-2.5 ConcurrentHashMap细节澄清

**来源**：字节一面段十四 + 手录分析 M3-3

**核心事实**：
- JDK7：Segment分段锁（继承ReentrantLock），默认16个段，并发度16
- JDK8：CAS + synchronized，锁粒度细化到桶（Node）级别
- put流程：先CAS尝试写入空桶 → 失败则synchronized锁住桶头节点 → 链表/红黑树插入
- size()：JDK7分段计数无锁累加，JDK8用baseCount + CounterCell数组分散竞争

## A-4. Transformer/LLM原理深化 🟠 高优先级

**来源**：阿里二面段十+段十一（P2）+ 手录分析 M3-5

**问题**：回答深度不够——"概率输出导致不稳定"是及格线，未提Temperature/Lost in the Middle/幻觉分类。

### A-4.1 话术（45秒）

> "从Transformer架构层面看，幻觉有三个来源。第一是概率采样——模型输出是对下一个token的概率分布做采样，temperature>0时每次都可能有不同的选择，当模型对某些事实不确定时概率分布平坦，更容易采样到错误token。第二是训练数据的局限——模型学到的是训练语料中的统计相关性而非真正的因果关系，比如训练数据中'QPS提升'经常和'优化'共现，模型就可能在没有真实数据的情况下也生成'QPS提升30%'。第三是位置编码的近似——Transformer用固定位置编码，长文本中间位置的信息提取能力下降（Lost in the Middle），可能导致基于文本中后段信息做判断时出现遗漏。我的Critic就是针对第二种——事实幻觉——做专门的事实核查。"

### A-4.2 模型训练过程基本概念（手录分析 M3-5）

> 预训练（Pre-training）：海量语料自监督学习，学习语言的统计规律
> SFT（Supervised Fine-Tuning）：高质量标注数据有监督微调，学会"按指令回复"
> RLHF（Reinforcement Learning from Human Feedback）：人类偏好反馈强化学习，对齐人类价值观

> "有向图判环。邻接表`Map<String, List<String>>`表示依赖关系。BFS拓扑排序：维护入度表，入度为0的节点入队，每次出队把邻居入度-1，为0时入队。最终出队数≠总节点数则有环。时间复杂度O(V+E)，空间O(V+E)。"
