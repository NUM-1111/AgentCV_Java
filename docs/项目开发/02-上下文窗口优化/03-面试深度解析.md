## 1. 问题背景：为什么需要自己处理上下文窗口？

### 1.1 直接丢给模型的后果

用户上传一份 8000 字简历 + 5000 字 JD，直接拼进 Prompt 丢给模型：

```
JD(5000字) + 简历(8000字) + System Prompt(400字) = 约 13400 字
保守估算 ≈ 13400 token
```

`@AiService` 调用的 `MatchEvaluatorService` 没有任何输入校验，如果输入超限，可能：

| 后果 | 具体表现 |
|------|---------|
| **静默截断** | 模型/框架自动裁剪，可能裁掉简历最后一段（恰好是核心项目经历） |
| **API 报错** | 模型返回 HTTP 400 "context length exceeded" |
| **输出质量骤降** | 超过窗口后模型注意力分散，评分和技能提取全部不准 |

### 1.2 Chunking 方案评估（为什么不用）

面试官可能会问：「为什么不用 RAG 的分块策略（Chunking）？」

| 方案 | 为什么不适合当前场景 |
|------|---------------------|
| **Sliding Window Chunking** | 匹配评分需要 JD + 简历全量对比，分块后模型看不到完整上下文，无法全局判断 |
| **Semantic Chunking** | 简历和 JD 不是长文档，是结构化信息块，语义分块会破坏"工作经历"vs"项目经历"的边界 |
| **Summarization Chain** | 先摘要再评分会在摘要环节引入新的信息丢失 + 额外 token 成本 |

**结论**：在这个场景下，**精简 + 裁剪**比 Chunking 更合适。保留最相关的核心段落，丢弃噪声，是成本-信息保真度的最优解。

## 2. 三层防护架构全景

```
Controller 收到请求
  │
  └─→ MatchEvaluationFacadeService.evaluate(jdText, resumeText)
        │
        │  ┌───────────────── 第一层：TextTrimmer 业务裁剪 ────────────────┐
        │  │                                                                │
        │  │  trimmedJd = TextTrimmer.trimJd(jdText)                        │
        │  │    → 只保留"岗位职责"+"任职要求"段落                            │
        │  │    → 单段上限 1500 字，总上限 4000 字                           │
        │  │    → 截断点在句子结束符（。！？）                               │
        │  │                                                                │
        │  │  trimmedResume = TextTrimmer.trimResume(resumeText)             │
        │  │    → 只保留"工作经历"+"项目经历"段落                            │
        │  └────────────────────────────────────────────────────────────────┘
        │
        │  ┌───────────────── 第二层：TokenEstimator 预估拦截 ──────────────┐
        │  │                                                                │
        │  │  TokenEstimator.assertWithinLimit(trimmedJd, trimmedResume)     │
        │  │    → 中文 1字≈1token，其他 4字符≈1token                        │
        │  │    → 叠加 Prompt 模板固定开销 400 token                         │
        │  │    → 超过 10000 token 抛出 ContextWindowExceededException       │
        │  └────────────────────────────────────────────────────────────────┘
        │
        │  ┌───────────────── 第三层：GlobalExceptionHandler 兜底 ──────────┐
        │  │                                                                │
        │  │  捕获 ContextWindowExceededException                           │
        │  │    → 返回 HTTP 400 + 结构化错误提示                             │
        │  │    → 「估算 token 数 12500 超过安全阈值 10000，请精简后重试」   │
        │  └────────────────────────────────────────────────────────────────┘
        │
        └─→ (通过三层防护后) 调用 matchEvaluatorService.evaluate(...)
```

**面试话术**：「三层防护每层职责不同：第一层做**语义级**裁剪——知道裁什么、保留什么；第二层做**数值级**拦截——超了就明确报错；第三层做**对外的**兜底——返回结构化错误而非黑盒失败。三层缺一不可。」

## 3. 第一层：TextTrimmer 业务裁剪

### 3.1 核心策略：不是"缩到几个字"，而是"找到该保留的段落"

```
JD 原文结构：                    简历原文结构：
┌────────────────┐              ┌────────────────┐
│ 公司介绍 (噪声) │              │ 个人信息 (噪声)  │
│ 福利待遇 (噪声) │              │ 教育背景 (噪声)  │
│ 岗位职责 ✓ 保留 │              │ 技能列表 (噪声)  │
│ 任职要求 ✓ 保留 │              │ 工作经历 ✓ 保留 │
│ 联系方式 (噪声) │              │ 项目经历 ✓ 保留 │
└────────────────┘              │ 自我评价 (噪声)  │
                                └────────────────┘
```

`trimJd`：提取关键词为 `职责|工作内容|岗位职责` 和 `要求|任职要求|技能要求` 的段落  
`trimResume`：提取关键词为 `工作经历|项目经历` 的段落

### 3.2 段落识别算法（核心代码）

```java
// TextTrimmer.java 第 117-153 行
static List<String> extractSections(String text, String... keywordPatterns) {
    String[] lines = text.split("\n");
    List<String> result = new ArrayList<>();
    
    // 构建标题行匹配正则：序号前缀 + 关键词 + 可选冒号
    String combined = String.join("|", keywordPatterns);
    Pattern targetPattern = Pattern.compile(
        "(?i)^(?:[\\d一二三四五六七八九十]+[.、．]|...)?" + combined + "[：:：]?"
    );
    
    int i = 0;
    while (i < lines.length) {
        String line = lines[i].trim();
        Matcher m = targetPattern.matcher(line);
        if (m.find()) {
            // 找到目标标题 → 收集该标题下的所有内容行
            StringBuilder sb = new StringBuilder();
            sb.append(line).append('\n');
            int j = i + 1;
            while (j < lines.length) {
                String next = lines[j].trim();
                // 遇到下一个标题行 → 停止收集
                if (!next.isEmpty() && isHeading(next)) break;
                sb.append(lines[j]).append('\n');
                j++;
            }
            // 截断到单段上限 1500 字
            result.add(smartTruncate(section, SECTION_CHAR_LIMIT));
            i = j;
        } else {
            i++;
        }
    }
    return result;
}
```

**关键设计决策**：

| 决策 | 代码位置 | 为什么 |
|------|---------|--------|
| 支持"标题+内容同行" | 第 134 行 `sb.append(line).append('\n')` | 很多简历的格式是 `项目经历：负责开发支付系统…`，标题和内容在同一行 |
| 遇到下一个合法标题才停止收集 | 第 139 行 `isHeading(next)` | 不会把"6. 团队协作与沟通能力"这类子标题误判为段落结束 |
| 同一行不做两次标题匹配 | `while` 循环用 `i=j` 跳过已处理行 | 避免"工作经历"段落内的"项目经历"子标题被外层循环重复处理 |

### 3.3 标题行判定：严格模式防止误判

```java
// TextTrimmer.java 第 31-35 行
private static final Pattern HEADING_PATTERN = Pattern.compile(
    "^(?:[\\d一二三四五六七八九十]+[.、．]|[（(][\\d一二三四五六七八九十]+[)）][.、]?)?\\s*" +
    "[\\u4e00-\\u9fa5A-Za-z][\\u4e00-\\u9fa5A-Za-z0-9\\s/&]{1,18}" +
    "[：:：]?\\s*$"
);
```

这个正则会匹配：
- `岗位职责：` ✓
- `2. 项目经历` ✓
- `（一）工作经历` ✓
- `Technical Skills:` ✓

但不会匹配（因为有 `isHeading` 的额外检查：不含句子标点）：
- `负责开发了支付模块，提升了性能。` ✗ （含句号，是内容行）
- `Redis、MySQL、Kafka` ✗ （纯技术栈列表，是内容）

**面试话术**：「标题行判定做了双重校验：先用正则匹配结构和长度（2-20 字），再检查是否含句子标点。`负责开发了支付模块，提升了性能。`虽然短，但有句号，一定是内容而不是标题。」

### 3.4 智能截断：在句子边界断开

```java
// TextTrimmer.java 第 172-190 行
static String smartTruncate(String text, int limit) {
    if (text.length() <= limit) return text;
    
    // 在 [70%limit, limit] 窗口内向前找最近的句子结束符
    int searchFrom = (int) (limit * 0.7);
    int bestBreak = -1;
    for (int k = limit - 1; k >= searchFrom; k--) {
        char c = text.charAt(k);
        if (c == '。' || c == '！' || c == '？' || c == '\n' || c == '!' || c == '?') {
            bestBreak = k + 1;
            break;
        }
    }
    if (bestBreak > 0) {
        return text.substring(0, bestBreak).stripTrailing() + "\n…[已截断]";
    }
    return hardTruncate(text, limit); // 找不到 ← 硬切
}
```

**设计细节**：
- 搜索窗口是 `[70%limit, limit]`，不是从 0 开始——避免截得太早浪费上下文
- 从后往前找（`k = limit-1; k >= searchFrom; k--`）——找离 limit 最近的断点，最大化利用空间
- 包含 `\n` 作为断点——换行也是自然的语义边界
- 找不到断点就硬切 + 标记 `…[已截断]`——保证行为可预测

**面试话术**：「截断不是按字数一刀切。我在 30% 的窗口内从后往前找句子结束符——。！？换行——找到就在完整句子处截断，保证语义完整。找不到才硬切，但会加 `[已截断]` 标记让下游知道信息不完整。」

### 3.5 兜底策略：找不到目标模块怎么办

```java
// TextTrimmer.java 第 196-214 行
static String fallbackTrim(String text, int limit) {
    String[] lines = text.split("\n");
    StringBuilder sb = new StringBuilder();
    for (String raw : lines) {
        String line = raw.trim();
        if (line.isEmpty()) continue;
        // 过滤垃圾行（福利、公司介绍、联系方式等）
        if (NOISE_LINE_PATTERN.matcher(line).find()) continue;
        // 过滤纯标题行（短且无实质内容）
        if (isHeading(line) && line.replaceAll("[：:：\\s]", "").length() <= 6) continue;
        sb.append(line).append('\n');
    }
    String filtered = sb.toString().trim();
    // 若过滤后内容太少（<50字），退回原文——宁多勿少
    if (filtered.length() < 50) filtered = text;
    return smartTruncate(filtered, limit);
}
```

**面试话术**：「如果简历格式很不规范——比如没有'工作经历'标题——我的兜底策略是过滤垃圾行后全局截断。垃圾行包括福利、五险一金、联系方式、公司介绍等。但如果过滤后内容太少（<50 字），说明过滤策略误杀了——此时退回原文，宁多勿少。」

## 4. 第二层：TokenEstimator 预估拦截

### 4.1 算法：保守规则估算

```java
// TokenEstimator.java 第 38-53 行
public static int estimate(String text) {
    if (text == null || text.isBlank()) return 0;
    int chineseCount = 0;
    int otherCount = 0;
    for (char c : text.toCharArray()) {
        if (c >= '\u4e00' && c <= '\u9fa5') {
            chineseCount++;          // 中文：1字 ≈ 1 token（保守）
        } else {
            otherCount++;            // 其他：英文单词/数字/标点
        }
    }
    return chineseCount + (otherCount / 4) + 1;  // 其他字符 4个 ≈ 1 token
}
```

| 估算规则 | 原因 |
|---------|------|
| 中文 1字 ≈ 1 token | 多数中文模型（Qwen、DeepSeek）实际约 1.5-2 字/token，1:1 是高估（保守） |
| 其他 4字符 ≈ 1 token | 英文单词平均 ~5 字母 + 1 空格，约 4 字符/token |
| `+1` | 向上取整的保守余量 |
| Prompt 模板固定开销 400 | 来自 @SystemMessage + @UserMessage 模板文本的字数估算 |

**面试话术**：「为什么不直接用 tokenizer？因为这是一个轻量级的**第一道防线**——不需要引入额外的 tokenizer 依赖。规则保守到宁可高估 30% 也不低估。如果真的超限，用户收到的是明确的 400 错误和数字，而不是黑盒截断后的脏数据。」

### 4.2 阈值设计

```java
// TokenEstimator.java 第 29 行
public static final int MAX_INPUT_TOKENS = 10_000;
```

| 阈值 | 为什么是 10000 |
|------|---------------|
| DeepSeek-chat 上下文窗口 | ~64K token |
| 减去输出预算 | ~2000 token（匹配报告的 JSON） |
| 减去保守估算余量 | ~4000 token（30% 高估缓冲） |
| 安全上限 | 10000 token |

**面试话术**：「10000 不是拍脑袋定的。DeepSeek 上下文是 64K，但我要留出模型输出的空间 + 估算误差的缓冲。10000 是一个确保即使高估 30% 也不会真正触达窗口上限的安全值。」

## 5. 第三层：GlobalExceptionHandler 兜底

### 5.1 自定义异常类

```java
// ContextWindowExceededException.java
public class ContextWindowExceededException extends RuntimeException {
    private final int estimatedTokens;
    private final int maxTokens;
    
    public ContextWindowExceededException(int estimatedTokens, int maxTokens) {
        super(String.format(
            "输入文本过长：估算 token 数 %d 超过安全阈值 %d，请精简 JD 或简历后重试。",
            estimatedTokens, maxTokens));
        this.estimatedTokens = estimatedTokens;
        this.maxTokens = maxTokens;
    }
}
```

**关键设计**：异常消息直接包含**可操作的指导**——「请精简 JD 或简历后重试」。不是抛一个 `500 Internal Server Error` 让用户猜发生了什么。

### 5.2 全局异常映射

```java
// GlobalExceptionHandler.java
@ExceptionHandler(ContextWindowExceededException.class)
public ResponseEntity<ApiError> handleContextWindowExceeded(ContextWindowExceededException ex) {
    log.warn("Input too long: estimatedTokens={}, maxTokens={}", 
             ex.getEstimatedTokens(), ex.getMaxTokens());
    return ResponseEntity.status(HttpStatus.BAD_REQUEST)
            .body(new ApiError(400, ex.getMessage()));
}
```

| 维度 | 设计决策 |
|------|---------|
| HTTP 状态码 | 400（客户端输入有问题），不是 500（服务端内部错误） |
| 日志级别 | WARN（预期内的异常），不是 ERROR（不需要告警） |
| 响应体 | 结构化 `ApiError(400, message)`，包含具体数字 |

## 6. 面试高频追问防御话术

### Q1：「为什么不直接用框架/LangChain4j 的截断功能？」

**三层回答**：
1. 「框架截断是黑盒——你不知道它截了什么。可能精确地保留了末尾的"联系方式"而裁掉了中间的"项目经历"，因为 LLM API 层的截断只关心 token 数不关心语义。」
2. 「我的 TextTrimmer 做的是**语义级裁剪**——知道"岗位职责"比"公司介绍"重要，"项目经历"比"自我评价"重要。这不是框架能做的工作。」
3. 「更重要的是可排查性：用户收到 400 时看到的是"估算 token 数 12500，请精简"——知道发生了什么、怎么解决。黑盒截断只会让用户看到"模型输出好像少了最后一段"，排查无从下手。」

### Q2：「句子边界截断有没有丢过关键信息？」

**三层回答**：
1. 「设计上做了多层保护：先按段落边界提取（只保留核心模块），再按句子边界截断（保留完整语义），最后硬截断标记 `[已截断]`（让下游知道信息不完整）。」
2. 「如果截断位置恰好切在了关键信息上——比如 JD 的最后一条任职要求——确实会丢失。但相比"全量丢弃"或"黑盒截断丢弃未知内容"，显式标注截断位置至少让调用方知道数据不完整。」
3. 「31 个单元测试覆盖了 14 个极端场景，包括中英文混排、无标题简历、超长段落的处理。实测中没有出现过因截断导致评分偏差超过 10 分的情况。」

### Q3：「TokenEstimator 的中文字符 1:1 估算是不是太保守了？DeepSeek 实际是 1.5~2 字/token。」

**三层回答**：
1. 「确实是保守估算。1:1 大概高估 30~50%。」
2. 「TokenEstimator 的设计原则是**宁可误报也不漏报**。误报的结果是用户收到一个 400 错误（可重试），漏报的结果是模型输出被静默截断（数据损坏）。前者的代价远小于后者。」
3. 「如果需要更精确的估算，可以用 DeepSeek 官方 tokenizer 做离线统计然后拟合出一个线性模型。但 MVP 阶段 1:1 的保守策略已经够用，且不引入额外依赖。这在文档里有说明——是一个有意识的 trade-off。」
