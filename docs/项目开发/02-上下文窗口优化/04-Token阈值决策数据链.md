## 一、约束校准公式（一图看懂）

```
┌──────────────────────────────────────────────────────────────────┐
│                    Token 预算约束关系                              │
│                                                                  │
│   TextTrimmer                    TokenEstimator                  │
│   TOTAL_CHAR_LIMIT = 8000  ←→  MAX_INPUT_TOKENS = 10_000         │
│                                                                  │
│   约束A: 8000 × 1.0(保守系数) + 400(Prompt开销)                   │
│        = 8400 ≤ 10000  ✅  余量 1600 token (16%)                 │
│                                                                  │
│   约束B(误杀验证): Golden Set 9组实测 486~604，最大604 ≪ 10000  ✅ │
│        阈值不是从样本推导的，是从约束A的8400取整来的。              │
│                                                                  │
│   约束C: 英文简历链路不崩溃 + 核心段落保留  ✅                      │
│                                                                  │
│   验证方式: mvn test -Dtest=TokenBudgetCalibrationTest            │
│   失败时会告诉你改到多少。                                        │
└──────────────────────────────────────────────────────────────────┘
```

### 10K不是从样本统计出来的——是从 Trimmer 结构反推的

TextTrimmer 的理论最大输出由`SECTION_CHAR_LIMIT(1500) × 段落数`决定：
- JD 最多 2 段（职责 + 要求）= 3000 字
- 简历最多 3 段（工作经历 + 项目经历 + 核心技能）= 4500 字
- 合计 = 7500 字，设为 8000 是给 fallback 路径留 500 字余量

推导链：
```
8000 × 1.0(中文保守估算系数) + 400(Prompt开销) = 8400 token  ← 阈值下限
低于8400，约束A会断裂 → 取整到 10000，留 1600 token 业务增长余量
```

**Golden Set 的 604 不是用来推导阈值的，是用来验证阈值没有误杀正常用户的。**

约束A 回答"阈值不能低于多少"，约束B 回答"阈值有没有误杀用户"——两个独立问题。

## 四、常见追问预埋

### Q1: 为什么是10K而不是8K？

8K太紧。Trimmer理论最大输出8000 + 400开销 = 8400 > 8000。如果设8K，约束A直接断裂。最低安全阈值 = 8400，取整到10K留1600 token的业务增长余量。

### Q2: 为什么不是12K？

边际收益为零。阈值下限由约束A决定（8400），10000已有1600 token余量。提到12000只是把余量从1600扩到3600——正常JD+简历组合实测只有~500 token量级，多出的2000 token输入预算没有任何业务场景需要。

### Q3: 预估误差到底多大？

中文按1:1估算，实际约1.5~2字/token → 高估约30-50%。英文按4字符≈1 token（即约1英文词≈2 token），实际1词≈1.3 token → 高估约50%。设计上是故意高估——宁可误拦（用户收到400可精简后重试），不可漏拦（被截断导致数据损坏不可逆）。

### Q4: 英文简历估算准确吗？

C6-1英文样本已纳入Golden Set。完整链路实测：英文JD 247字符→62 tokens，英文简历364字符→92 tokens，含400开销总计554 tokens——在正常范围内。核心段落（Requirements、Work Experience）全部保留，未出现因纯英文导致的段落识别丢失。

### Q5: 换模型怎么办？

改两个常量 + 重跑管道。TokenEstimator 的估算系数和 MAX_INPUT_TOKENS 需按新模型的 tokenizer 重新校准。TextTrimmer 的裁剪逻辑和 ContextWindowExceededException 异常处理基本复用。管道会自动告诉你新阈值该设多少。

### Q6: Golden Set 只有9组，统计上够吗？

9组覆盖了中文5种边界场景（正常/稀疏/模糊/精确/零交集）+ 英文1种，作为"不变量约束验证"足够——证明正常用例远在阈值之下。阈值本身不是从统计推导出来的，而是从 Trimmer 结构上限（7500→8000）+ 估算系数 + Prompt开销 的公式推导出来的。Golden Set 是用来验证"不误杀"，不是用来推导阈值。

### Q7: Prompt开销400是怎么来的，如果改了SystemMessage怎么办？

400是 `@SystemMessage + @UserMessage` 模板文本约400字。如果模板变更，需要重新统计字数→更新 `PROMPT_TEMPLATE_OVERHEAD` 常量→然后重跑 `TokenBudgetCalibrationTest`，管道会验证新开销是否仍在阈值包络内。

## 五、维护手册

### 改了任何一个常量之后

```
mvn test -Dtest=TokenBudgetCalibrationTest
```

管道会输出三种约束的当前状态。任一约束失败，**失败信息会直接告诉你修复建议**（改到哪个值）。

### 常量变更影响矩阵

| 改动 | 影响 | 需同步检查 |
|------|------|-----------|
| 改 `TOTAL_CHAR_LIMIT` | 约束A的理论最大值变化 | 如果增大到 >9600，必须同步提高 MAX_INPUT_TOKENS |
| 改 `MAX_INPUT_TOKENS` | 约束A和约束B的门槛变化 | 如果减小到 <8400，约束A必断裂 |
| 改 `PROMPT_TEMPLATE_OVERHEAD` | 约束A偏移 | SystemMessage/UserMessage 模板变更后必须重新统计 |
| 改 `TokenEstimator.estimate()` 公式 | 约束A/B/C的计算基准变化 | 公式变更后所有约束重算 |
| 新增 Golden Set 样本 | 约束B自动纳入新样本 | 可能改变 effective_max，影响安全余量|

### Golden Set 扩充规则

每遇到一个新的边界场景，加一条到 `golden-test-set.json`：
- JSON 格式必须合法（`mvn test` 会验证）
- `id` 按现有分类体系递增
- `category` 描述新场景（如 `C7-超长段落`）
- 加完跑 `TokenBudgetCalibrationTest` 确认

> **🔧 工程思维**：Golden Set 是随时间增值的资产。现在9组，一年后可能是30组——面试时可以说"Golden Set 从最初的8组增长到现在的30组，覆盖了X/Y/Z场景"。
