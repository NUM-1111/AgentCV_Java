# 模拟面试记录 — 上下文窗口优化

## 需要提升的点（面试前必看）

1. **兜底阈值要记住**：`fallbackTrim` 中过滤后内容 `< 50` 字符才退回原文，这个数字要能脱口而出。
2. **安全阈值的来源要能解释**：`MAX_INPUT_TOKENS = 10_000` 的依据是 DeepSeek-chat 上下文窗口约 64K，减去模型输出预算（约 1000 token）和 Prompt 模板开销（400 token）后，保守设定为 10000，留有充足余量。
3. **换模型的影响要有基本认知**：不同模型 tokenizer 不同，换模型时 `TokenEstimator` 的估算规则和阈值需要重新校准，`TextTrimmer` 和异常处理逻辑基本可复用。
4. **极端场景要能引用测试用例**：回答"没有目标模块时效果如何"时，直接说"我们有对应的极端场景测试用例覆盖"，比单纯推断更有说服力。

## Q&A

### Q1：背景理解

**问：** 你当时发现这个问题的契机是什么？能描述一下"上下文窗口溢出"在你们系统里具体会造成什么现象？

**答：** 当时我们没有对输入有处理的意识，基本 0 处理，结果就是当用户输入的 jdText 过大的时候，会导致模型自行进行静默截断。这是最糟糕的错误：首先 Token 消耗很大，其次就是静默报错、自行截断，让问题难以察觉。

**评价：** ✅ 通过。"静默截断"定位准确，能说出"问题难以察觉"是最糟糕的地方，抓住了 bug 的本质危害。

---

### Q2：方案设计

**问：** 你最终采用了"业务层裁剪 → Token 预估拦截 → 调用模型"这三步流水线。为什么要把裁剪放在 Token 预估之前，而不是反过来？这个顺序的设计依据是什么？

**答：** 首先业务层裁剪是在原输入进行的预处理，通过筛选把我们系统需要分析的数据拿出来，把不需要的舍弃，那么处理后的 text 才是我们需要喂给模型去跑的。如果颠倒顺序，可能会导致本来处理后能够跑的模型，通过 Token 预估判断为不能跑了，这就是一个错误的处理。设计的依据是，模型的上下文窗口有限制，我们需要对可能会超出限制的输入进行预处理，而 Token 预估是把已经确定要放入模型的 text 进行的拦截，旨在对及时处理后仍然超出限制的输入进行拦截，防止模型出现上述问题。

**评价：** ✅ 基本通过，逻辑清晰。**补充点**：Token 预估不只是"防止超限"，还是"防止裁剪逻辑本身出 bug 时的兜底保险"，加上这一层理解会更完整。

---

### Q3：技术细节

**问：** `TextTrimmer` 的兜底策略是：找不到目标模块时，过滤垃圾行后再截断。如果一份简历完全没有"工作经历"和"项目经历"这两个标题，裁剪结果会是什么？这种情况下裁剪后的内容还能支撑模型做出有效的匹配评估吗？

**答：** 我们的处理逻辑是：如果没有找到目标模块，我们仍然会过滤联系方式等垃圾行，剩下的可能是一些其他信息内容。如果这些信息过少，我们会直接返回原文；如果满足长度要求，我们会对内容处理后返回模型。裁剪之后的内容肯定是难以让模型进行有效评估的，大概率会显示符合要求的技能或者项目几乎为 0，然后给出对应的建议。

**评价：** ⚠️ 基本通过，但有细节漏洞。**需补充**：兜底阈值是过滤后内容 `< 50` 字符才退回原文（见 `TextTrimmer.java` 第 210 行）。另外"大概率技能为 0"是推断，面试中应直接说"我们有极端场景的测试用例覆盖这个 case"更有说服力。

---

### Q4：边界与权衡

**问：** `TokenEstimator` 用的是保守估算，会不会在某些场景下误判——把实际没超限的请求拦截掉？你当时是怎么权衡"误拦截率"和"安全性"的？

**答：** 会有这个误差，但安全的拦截比危险的通过更有价值：1. 模型的上下文限制对于简历和 JD 来说其实很大，很少有会超过限制的文本；2. 即使有临近上下文限制边界的输入，我们仍然采用"宁可错杀也不放过"的原则，因为因长度拦截报错总比静默报错要好。

**评价：** ✅ 通过，思路正确。**需补充**：安全阈值 10000 的来源——DeepSeek-chat 上下文窗口约 64K，保守设定 10000 作为输入上限，留有充足余量给模型输出和 Prompt 模板开销。面试官大概率会追问这个数字的依据。

---

### Q5：深度扩展

**问：** 假设未来需要支持更长的简历，或者模型换成了支持 128K context window 的版本，你现在这套方案哪些部分需要改动，哪些可以复用？

**答：** 如果需要支持更长的 CV，首先确认是否能更换模型，然后这套方法可以在扩大上下文窗口限制边界后继续复用，主要是拓展跟学术相关的 pattern。如果是改变模型……不太清楚。

**评价：** ⚠️ 部分通过，有明显短板。**需补充**：换模型时，`TokenEstimator` 的估算规则和阈值需要重新校准（不同模型 tokenizer 分词粒度不同，如 GPT 系列用 BPE，中文 token 数会更多）；`TextTrimmer` 的裁剪逻辑和 `ContextWindowExceededException` 的异常处理基本可以复用，只需修改阈值常量。这个回答不需要深入了解 tokenizer 原理，但要体现对"模型可替换性"的基本意识。
