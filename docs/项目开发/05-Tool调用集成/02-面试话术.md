## 一、设计决策：为什么给 Critic 注册 Tool？

### 核心问题

LLM 在以下场景存在天然弱点：
- **数值精确比对**——LLM 擅长语义理解，但不擅长"5000 ≠ 2000"这种精确数值判断
- **技术栈差集运算**——LLM 可能忽略某个技术的缺失或新增，因为它对列表做差集不精确
- **角色措辞升级检测**——"参与→主导"这类关键词替换，LLM 判断不一致（有时认为合理有时认为夸大）

**设计决策**：让 Critic 拥有"核查武器"——检测到可疑声明时，**自主决定**调用 Tool 做精确比对，而不是凭感觉猜。

### 为什么不用纯 LLM Prompt 约束？

> "Prompt 告诉 Critic'请精确比对数值'——但它没有'数值提取+差集运算'的能力。就像告诉一个人'请精确计算 12345 × 67890'——他可以努力算，但不如给他一个计算器。FactCheckTool 就是 Critic 的计算器。"

---

## 二、三个 @Tool 方法的设计

### checkClaim — 数值精确比对

**设计要点**：
- 返回 String 而不是 boolean——返回值作为 `ToolExecutionResultMessage` 发回 LLM，需要让 LLM 能直接理解差异
- "不一致：原为 QPS 2000，改为 QPS 5000" 比返回 "false" 更有用——LLM 不需要二次推理
- 覆盖4种场景：双方都有数字（差集比对）、原文无数字改写有（疑似捏造）、原文有数字改写无（可能遗漏）、双方都无（纯定性描述）

### checkTechStack — 技术栈差集运算

**设计要点**：
- 大小写不敏感：`RocketMQ` == `rocketmq`，防止大小写差异误报
- 支持多分隔符：逗号、中文逗号、顿号、空格
- 输出两类差异：新增技术（疑似捏造）+ 遗漏技术（可能丢失信息）

### checkRoleWording — 角色措辞升级检测

**设计要点**：
- 关键词集合：MILD_WORDS（参与/协助/配合/支持/了解/接触/学习）vs STRONG_WORDS（主导/设计/架构/从零搭建/独立负责/领导）
- 只有"原文有弱措辞 且 改写有强措辞"才判定为夸大
- 原文本身就有强措辞（如"主导"）→ 改写使用强措辞正常

---

## 三、为什么返回 String 而不是 boolean？

> "这是 LangChain4j 的 Tool 调用机制决定的。Tool 的返回值会作为 `ToolExecutionResultMessage` 的 content 字段发回给 LLM。如果我返回 `boolean`，LLM 收到的是 'true' 或 'false'——它不知道'哪里不一致'，需要二次推理。返回差异详情字符串——LLM 直接拿到'原文 QPS=2000，改写 QPS=50000'——它可以据此写出更准确的 violation detail。这本质上是在提升 Tool 调用链路的信息密度。"

---

## 四、Agent vs Tool 的本质区别

**常被问**：「Agent 和 Tool/Skills 有什么区别？」

> "Agent 有决策权——它有自己的 SystemMessage 定义身份和判定标准，能自主决定'这个违规是 FAKE_DATA 还是 EXAGGERATION'。Tool 是被调用的能力模块——它只做精确计算（比如数值比对、差集运算），把结果返回给 Agent 做决策。
>
> 举个类比：Critic 是法官——它决定'有罪还是无罪'；FactCheckTool 是法医——它只提供'伤口深度 3cm'的事实数据。
>
> 面试中经常被问的 'Agent vs Skills' 也是同一个道理——如果你只需要一个检查模块，用 Tool/Skill。如果你需要独立的角色身份和判定标准，用 Agent。我的场景里 Critic 有独立的判定标准（四维度+severity 分级）和决策权（通过/打回+写 feedback）——所以选 Agent。"
