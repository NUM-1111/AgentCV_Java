# 05 — Tool 调用集成（FactCheckTool + @Tool 机制）

> **状态**：✅ 已完成 | **日期**：2026-06-29 | **关联需求**：[I-8](../../面试准备/复习计划/复习计划5-三层改进方案/01-项目设计与数据验证.md#i-8-toolfunction-calling-集成-最高优先级开发向)

---

## 1. 问题陈述

### 1.1 为什么做这件事

AgentCV 的 Agent 是纯 LLM 调用——`FactCriticAgent` 只通过 SystemMessage 告诉 LLM"要精确比对数字"，但 LLM 天然不擅长精确数值比对（如 `5000 ≠ 2000`）、集合差集运算（技术栈差异）、以及角色措辞升级检测。这导致：

- **面试空白**：被问"Agent vs Skills 区别"时沉默 45 秒（阿里一面段十三）
- **审查质量不可靠**：Critic 对数字篡改的检测依赖 LLM 的"感觉"，而非精确计算
- **项目深度不足**：LangChain4j 原生支持 `@Tool` 注解，但项目中从未使用——这就是"AI Wrapper"和"Agent 平台"的本质区别

### 1.2 不做会怎样

- 面试中继续无法回答"Agent vs Skills"的追问
- Critic 可能漏判数值差异（LLM 单独判断 "5000 ≠ 2000" 的准确率不是 100%）
- 项目停留在"能跑但没有 Tool 能力"的阶段，与竞品（LangChain/Coze/Multi-Agent 框架）差距拉大

## 2. 架构决策

### 2.1 决策矩阵：4 条路径对比

| 评估维度 | 路径 A：手动 Builder | 路径 B：全局自动发现 | **路径 C：@AiService(tools)** ✅ | 路径 D：ToolProvider |
|----------|---------------------|---------------------|-------------------------------|------|
| 框架是否支持 | ✅ | ❌ 不支持 | ✅ | ✅ |
| 改动面大小 | 大（需 @Configuration） | — | **小（改 1 注解 + 新建 1 类）** | 中 |
| 是否破坏现有注入链 | ⚠️ 会破坏 | — | ✅ **不破坏** | ⚠️ 可能破坏 |
| 复杂度 | 中 | — | **低** | 高 |
| 适合场景 | 新 Agent 从零创建 | — | **给现有 Agent 加 Tool** | 动态 Tool 集合 |

### 2.2 选定方案：路径 C

```java
@Component("factCheckTool")        // Spring Bean，Bean 名 = "factCheckTool"
public class FactCheckTool { ... }

@AiService(tools = {"factCheckTool"})  // 通过 Bean 名引用，框架自动生成 JSON Schema
public interface FactCriticAgent { ... }
```

**决策理由**：

1. **改动面最小**：Coordinator 一行没改，只改了 FactCriticAgent 的注解参数
2. **不破坏注入链**：保持 `@AiService` + `@Autowired` 自动代理模式，Spring Boot 无缝适配
3. **扩展空间预留**：未来可按需切换到 `@AiService(toolProvider = "...")` 实现动态 Tool 选择

### 2.3 关键设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| Tool 注册在哪个 Agent 上？ | Critic（不是 Coordinator，不是 Writer） | Critic 是审查者，Tool 是它的核查武器。Writer 不需要核查工具，Coordinator 不管内容审查 |
| Tool 返回值类型？ | `String`（不是 `boolean`） | 返回值变成 `ToolExecutionResultMessage.content`。`"不一致：原为 QPS 2000，改为 QPS 5000"` 比 `"false"` 有用——LLM 直接拿差异详情写 violation detail |
| 数值比对用正则还是 NLP？ | 正则 | 确定性——同一输入永远返回同一结果，不依赖模型版本 |
| 技术栈比对大小写敏感？ | 不敏感（`rocketmq == RocketMQ`） | LLM 输出的大小写不稳定，统一 `toLowerCase()` 处理 |

## 3. 实现概要

### 3.1 文件清单

| 文件 | 类型 | 行数 | 说明 |
|------|------|------|------|
| `FactCheckTool.java` | 新建 | 260 | 3 个 `@Tool` 方法：`checkClaim`、`checkTechStack`、`checkRoleWording` |
| `FactCriticAgent.java` | 修改 | 94→108 | `@AiService` → `@AiService(tools = {"factCheckTool"})` + SystemMessage 增加 Tool 抉择框架 |
| `FactCheckToolTest.java` | 新建 | 248 | 19 个纯 Java 单元测试 |
| `ToolCallingIntegrationTest.java` | 新建 | 197 | 8 个集成测试，验证 LLM 自动调用 Tool |

### 3.2 核心类说明

```
FactCheckTool (@Component)
├── checkClaim(@P original, @P rewritten) → String
│   └── 正则提取数值 → Set 差集比对 → 5 种分支返回不同结果
├── checkTechStack(@P originalList, @P rewrittenList) → String
│   └── 解析技术名 → 大小写不敏感 Set 差集 → "新增技术：kafka"
└── checkRoleWording(@P originalRole, @P rewrittenRole) → String
    └── 弱/强措辞词表匹配 → 检测角色夸大模式
```

### 3.3 Tool ↔ LLM 数据流

```
每次 Critic.check() 调用：

1. LangChain4j 扫描 FactCheckTool 的 @Tool 方法 → 自动生成 JSON Schema
2. JSON Schema 注入 LLM 请求的 tools 字段（顶层，与 messages 平级）
3. LLM 判断需要精确比对 → 返回 ToolExecutionRequest（content=null）
4. LangChain4j 拦截 → 反射调用 checkClaim() → 拿到返回值
5. 返回值包装为 ToolExecutionResultMessage（role: "tool"）→ 发回 LLM
6. LLM 基于 Tool 结果做最终判断 → 返回 CiticReport
```

### 4.3 集成测试策略：已知违规输入法

**核心思路**：不直接断言 ToolRequest（LangChain4j 未暴露此 API），而是通过"已知违规输入"间接验证。

**验证链路**：
```
输入：原文 QPS 2000 → bullet QPS 5000
 ↓
验证①：approved = false（Critic 发现了问题）
验证②：violations 中有 FAKE_DATA 类型
验证③：detail 中同时包含 "2000" 和 "5000"（证明做了精确比对）
验证④：日志中出现 "checkClaim called" trace
```

**实际运行日志证据**（2026-06-29 测试运行）：
```
Tool execution result: 不一致：原文有但改写遗漏 [2000]；改写出现原文没有的数值 [5000]
Tool execution result: 新增技术：kafka（原文未出现→疑似捏造）
Tool execution result: 角色夸大：原文使用[参与]，改写使用[从零搭建, 架构, 设计, 主导]
```

## 5. 面试要点

### 5.1 30 秒话术

> "我给 Critic Agent 集成了 LangChain4j 的 @Tool 机制。通过 `@AiService(tools = {"factCheckTool"})` 注册了三个核查工具——checkClaim 做精确数值比对、checkTechStack 做技术栈差集、checkRoleWording 做角色措辞检测。Agent 在发现可疑声明时自动调用 Tool，而不是凭 LLM 的感觉判断。这就是 Agent vs Skills 的区别——Agent 有决策权，Tool 是被调用的能力模块。"

### 5.2 追问预埋

| 面试官追问 | 回答要点 |
|-----------|---------|
| "为什么选 @AiService 的 tools 参数而不是手动 builder？" | 改动面最小，不破坏现有 Spring Boot 注入链。4 条路径都评估过，选了最干净的 |
| "Tool 返回值怎么回到 LLM？" | 变成 `ToolExecutionResultMessage`（role: "tool"），附在 messages 数组后面发回 LLM。返回 String 比 boolean 好——LLM 直接拿差异详情 |
| "怎么验证 Tool 确实被调用了？" | 没有直接断言 ToolRequest（API 没暴露）。用已知违规输入法——输入 QPS 2000→5000 的篡改案例，验证 Critic 的输出 + 日志 trace |
| "未来怎么扩展？" | 预留了 toolProvider 接口。做 I-1 评分体系时，改成 `toolProvider = "scoringToolProvider"` 实现按 JD 行业动态选 Tool |

### 5.3 架构图


## 6. 扩展预留

### 6.1 从静态 Tool 到动态 ToolProvider

当前：`@AiService(tools = {"factCheckTool"})` — 静态，3 个 Tool 永远不变。

未来 I-1 评分体系：

```java
// Change one line:
@AiService(toolProvider = "scoringToolProvider")  // ← 从 tools 改为 toolProvider
public interface FactCriticAgent { ... }

// ScoringToolProvider 根据 JD 行业动态选择评分 Tool 集合
@Component("scoringToolProvider")
public class ScoringToolProvider implements ToolProvider {
    @Override
    public ToolProviderResult provideTools(ToolProviderRequest request) {
        JobCategory category = classifyJD(request.userMessage().singleText());
        return switch (category) {
            case BACKEND -> backendScoringTools;
            case DATA_ANALYST -> analyticsScoringTools;
            // ...
        };
    }
}
```

迁移成本 = 一行注解改动，零代码重构。

### 6.2 新增 Tool 的步骤

```
1. 新建 XxxTool.java → @Component("xxxTool")
2. 在 @AiService(tools = {..., "xxxTool"}) 加一个 Bean 名
3. 在 SystemMessage 里加一行 Tool 描述
4. 写 XxxToolTest.java
```
