# 02 — 需求分析与产品规划：从"做功能"到"做产品"

---

## 0. 为什么写这篇

当前项目的问题不是技术没写好，而是**没有人定义过"用户用这个工具要达成什么"**。

证据：
- 前端输入框叫"原始简历/项目经历"，但实际用户会粘贴什么？一整份简历？还是一个项目描述？
- 输出是 `rewrittenBulletPoints`（要点列表），但用户需要的是**一份完整简历**，不是几个要点
- SSE 流式只推送阶段开始/结束，中间数十秒空白——用户感受不到"流式"的价值
- 用户输入里包含个人信息、教育背景、多个项目，但系统只改写了"项目经历"部分，其余全丢了

这篇文档的目标：**从头定义用户场景 → 推导功能需求 → 规划前后端改造**。

## 1. 用户是谁？他要做什么？

### 1.1 用户画像

| 属性 | 描述 |
|------|------|
| 谁 | 求职者（自己或朋友），有一份已有简历 |
| 场景 | 看到某个心仪岗位的 JD，想把简历针对这个岗位优化 |
| 痛点 | 手动改写简历费时、不确定哪些关键词该突出、担心改完后夸大事实 |
| 期望 | 粘贴 JD + 简历 → 得到一份**完整可用的新简历**，过程中能看到进度 |

### 1.2 用户输入长什么样？

用户不会只粘贴"项目经历片段"。他会粘贴**一整份简历**，包含：

```
张三
手机 138xxxx | email@xxx.com

教育背景
2023-2027 某某大学 计算机科学 本科

技能
Java, Spring Boot, Redis, MySQL, Docker...

项目经历
项目一：电商订单系统（2024.06-2024.12）
负责订单系统性能优化，通过缓存和异步处理，QPS从500提升至2000。
使用了Redis和RocketMQ。参与了数据库查询优化的相关工作。

项目二：RAG 智能问答系统（2025.01-2025.06）
基于 LangChain + Milvus 构建知识库问答，实现双阈值降级检索...

实习经历
2025.07-2025.09 某公司 Java 开发实习生...
```

### 1.3 用户期望的输出长什么样？

用户期望得到的**不是** 9 条 rewrittenBulletPoints。他期望的是：

```
张三
手机 138xxxx | email@xxx.com

教育背景  ← 不变
2023-2027 某某大学 计算机科学 本科

技能  ← 不变
Java, Spring Boot, Redis, MySQL, Docker...

项目经历  ← 这里被优化了
项目一：电商订单系统（2024.06-2024.12）
【改写后】主导订单系统高并发优化，引入 Redis 缓存 + RocketMQ 异步削峰，
QPS 从 500 提升至 2000，响应时间降低 60%...

项目二：RAG 智能问答系统（2025.01-2025.06）
【改写后】设计并实现基于 LangChain + Milvus 的多租户 RAG 系统...

实习经历  ← 不变
2025.07-2025.09 某公司 Java 开发实习生...
```

**关键洞察：系统需要做"局部替换"，而不是"从零生成"。**

## 2. 当前系统 vs 用户期望的差距

| 维度 | 当前系统做了什么 | 用户需要什么 | 差距 |
|------|----------------|------------|------|
| **输入** | 接受 `jdText` + `originalProjectText`（3000 字符上限） | 粘贴 JD + 完整简历 | 输入被截断，用户被迫手动切分 |
| **输出** | 返回 `rewrittenBulletPoints`（仅项目要点列表） | 返回完整的优化后简历 | 个人信息/教育/技能/其他项目全丢了 |
| **拼接** | 无 | 需要把优化后的项目经历**回填**到原简历的对应位置 | 完全缺失 |
| **流式体验** | 阶段级推送（SCORING_DONE → WRITER_DONE → CRITIC_DONE），中间静默数十秒 | 看到处理进度（评分中→改写中→审查中），知道系统没死，而非白屏干等 | 阶段间静默期浏览器可能断开（已通过心跳 R5 修复） |
| **错误处理** | 只有全局 try-catch | Writer 生成英文时，用户看到英文 bullet 一脸茫然 | 已修复（R4） |
| **评分反馈** | 给出 matchScore 和 matched/missing skills | 用户想看到：我应该重点突出哪些 JD 关键词？ | 评分信息未融入改写流程 |

## 3. 从差距推导需求：完整的需求列表

### R1：完整简历输入（不截断）

**现状：** 输入框上限 3000 字符，用户粘贴完整简历会超限。

**需求：** 前端允许粘贴完整简历，后端不再限制 3000 字符（改为合理的上限如 10000），由 TextTrimmer 负责裁剪。

### R2：完整简历输出（回填拼接）

**现状：** 只返回 `rewrittenBulletPoints`，丢失其他内容。

**需求：** 输出是一份完整的优化后简历。系统需要：
- 识别原简历的结构（个人信息 / 教育 / 技能 / 项目经历 / 实习 / 其他）
- 只改写"项目经历"部分
- 将改写后的项目经历回填到原结构，其余部分原样保留

### R3：真正的流式体验

**现状：** 事件粒度是"一个阶段做完"。SCORING_START →（等 9s）→ SCORING_DONE。

**需求：** 
- Phase 2（改写）应该是逐 bullet 或逐句生成，而不是全部写完才推送
- 如果 LLM API 支持 streaming（`chat().stream()`），前端应该看到文字逐字出现
- 如果 LLM API 不支持 streaming，至少每个 bullet 写完就推送一次

### R4：中文输出约束

**现状：** Writer Agent system message 中没有语言要求。

**需求：** 在 Writer Agent 的 system message 中明确："所有输出必须使用中文，技术名词（如 Redis、QPS）可保留英文但描述必须中文"。

### R5：SSE 心跳

**现状：** 两个事件之间可能间隔数十秒，连接静默。

**需求：** 每隔 5 秒发一个 heartbeat 事件（`: heartbeat`），让前端知道连接没断，也让浏览器不超时。

## 4. 技术方案：从需求到代码

### 4.1 R1+R2：完整的输入输出改造

**输入侧改造（前端 + Controller）：**

```
旧：jdText（纯文本）+ originalProjectText（纯文本）
新：jdText（纯文本）+ fullResume（完整简历文本）
```

用户粘贴整份简历，Controller 不做 3000 字符截断。

**Service 层改造：**

```
新增方法：optimizeFullResume(jdText, fullResumeText)
  Step 1: parseResume() → 把完整简历拆成结构化片段
    返回 ResumeSections { header, education, skills, projects[], experience, other }
    
  Step 2: 对每个 project 调用现有 optimize(jdText, project.text)
    每个 project 独立走 Actor-Critic 管线
    
  Step 3: 将所有改写后的 project 回填到原结构
    返回 String: 完整的优化后简历文本
```

**输出侧：** `OptimizationReport` 新增字段 `finalResumeText`（完整简历字符串）。

### 4.2 R3：真正的流式改写

当前事件粒度：阶段级别。需要改为 bullet 级别：

```
旧事件流：
SCORING_START → SCORING_DONE → WRITER_START → WRITER_DONE → CRITIC_START → CRITIC_DONE → COMPLETE

新事件流：
SCORING_START → SCORING_DONE（含评分结果）
  → WRITER_START（第1轮）
    → BULLET_GENERATED {index: 1, text: "..."}  ← 新增！每个 bullet 写完就推
    → BULLET_GENERATED {index: 2, text: "..."}
    → BULLET_GENERATED {index: 3, text: "..."}
  → WRITER_DONE
  → CRITIC_START
    → TOOL_CALLED {tool: "checkClaim", result: "一致"}  ← 新增！Tool 调用也推
    → TOOL_CALLED {tool: "checkTechStack", result: "新增技术..."}
  → CRITIC_DONE
→ COMPLETE
```

**StreamEvent.Type 新增：**
```java
BULLET_GENERATED,   // data = {index: int, text: String}
TOOL_CALLED,        // data = {toolName: String, arguments: String, result: String}
HEARTBEAT           // message = ""，纯保活
```

**挑战：** Writer Agent 目前是一次性调用返回完整 `WriterDraft`。要逐 bullet 推送，有两种方式：
- **方式 A（推荐）：** 改 Writer Agent 的 system message，让它对每个项目经历分别调用一次 `rewrite()`，这样就可以在每次完成后推送
- **方式 B（终极）：** 使用 LangChain4j 的 `TokenStream` API，让 `rewrite()` 返回 `TokenStream`，然后逐 token 推送

### 4.3 R4：中文输出约束（最小改动）

**Writer Agent system message 增加一行：**
```
5. 所有输出必须使用中文。技术名词（如 Redis、QPS、RocketMQ）可保留英文原名，
   但所有描述、动词、句式必须使用中文。严禁整段或整句输出英文。
```

### 4.4 R5：SSE 心跳

**Controller 层改造：**
```java
// 在异步线程中启动一个定时器，每 5 秒发心跳
ScheduledExecutorService heartbeat = Executors.newSingleThreadScheduledExecutor();
heartbeat.scheduleAtFixedRate(() -> {
    try { emitter.send(SseEmitter.event().comment("heartbeat")); }
    catch (IOException e) { heartbeat.shutdown(); }
}, 5, 5, TimeUnit.SECONDS);
```

## 5. 改造优先级与分期规划

一次全改工作量太大，而且容易引入新 bug。建议分三期：

### 第一期：止血（最小改动，立即提升体验）

| 优先级 | 改造项 | 工作量 | 影响 |
|--------|-------|--------|------|
| P0 | R4: Writer Agent 加中文约束 | 1 行 system message | 直接解决英文输出问题 |
| P0 | R5: SSE 心跳 | Controller 加 5 行 | 防止连接静默超时 |
| P1 | R3-逐bullet: 每个项目经历单独调 rewrite() | Service 层改 for 循环 | 改写阶段不再一次性等几十秒 |
| P1 | 前端流式事件渲染粒度跟随 R3 | 新增 BULLET_GENERATED case | 用户看到 bullet 逐个出现 |

### 第二期：完整简历（解决 R1+R2）

| 优先级 | 改造项 | 工作量 |
|--------|-------|--------|
| P1 | 简历结构解析器（简单的正则/关键词分段） | 新增工具类 |
| P1 | Service.optimizeFullResume() | 新增方法 |
| P1 | OptimizationReport 新增 finalResumeText 字段 | 修改 model |
| P2 | 前端输入框改名为"完整简历"，去掉 3000 字符限制 | 修改 index.html |
| P2 | 前端新增"复制完整简历"按钮 | 修改 index.html |

### 第三期：终极流式（R3-逐token）

| 优先级 | 改造项 | 工作量 |
|--------|-------|--------|
| P3 | Writer Agent 返回 TokenStream | 改 Agent 接口 |
| P3 | Service 逐 token 消费并推送 BULLET_TOKEN 事件 | Service 逻辑改造 |
| P3 | 前端打字机效果渲染 | 前端新增动画逻辑 |

```
当前限制（第一期）：输出仍是 bullet points，
用户需要手动复制后粘贴回自己的简历。
```

## 7. 总结：你现在应该做什么

你的混乱来源于"做了技术但没有定义产品"。这不是你的问题——这是所有从个人项目转向"面向用户的工具"时都会遇到的坎。

**核心认知转变：**

> 以前：我有什么技术 → 我能做出什么功能
> 现在：用户需要什么体验 → 我该用什么技术支撑这个体验
