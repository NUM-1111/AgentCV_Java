## 一、设计决策：为什么是阶段级推送而不是逐字流式？

### 产品决策

简历优化不是对话产品——用户不需要看"逐字打字"的 AI 输出效果。三个阶段的进度（评分→改写→审查）已经足够给用户明确的心理预期。

### 技术现实

当前管线是三个 Agent **串行调用**——每次 Agent 调用是阻塞的（等 LLM 完整返回后才能进入下一阶段），天然按阶段分段。如果要做逐字流式，需要把每个 Agent 调用都改成 Streaming 模式——LangChain4j 支持但当前 ROI 不高。

> "这是一个有意识的产品决策，不是技术做不到。产品层面：简历优化不是对话产品，用户不需要逐字效果。技术层面：三阶段管线天然分段，逐字流式需要改造 Agent 调用为 Streaming 模式——技术上可行但当前阶段 ROI 不高。"

---

## 二、SSE vs WebSocket 的选型理由

| 技术 | 适用场景 | 为什么不用 |
|------|---------|-----------|
| SSE | 单向推送（服务端→客户端） | ✅ 正好匹配——我们只需要推进度 |
| WebSocket | 双向实时通信 | ❌ 过重——不需要客户端发消息到服务端 |
| 轮询 | 简单场景 | ❌ 无效请求多，60-120s 管线耗时会大量浪费 |

> "SSE 比 WebSocket 轻量——这里是单向推送不需要双向通信。SSE 直接用 HTTP 协议，无额外连接开销。超时设了 2 分钟，每 10 秒发一次 heartbeat 防浏览器/代理断开。"

---

## 三、heartbeat 的必要性

管线耗时 60-120 秒，如果在两次阶段事件之间有长时间静默（如 Writer 调用 LLM 需要 20-40 秒），浏览器或中间代理可能认为连接已死而断开 SSE。

每 10 秒发一次 `SseEmitter.event().comment("heartbeat")` 保持连接活跃。完成后 `heartbeat.shutdown()` 释放定时器。

---

## 四、前端对接（AI 辅助跨端实践）

前端 SSE 对接借助 Claude Code 完成——这是一个**后端深耕但能跨端排查**的案例：

- SSE 连接：`EventSource` 监听 `/api/v1/resume/optimize/stream`
- 事件类型：`SCORING_START` → `WRITER_DONE` → `CRITIC_DONE` → `COMPLETE` → `ERROR`
- 进度条 UI：三阶段百分比 + 当前阶段标签
- 错误处理：`EventSource.onerror` 自动重连（最多3次，指数退避）
- 完成后：`📋 复制完整简历`（`navigator.clipboard.writeText()`）+ `📥 导出 MD`（Blob 下载）
