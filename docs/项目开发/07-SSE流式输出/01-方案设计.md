## 问题 1：现有架构长什么样？（约束边界）

```
┌─ 前端 index.html ─────────────────────────────┐
│  fetch('/api/v1/resume/...') → await res.json()│
│  问题：等 15-75 秒，白屏，一次性返回全部结果      │
└──────────────────┬─────────────────────────────┘
                   │ HTTP POST (同步等待)
                   ▼
┌─ Controller 层 ────────────────────────────────┐
│  ResumeController.score()       → scoreResult  │
│  ResumeController.optimize()    → OptimizationReport │
│  全部是普通 @PostMapping，返回 POJO              │
└──────────────────┬─────────────────────────────┘
                   │
                   ▼
┌─ Service 层 ───────────────────────────────────┐
│  ResumeOptimizationService                      │
│    scoreOnly(jd, cv)                            │
│      → scoringAgent.score() → ScoreResult       │
│      全程同步，~15s                              │
│                                                  │
│    optimize(jd, cv)                              │
│      Phase 1: scoringAgent.score()    // ~15s     │
│      Phase 2+3: Actor-Critic 循环               │
│        for (round 0..2):                         │
│          writerAgent.rewrite()       // ~10s     │
│          criticAgent.check()         // ~5s      │
│          if approved → return                    │
│      全程同步，30-75s                             │
│      外部完全不知道内部发生了什么                  │
└─────────────────────────────────────────────────┘
```

从架构图可以提取出 **5 个核心约束**，它们决定了我们"能改什么"和"必须改什么"：

| 编号 | 约束内容 | 影响 |
|------|---------|------|
| C1 | Service 的三阶段管线是同步方法，内部没有"事件发射"机制——`optimize()` 返回前，外部零感知 | 要想实现"逐步推送"，必须在 Service 内部增加事件回调 |
| C2 | Controller 返回的是 `ResponseEntity<POJO>`，Spring MVC 在方法返回前不写响应体 | 需要换成 `SseEmitter`（Spring 原生的 SSE 支持），让 Controller 能在处理过程中多次写数据 |
| C3 | 前端使用 `fetch().then(res.json())`，等全部数据到了才渲染 | 需要改为 `ReadableStream` 逐块读取 SSE 事件 |
| C4 | Agent（Writer/Critic/Scoring）和工具类（TokenEstimator/TextTrimmer）是稳定的业务核心，不应该为传输层改动而修改 | 隔离"业务逻辑"和"传输方式" |
| C5 | 现有 2 个同步端点（`/score`、`/optimize`）已被前端使用，不能破坏 | 新端点独立新增，旧端点保持原样 |

## 问题 2：从约束到变更——为什么改这些文件？

下面逐一推导：**每个约束对应什么变更，以及为什么。**

### C1 → Service 层增加事件回调

**约束：** `optimize()` 是同步方法，没有"中间通知"机制。

**推理：**
- 要推送进度，Service 必须在每个阶段完成时通知外部。最轻量的方式是**回调函数**——Service 每走完一个阶段，调用一次回调。
- 回调的参数不能只是字符串，否则前端无法区分"这是 Phase 1 评分结果"还是"Phase 2 改写草稿"。需要一个**事件类型枚举 + 结构化数据载体**。

**结论：**
- **新增** `StreamEvent` 记录（`Type` 枚举 + `message` + `data` 载体）——这是 Service 和 Controller 之间的"合同"
- **修改** `ResumeOptimizationService`，新增 `optimizeStreaming(jd, cv, Consumer<StreamEvent>)`，内部逻辑与 `optimize()` 共享 Actor-Critic 核心循环，但每一步通过回调推送事件

### C2 → Controller 层增加 SSE 端点

**约束：** 普通 `@PostMapping` 必须在方法返回后才写响应，无法逐步推送。

**推理：**
- Spring 提供 `SseEmitter`，允许在异步线程中多次调用 `emitter.send()`，浏览器通过 `text/event-stream` 协议逐条接收事件。
- Controller 的职责是把 Service 发出的 `StreamEvent` 翻译成 SSE 格式——这保持了"Service 不依赖 SSE API"的设计原则（C4）。

**结论：**
- **修改** `ResumeController`，新增 `POST /api/v1/resume/optimize/stream` 端点，使用 `SseEmitter` + 单线程池异步执行

### C3 → 前端增加 SSE 消费逻辑

**约束：** 现有 `fetch().then(res.json())` 等全部数据到了才渲染。

**推理：**
- SSE 需要前端用 `res.body.getReader()` 按 chunk 读取，解析 `event:` 和 `data:` 字段，然后根据事件类型逐步渲染。
- 需要一个新按钮触发流式端点，与现有的"同步优化"按钮并存。

**结论：**
- **修改** `index.html`，新增"⚡ 流式优化"按钮 + `ReadableStream` SSE 解析 + 按事件类型分段渲染

### C4 → Agent 层不动

**约束：** Agent 是稳定的业务核心，不应为传输层改动。

**推理：**
- `ResumeWriterAgent.rewrite()` 的输入输出完全不变，只是调用方从 `optimize()` 变成 `optimizeStreaming()`。
- `FactCriticAgent.check()` 同理。
- 这验证了设计的正确性：**传输层变化不影响业务核心**。

**结论：** Agent 层零改动。

### C5 → 旧端点不动

**约束：** 现有同步端点已被使用，不能破坏。

**结论：** `/score` 和 `/optimize` 保持原样，不做任何修改。

## 问题 3：有哪些可行的设计方案？

### 方案 A：Consumer\<String\> 回调

```java
public void optimizeStreaming(String jd, String cv, Consumer<String> onEvent) {
    onEvent.accept("正在分析 JD…");
    ScoreResult score = scoringAgent.score(jd, cv);
    onEvent.accept(serializeScore(score));
    // ...
}
```

| 维度 | 评价 |
|------|------|
| 优点 | 改动量最小，Service 核心逻辑不重复 |
| 缺点 | 前端只能拿到字符串，无法区分"进度提示"和"结果数据"——比如"评分完成"和草稿内容混在一起，前端需要自己做字符串解析 |
| 结论 | ⚠️ 能跑，但前后端耦合在字符串格式上，不优雅 |

### 方案 B：Consumer\<StreamEvent\> 事件类型化回调

```java
public void optimizeStreaming(String jd, String cv, Consumer<StreamEvent> onEvent) {
    onEvent.accept(StreamEvent.of(SCORING_START, "正在分析 JD…"));
    ScoreResult score = scoringAgent.score(jd, cv);
    onEvent.accept(StreamEvent.of(SCORING_DONE, "评分完成", score));

    for (int round = 0; round < maxRounds; round++) {
        onEvent.accept(StreamEvent.of(WRITER_START, "第"+(round+1)+"轮改写…"));
        WriterDraft draft = writerAgent.rewrite(jd, cv, feedback);
        onEvent.accept(StreamEvent.of(WRITER_DONE, "草稿完成", draft));

        onEvent.accept(StreamEvent.of(CRITIC_START, "Critic 审查中…"));
        CriticReport c = criticAgent.check(cv, formatBullets(draft));
        boolean passed = c.approved() || maxSeverity(c) <= 2;
        onEvent.accept(StreamEvent.of(CRITIC_DONE,
            passed ? "审查通过" : "发现"+c.violations().size()+"条违规", c));

        if (passed) {
            onEvent.accept(StreamEvent.of(COMPLETE, "完成", finalReport));
            return;
        }
        feedback = c.feedback();
    }
}
```

| 维度 | 评价 |
|------|------|
| 优点 | 前端按事件类型精准渲染——SCORING_DONE 展示分数卡片，WRITER_DONE 展示改写预览，CRITIC_DONE 展示审查结果 |
| 缺点 | 需要在 Service 层定义 `StreamEvent` 类型（但这是纯 POJO，不依赖任何框架） |
| **结论** | **✅ 最优解**。为什么？因为 `StreamEvent` 是 Service 和 Controller 之间的"合同"——Service 说"我发出 SCORING_DONE，数据类型是 ScoreResult"，Controller 负责把它翻译成 SSE 的 `event:` + `data:` 格式。想知道推到哪一步？看事件类型就行 |

### 方案 C：Service 不动，Controller 层模拟进度

```java
@PostMapping(value = "/optimize/stream", produces = TEXT_EVENT_STREAM)
public SseEmitter stream(@RequestBody OptimizeRequest req) {
    SseEmitter emitter = new SseEmitter(120_000L);
    executor.execute(() -> {
        emitter.send(event("progress", "正在优化…"));
        OptimizationReport report = service.optimize(req.jdText(), req.cvText()); // 还是同步等
        emitter.send(event("result", report));
        emitter.complete();
    });
    return emitter;
}
```

| 维度 | 评价 |
|------|------|
| 优点 | Service 一行不改 |
| **致命问题** | 只能发"开始"和"结束"，中间 60 秒连接静默——没利用 SSE 的核心价值（逐步推送）。本质和 HTTP 传统传输没区别 |
| 结论 | ❌ 伪流式，不符合需求 |

## 问题 4：方案选择

**选定方案 B：`Consumer<StreamEvent>` 回调 + 事件类型枚举**

### 选择理由

| 理由 | 解释 |
|------|------|
| Service 核心逻辑不重复 | `optimizeStreaming()` 和 `optimize()` 共享相同的 Actor-Critic 决策逻辑，只多了一层回调 |
| 调用方不依赖传输协议 | `StreamEvent` 是纯 POJO，Service 不需要知道 `SseEmitter` 的存在——Controller 负责把事件翻译成 SSE 格式。哪天换 WebSocket，只改 Controller |
| 前端能精准渲染 | 事件类型决定渲染方式——`SCORING_DONE` 展示评分卡片，`WRITER_DONE` 展示改写预览，`CRITIC_DONE` 展示审查状态，`COMPLETE` 展示最终结果 |
| 可测试 | `StreamEvent` 是值对象，可以直接在单元测试中断言事件序列 |

### 事件流时序

```
SCORING_START  → "正在分析 JD 并评估匹配度…"
SCORING_DONE   → {data: {scoreResult: {matchScore: 82, matchedSkills: [...], missingSkills: [...]}}}
WRITER_START   → "第 1 轮改写…"
WRITER_DONE    → {data: {rewrittenBulletPoints: ["1. 主导订单系统...", ...]}}
CRITIC_START   → "Critic 审查中…"
CRITIC_DONE    → "审查通过" / "发现 N 条违规"
COMPLETE       → {data: {完整 OptimizationReport}}
```
