## 1. 问题背景：模型输出的 JSON 到底有多不靠谱？

### 1.1 三层不稳定问题（+ ⚠️ 第 0 层：框架层 Gson 盲区）

> **🆕 2026-07-17 端到端验证发现**：在四层防御 Pipeline 之前，还存在一个"第 0 层"盲区——**LangChain4j 的结构化输出底层使用 Gson（严格模式）做第一次解析**。LLM 返回的 JSON 中如果 `detail` 字段包含未转义双引号、或 `bulletPoints` 数组元素含未转义字符，Gson 直接抛 `MalformedJsonException`，此时四层防御 Pipeline 根本没机会执行。

LLM 输出的 JSON 不是标准的 API 返回值，而是**概率生成**的文本。在调用 `MatchEvaluatorService.evaluate()` 之后，`ObjectMapper.readValue()` 之前，面临三层不稳定 + 一个框架层盲区：

| 层级 | 问题 | 示例 |
|------|------|------|
| **① 结构污染** | JSON 被 Markdown 包裹、前后有噪声文本 | `好的，这是分析结果：\n```json\n{"matchScore":85}\n```\n希望对你有所帮助！` |
| **② 语法违规** | JSON 带了注释、尾逗号、单引号 | `{"matchScore":85, /* 评分 */ "matchedSkills": ['Java', 'Spring'],}` |
| **③ 字段漂移** | 字段名不按约定走 | `match_score` / `MatchedSkills` / `skill_gaps` / `matched-skills` |

### 1.2 为什么不能只靠 Prompt 约束？

面试官可能会问：「你在 Prompt 里写清楚"请输出标准 JSON 格式"不就行了？」

**回答**：
> 「Prompt 约束是软性的——模型在生成质量 vs 格式严格之间，会优先满足生成质量目标。而且不同模型、同一模型的不同温度参数、甚至同一请求的不同 token 采样路径，都会导致格式不一致。工程上必须假设**模型输出不可靠**，在输入端做多层防御。」

## 2. 四层 Pipeline 全景

```
matchEvaluatorService.evaluate(jd, resume)
  │
  │  返回: raw（原始字符串，可能包含 Markdown / 噪声 / 注释 / 尾逗号 / 字段漂移）
  │
  │  ┌─────────────────── 第一层：extractJsonObject ──────────────────────┐
  │  │  正则匹配第一个 { 和最后一个 }，提取纯 JSON 主体                      │
  │  │  "好的，分析结果如下：\n```json\n{...}\n```" → "{...}"              │
  │  └────────────────────────────────────────────────────────────────────┘
  │
  │  ┌─────────────────── 第二层：FieldNameNormalizer ────────────────────┐
  │  │  正则归一化字段名，覆盖 @JsonAlias 范围外的未知变体                    │
  │  │  "match_score" → "matchScore"                                      │
  │  │  "skill_gaps"  → "missingSkills"                                   │
  │  └────────────────────────────────────────────────────────────────────┘
  │
  │  ┌─────────────────── 第三层：Jackson 宽松解析 + @JsonAlias ──────────┐
  │  │  ALLOW_COMMENTS / ALLOW_TRAILING_COMMA / ALLOW_SINGLE_QUOTES      │
  │  │  FAIL_ON_UNKNOWN_PROPERTIES = false                                │
  │  │  @JsonAlias({"match_score", "score"}) → 精确兜底                    │
  │  │  输出: MatchReport 对象（已反序列化，但字段值可能不合法）              │
  │  └────────────────────────────────────────────────────────────────────┘
  │
  │  ┌─────────────────── 第四层：Bean Validation ────────────────────────┐
  │  │  @Min(0) @Max(100) matchScore → 拦截 matchScore=150               │
  │  │  @NotNull matchedSkills → 拦截 null 列表                           │
  │  │  @NotBlank improvementAdvice → 拦截空字符串                         │
  │  │  不通过 → 抛出 AiOutputValidationException                         │
  │  └────────────────────────────────────────────────────────────────────┘
  │
  └─→ return MatchReport（四层校验通过，数据合法）
```

## 3. 第一层：extractJsonObject — 剥离 Markdown 包裹

### 3.1 代码

```java
// MatchEvaluationFacadeService.java 第 94-104 行
private String extractJsonObject(String raw) {
    if (raw == null) {
        return "{}";
    }
    int start = raw.indexOf('{');
    int end = raw.lastIndexOf('}');
    if (start >= 0 && end > start) {
        return raw.substring(start, end + 1);
    }
    return raw;
}
```

### 3.2 处理的各种情况

| 输入 | 处理结果 |
|------|---------|
| `这是分析结果：\n```json\n{"matchScore":85}\n```\n以上。` | `{"matchScore":85}` |
| `{"matchScore":85}` | `{"matchScore":85}`（不变） |
| `null` | `{}`（空对象兜底，后续 Bean Validation 会拦截） |
| `没有匹配到任何结果` | `没有匹配到任何结果`（原样返回，后续 Jackson 解析会抛异常 → GlobalExceptionHandler 兜底） |

### 3.3 设计要点

**面试话术**：
> 「这一层极简但有深度。用 `indexOf('{')` 和 `lastIndexOf('}')` 而不是复杂的正则，因为模型可能在 JSON 内部嵌套写 `{` 比如 `"description":"使用{placeholder}"`——但 JSON 的最外层花括号就是第一个 `{` 和最后一个 `}`。不需要解析嵌套，只需要找到最外层。」

**为什么不用 Markdown 代码块解析库？**
> 「不需要。模型可能用 ` ```json ` 包裹，也可能用 ` ``` ` 包裹，也可能什么都不加。最简单的策略就是找最外层花括号——永远正确，零依赖。」

## 4. 第二层：FieldNameNormalizer — 覆盖未知变体

### 4.1 为什么需要这一层？@JsonAlias 不够吗？

`@JsonAlias` 是精确匹配——你必须提前知道所有可能的变体：

```java
@JsonAlias({"match_score", "score"})  // 知道这两个变体
int matchScore;
```

但模型可能输出：
- `MatchScore`（首字母大写）
- `match-score`（连字符分隔）
- `MATCH_SCORE`（全大写）
- `Match_Score`（混合大小写）

每发现一个新变体就去加 `@JsonAlias` 是**打地鼠**。

### 4.2 规则表

```java
// FieldNameNormalizer.java 第 40-65 行
private static final List<NormalizeRule> RULES = List.of(
    
    // matchScore：覆盖 match_score / matchscore / match score / MatchScore 等
    new NormalizeRule(
        Pattern.compile("(?i)\"(match[_\\s]?score|matchscore)\"\\s*:"),
        "\"matchScore\":"
    ),
    
    // matchedSkills：覆盖 matched_skills / matchedskills / skills_matched 等
    new NormalizeRule(
        Pattern.compile("(?i)\"(matched[_\\s]?skills?|skills?[_\\s]?matched|matchedskills?)\"\\s*:"),
        "\"matchedSkills\":"
    ),
    
    // missingSkills：覆盖 missing_skills / skill_gaps / gaps 等
    new NormalizeRule(
        Pattern.compile("(?i)\"(missing[_\\s]?skills?|missingskills?|skill[_\\s]?gaps?|gaps?|missing[_\\s]?requirements?)\"\\s*:"),
        "\"missingSkills\":"
    ),
    
    // improvementAdvice：覆盖 improvement_advice / improvement / suggestion / advice 等
    new NormalizeRule(
        Pattern.compile("(?i)\"(improvement[_\\s]?advice|improvementadvice|advice[_\\s]?texts?|suggestions?|improvements?)\"\\s*:"),
        "\"improvementAdvice\":"
    )
);
```

### 4.3 每条规则的正则设计细节

以 `matchScore` 规则为例：

```java
Pattern.compile("(?i)\"(match[_\\s]?score|matchscore)\"\\s*:")
```

| 部分 | 含义 | 匹配示例 |
|------|------|---------|
| `(?i)` | 大小写不敏感 | `MatchScore`, `MATCHSCORE`, `matchscore` |
| `"` | 匹配开头的双引号 | 确保只匹配 JSON key，不误改 value 中的普通文本 |
| `match[_\\s]?` | "match" 后可选 `_` 或空格 | `match_score`, `match score` |
| `score` | 固定部分 | — |
| `\|matchscore` | 也匹配无分隔符变体 | `matchscore` |
| `"` | 匹配结尾的双引号 | — |
| `\\s*:` | 空白 + 冒号 | — |
| **替换为** | `"matchScore":` | 标准 camelCase |

**面试话术**：
> 「每条规则覆盖 5~8 种变体。核心设计原则是：用 `[_\s]?` 匹配有无分隔符、用 `(?i)` 匹配大小写、用语义相近词（gaps / suggestion）纳入同一规则。总共 4 个字段 × 5~8 个变体 = 约 25+ 种漂移场景被覆盖。」

### 4.4 为什么用正则改字符串而不是解析成 JsonNode？

```java
// FieldNameNormalizer.java 第 7-11 行的注释直接说明了原因
/**
 * 为什么在反序列化之前用正则处理，而不是解析成 JsonNode 再改 key？
 * 因为此时 JSON 可能还带有注释、单引号、尾逗号等非标准语法，
 * Jackson 尚未介入，正则直接操作字符串不依赖 JSON 合法性，能更早拦截漂移。
 */
```

**面试话术**：
> 「按常理，修改 JSON key 应该先解析成 JsonNode 再改。但 FieldNameNormalizer 在 Jackson 之前执行——此时 JSON 可能还有注释、尾逗号、单引号，Jackson 还没消化这些非标准语法。直接正则改字符串不依赖 JSON 合法性，能更早介入。」

## 5. 第三层：Jackson 宽松解析 + @JsonAlias

### 5.1 JacksonConfig：四个宽松开关

```java
// JacksonConfig.java
@Bean @Primary
public ObjectMapper objectMapper() {
    return JsonMapper.builder()
            .enable(JsonReadFeature.ALLOW_JAVA_COMMENTS)      // 允许 // 和 /* */
            .enable(JsonReadFeature.ALLOW_YAML_COMMENTS)      // 允许 #
            .enable(JsonReadFeature.ALLOW_TRAILING_COMMA)     // 允许尾逗号
            .enable(JsonReadFeature.ALLOW_SINGLE_QUOTES)      // 允许单引号
            .disable(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES) // 忽略未知字段
            .build();
}
```

| 开关 | 解决的问题 | 输入示例 |
|------|-----------|---------|
| `ALLOW_JAVA_COMMENTS` | JSON 含 `// 注释` 或 `/* 注释 */` | `{"matchScore": 85 /* 评分 */}` |
| `ALLOW_YAML_COMMENTS` | JSON 含 `# 注释` | `{"matchScore": 85 # 匹配分数}` |
| `ALLOW_TRAILING_COMMA` | JSON 数组/对象末尾多余逗号 | `{"matchScore": 85, "skills": ["Java",],}` |
| `ALLOW_SINGLE_QUOTES` | 字段/值用了单引号 | `{'matchScore': 85, 'skills': ['Java']}` |
| `FAIL_ON_UNKNOWN_PROPERTIES=false` | 模型多输出了额外字段 | `{"matchScore": 85, "_thought": "这个候选人不匹配"}` |

**面试话术**：
> 「Jackson 默认是严格的 JSON 解析器——注释、尾逗号、单引号全部报错。我开了四个宽松开关，让 Jackson 在**容错模式**下工作。第五个开关 `FAIL_ON_UNKNOWN_PROPERTIES=false` 特别重要——模型经常输出 `_thought`、`reasoning` 这类字段，忽略它们而不是抛异常。」

**面试官追问**：「这些开关有什么风险？」

> 「唯一的风险是把**真正的格式错误**也吞掉了。比如模型输出了一个语法完全混乱的 JSON，宽松解析可能产生一个"部分字段有值、部分字段为 null"的对象——此时 Bean Validation 会兜底拦截（比如 `@NotNull matchedSkills` 会检测到 null）。所以风险是可控的。」

### 5.2 @JsonAlias：精确兜底

```java
// MatchReport.java
@JsonAlias({"match_score", "score"})
int matchScore;

@JsonAlias({"matched_skills"})
List<String> matchedSkills;

@JsonAlias({"missing_skills"})
List<String> missingSkills;

@JsonAlias({"improvement_advice", "advice"})
String improvementAdvice;
```

| 分工 | FieldNameNormalizer | @JsonAlias |
|------|--------------------|-----------|
| **处理时机** | JSON 字符串 → 反序列化之前 | 反序列化过程中 |
| **匹配方式** | 正则模糊匹配 | 精确字符串匹配 |
| **覆盖范围** | 未知变体（5~8种/字段） | 已知变体（2~3个/字段） |
| **定位** | 兜未知 | 兜已知 |

**面试话术**：
> 「两者是互补关系。FieldNameNormalizer 是正则模糊归一化——`matched_skills`、`MatchedSkills`、`matched-skills` 全转成 `matchedSkills`，覆盖我不知道的变体。@JsonAlias 是精确兜底——`score` 这个别名必须显式声明。先模糊归一化，后精确兜底，双层防护。」

## 6. 第四层：Bean Validation — 字段值合法性校验

### 6.1 校验注解

```java
// MatchReport.java
public record MatchReport(
    @Min(0) @Max(100)                    // matchScore 必须在 0~100
    @Description("0-100分的整数...") 
    int matchScore,

    @NotNull(message = "matchedSkills 不能为空")   // 列表不能为 null
    List<String> matchedSkills,

    @NotNull(message = "missingSkills 不能为空")
    List<String> missingSkills,

    @NotBlank(message = "improvementAdvice 不能为空白")  // 字符串不能为空/空白
    String improvementAdvice
) {}
```

### 6.2 校验执行

```java
// MatchEvaluationFacadeService.java 第 83-92 行
private void validateReport(MatchReport report) {
    Set<ConstraintViolation<MatchReport>> violations = validator.validate(report);
    if (violations.isEmpty()) {
        return;
    }
    String detail = violations.stream()
            .map(v -> v.getPropertyPath() + " " + v.getMessage())
            .collect(Collectors.joining("; "));
    throw new AiOutputValidationException("模型输出字段校验失败: " + detail);
}
```

### 6.3 实际拦截过的问题

| 校验注解 | 拦截情况 | 如果不拦截会怎样 |
|---------|---------|----------------|
| `@Min(0) @Max(100)` | 模型输出 `matchScore: 150` | 下游服务拿到超限分数，误以为候选人格外匹配 |
| `@Min(0) @Max(100)` | 模型输出 `matchScore: -10` | 负数评分进入数据库，统计偏差 |
| `@NotNull matchedSkills` | 模型忘记输出 skills 字段 | NPE 崩溃或空列表污染下游 |
| `@NotBlank improvementAdvice` | 模型输出 `"improvementAdvice": ""` | 前端展示空建议，用户困惑 |

**面试话术**：
> 「Bean Validation 是最后一道防线。前三层确保 JSON 能成功反序列化，但反序列化成功≠数据合法。模型输出 `matchScore: 150` 能被解析成 `int`，但不该进入业务逻辑——@Min/@Max 在字段级别拦截这种脏数据，抛 `AiOutputValidationException` → 500 返回给前端，而不是静默进入下游。」

### 6.4 异常传递链

```
Bean Validation 失败
  → throw AiOutputValidationException("matchScore 必须在0到100之间")
      → GlobalExceptionHandler.handleAiOutputValidationException()
          → 返回 HTTP 500 + ApiError(500, "AI 分析引擎暂时开小差了...详情: matchScore 必须在0到100之间")
```

**面试话术**：
> 「AiOutputValidationException 返回 500 而不是 400。因为这是服务端的问题——模型输出了不合法的数据，不是用户的输入有问题。用户对此无能为力，所以提示用户'请稍后重试'。」

## 7. 全局异常兜底：最外层防线

```java
// GlobalExceptionHandler.java
@ExceptionHandler(IllegalArgumentException.class)
public ResponseEntity<ApiError> handleIllegalArgument(IllegalArgumentException ex) {
    return ResponseEntity.status(HttpStatus.BAD_REQUEST)  // 400：用户问题
            .body(new ApiError(400, ex.getMessage()));
}

@ExceptionHandler(AiOutputValidationException.class)
public ResponseEntity<ApiError> handleAiOutputValidationException(AiOutputValidationException ex) {
    return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR)  // 500：模型问题
            .body(new ApiError(500, "AI 分析引擎暂时开小差了...详情: " + ex.getMessage()));
}

@ExceptionHandler(Exception.class)
public ResponseEntity<ApiError> handleException(Exception ex) {
    return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR)  // 500：未知兜底
            .body(new ApiError(500, "AI 分析引擎暂时开小差了...详情: " + ...));
}
```

**三个异常映射的语义差异**：

| 异常 | HTTP 状态码 | 语义 |
|------|-----------|------|
| `IllegalArgumentException` | 400 | 用户输入有问题（JD/简历为空、过长），用户可自行修正 |
| `AiOutputValidationException` | 500 | 模型输出不合法（matchScore=150），用户无能为力，服务端问题 |
| `Exception`（兜底） | 500 | 未知问题，记录 ERROR 日志，返回统一提示 |

## 8. 四层 Pipeline 的容错设计思想

### 8.1 为什么是"宽松解析 → 严格校验"的顺序？

| 阶段 | 策略 | 原因 |
|------|------|------|
| extractJsonObject | 宽松（只找花括号） | 模型输出格式多变，不能假设它有固定结构 |
| FieldNameNormalizer | 模糊（正则归一化） | 字段名漂移的变体数量不可预测 |
| Jackson 解析 | 宽松（4 个开关） | 允许非标准 JSON 语法 |
| Bean Validation | **严格**（字段级约束） | 数据进入业务逻辑前的最后防线 |

**面试话术**：
> 「前三级是"尽可能让数据进来"——容忍格式差异、字段名漂移。最后一级是"进来之后严格审查"——不合法的值直接拦截。这个设计哲学的根源是：LLM 输出的**格式不可控**但**语义通常正确**，所以格式层要宽进，业务层要严出。」

## 9. 面试高频追问防御话术

### Q1：「FieldNameNormalizer 和 @JsonAlias 有什么区别？为什么不只用其中一个？」

**三层回答**：
1. 「@JsonAlias 是精确匹配——你必须提前知道所有可能的别名，比如 `@JsonAlias({"match_score", "score"})`。FieldNameNormalizer 是规则归一化——用正则覆盖未知变体，比如 `MatchScore`、`MATCH_SCORE`、`match-score` 不需要逐个声明。」
2. 「两者的执行时机不同：FieldNameNormalizer 在 JSON 字符串级别、Jackson 介入之前执行——此时文本可能还有注释和尾逗号，正则直接改字符串不依赖 JSON 合法性。」
3. 「如果只用 @JsonAlias，每发现一个新变体就要改代码重新部署——这是打地鼠。FieldNameNormalizer 用正则规则覆盖了 25+ 种漂移，大幅降低维护成本。」

### Q2：「如果模型输出的 JSON 根本没有 matchScore 字段，怎么处理？」

**三层回答**：
1. 「Jackson 反序列化时，缺失的字段会赋默认值（`int` → `0`，`List` → `null`）。」
2. 「如果 `matchScore` 缺失，默认值为 `0`，虽然通过了 `@Min(0)`，但业务上评分 0 显然不对。如果 `matchedSkills` 缺失，默认值为 `null`，`@NotNull` 校验会立即拦截。」
3. 「如果需要更精确的检测，可以在 Bean Validation 后加一层业务逻辑校验——比如 `matchScore == 0` 时打 WARN 日志并返回'模型输出异常'——但 MVP 阶段 Bean Validation 已经拦截了最严重的问题（null、空字符串、超限值）。」

### Q3：「extractJsonObject 用 indexOf 找花括号，如果 JSON 内部也有花括号怎么办？」

**回答**：
> 「不影响。`indexOf('{')` 找的是字符串里**第一个** `{`——那一定是 JSON 的最外层起始花括号。`lastIndexOf('}')` 找的是**最后一个** `}`——那一定是 JSON 的最外层结束花括号。JSON 内部的嵌套花括号（比如 `"pattern": "{placeholder}"`）在字符串中间，不会被这两个端点匹配到。这在 JSON 语法上是恒成立的——不需要解析嵌套。」

### Q4：「Jackson 的四个宽松开关有什么风险？」

**回答**：
> 「唯一的风险是把真正的语法错误也吞掉。比如模型输出了一个完全混乱的 JSON——宽松解析可能产生部分字段为 null、部分字段为默认值的对象。此时 Bean Validation 的 `@NotNull` 和 `@NotBlank` 会兜底拦截，所以风险可控。如果关闭开关用严格解析，每次模型多写一个注释就抛异常，成功率会从 99% 掉到 70% 以下。」
