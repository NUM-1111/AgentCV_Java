# 问题三：解析成功但业务无效（静默错误）

## 问题是什么

JSON 反序列化成功，接口返回 HTTP 200，但 `MatchReport` 里的字段值不合法：

- `matchScore = 0`（模型输出了 `matchScore` 字段但值为 `0.8`，被解析成整数 `0`）
- `matchedSkills = null`（字段漂移导致映射失败，默认值为 `null`）
- `improvementAdvice = "   "`（模型输出了空白字符串）
- `missingSkills = null`（模型漏输出该字段）

这类问题比解析崩溃更危险：接口看起来正常，但业务层拿到的是错误数据，可能产生错误的匹配结论，且没有任何报错信号。

---

## 为什么有这个问题

**1. 反序列化只保证"结构合法"，不保证"业务有效"**

Jackson 的职责是把 JSON 字符串转成 Java 对象，它不知道 `matchScore` 必须在 0-100 之间，也不知道 `improvementAdvice` 不能是空白字符串。只要 JSON 格式合法、类型匹配，它就认为成功了。

**2. 原来的 `MatchReport` 没有任何约束注解**

原始代码里 `MatchReport` 是一个普通 Record，没有 `@Min`、`@Max`、`@NotNull`、`@NotBlank` 等约束：

```java
// 改造前：无任何约束
public record MatchReport(
    int matchScore,
    List<String> matchedSkills,
    List<String> missingSkills,
    String improvementAdvice
) {}
```

字段值是什么就是什么，业务层直接使用，没有任何拦截。

**3. 没有统一的校验触发点**

即使加了约束注解，Spring 的 `@Valid` 只在 Controller 层的请求参数上自动触发。`MatchReport` 是从模型输出解析来的，不经过 Controller 参数绑定，`@Valid` 不会自动生效，需要手动触发校验。

---

## 用什么方法解决

### 第一步：给 `MatchReport` 加字段约束

```java
public record MatchReport(
    @JsonAlias({"match_score", "score"})
    @Min(0) @Max(100)
    int matchScore,

    @JsonAlias({"matched_skills"})
    @NotNull(message = "matchedSkills 不能为空")
    List<String> matchedSkills,

    @JsonAlias({"missing_skills"})
    @NotNull(message = "missingSkills 不能为空")
    List<String> missingSkills,

    @JsonAlias({"improvement_advice", "advice"})
    @NotBlank(message = "improvementAdvice 不能为空白")
    String improvementAdvice
) {}
```

约束语义：
- `matchScore`：必须是 0-100 的整数，超出范围说明模型输出了非法分值
- `matchedSkills`：不能为 null，字段漂移导致映射失败时会被拦截
- `missingSkills`：不能为 null，同上
- `improvementAdvice`：不能是空白字符串，模型输出空建议时会被拦截

### 第二步：在 Facade 层手动触发校验

在 `MatchEvaluationFacadeService` 里，反序列化成功后立即执行 Bean Validation：

```java
private void validateReport(MatchReport report) {
    Set<ConstraintViolation<MatchReport>> violations = validator.validate(report);
    if (violations.isEmpty()) {
        return;
    }
    // 聚合所有违规信息，一次性抛出
    String detail = violations.stream()
            .map(v -> v.getPropertyPath() + " " + v.getMessage())
            .collect(Collectors.joining("; "));
    throw new AiOutputValidationException("模型输出字段校验失败: " + detail);
}
```

`Validator` 通过构造函数注入，由 Spring 管理。

### 第三步：新增专用异常 + 统一异常出口

新增 `AiOutputValidationException`，区分"AI 输出校验失败"和其他异常：

```java
public class AiOutputValidationException extends RuntimeException {
    public AiOutputValidationException(String message) {
        super(message);
    }
}
```

在 `GlobalExceptionHandler` 里统一处理，返回结构化错误：

```java
@ExceptionHandler(AiOutputValidationException.class)
public ResponseEntity<ErrorResponse> handleAiValidation(AiOutputValidationException ex) {
    return ResponseEntity.status(500)
        .body(new ErrorResponse("AI_OUTPUT_INVALID", ex.getMessage()));
}
```

这样前端和调用方拿到的是明确的失败信号，而不是错误的业务值。

## 前后效果对比

| 场景 | 改造前 | 改造后 |
|------|--------|--------|
| `matchScore = 120` | HTTP 200，业务层拿到非法分值 | `AiOutputValidationException`，HTTP 500 明确拦截 |
| `matchedSkills = null` | HTTP 200，业务层 NPE 或空结果 | 校验失败，明确拦截 |
| `improvementAdvice = "   "` | HTTP 200，前端展示空白建议 | 校验失败，明确拦截 |
| 解析失败 | 框架堆栈，无上下文 | `IllegalStateException` 附带原始输出摘要 |
| 校验失败 | 无感知，静默错误 | `AiOutputValidationException` 附带具体字段和原因 |

核心变化：**从"容易 silently wrong"变为"即使异常也能被显式发现并阻断"。**

## 拓展：还有哪些方案

**方案 A：区分解析失败和校验失败的错误码**

当前两类失败都返回 HTTP 500，前端无法区分"模型输出格式错了"和"模型输出值不合法"。可以给 `AiOutputValidationException` 加错误码（如 `AI_OUTPUT_INVALID`），给解析失败加另一个错误码（如 `AI_OUTPUT_PARSE_ERROR`），让前端可以细分处理（比如解析失败时提示"服务暂时不可用"，校验失败时提示"评估结果异常，请重试"）。

**方案 B：列表元素级校验**

当前只校验 `matchedSkills != null`，但列表里可能有空字符串（`["Java", "", "Spring Boot"]`）。可以升级为 `List<@NotBlank String>`，对每个元素做约束。

**方案 C：业务语义校验**

Bean Validation 只能做通用约束（非空、范围），无法做业务语义校验（比如"建议文案至少 20 字"、"技能列表不能超过 20 个"）。可以在 `validateReport` 里加自定义业务规则，在 Bean Validation 之后执行。

**方案 D：解析失败自动重试**

当解析或校验失败时，可以带着"格式纠正提示"重新调用模型（比如"你上次的输出格式不对，请严格按照以下 Schema 重新输出"），最多重试 N 次。这能进一步提升成功率，但会增加延迟和 token 消耗，需要权衡。
