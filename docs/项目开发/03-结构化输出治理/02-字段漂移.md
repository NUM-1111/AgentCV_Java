# 问题二：字段漂移导致静默错误

## 问题是什么

模型返回的 JSON 字段名与后端期望的不一致，但反序列化不报错，字段悄悄变成默认值（`0`、`null`、`""`），业务层以为成功了，实际上拿到的是错误数据。

典型漂移案例：

```json
// 后端期望
{ "matchScore": 78, "matchedSkills": [...], "missingSkills": [...], "improvementAdvice": "..." }

// 模型实际输出（各种变体）
{ "match_score": 78, ... }          // snake_case
{ "score": 78, ... }                // 缩写
{ "MatchScore": 78, ... }           // 首字母大写
{ "matchscore": 78, ... }           // 无分隔符
{ "skills_matched": [...], ... }    // 顺序颠倒
{ "gaps": [...], ... }              // 语义相近词
{ "suggestion": "...", ... }        // 同义词
```

最危险的不是报错，而是"静默错误"：`matchScore` 拿到 `0`，`matchedSkills` 拿到 `null`，接口返回 HTTP 200，但业务结果完全错误。

---

## 为什么有这个问题

**1. 模型对字段命名没有强约束**

模型在训练时见过大量 JSON 数据，`camelCase`、`snake_case`、缩写、同义词都有。即使 Prompt 里指定了字段名，模型仍然有概率"按自己的理解"输出变体，尤其是在上下文较长或多轮对话时。

**2. `@JsonAlias` 是静态枚举，覆盖范围有限**

`@JsonAlias` 只能精确匹配你提前预设的别名：

```java
@JsonAlias({"match_score", "score"})   // 只覆盖这两个
int matchScore,
```

`matchscore`（无下划线）、`MatchScore`（大写）、`MATCH_SCORE`（全大写）都不在列表里，遇到就会静默丢值。每次发现新漂移都要改代码重新部署，是被动防御。

**3. 没有字段级约束，丢值不会报错**

原来的 `MatchReport` 没有 `@NotNull`、`@NotBlank` 等约束，字段变成 `null` 或 `0` 后，后续业务逻辑直接使用，不会有任何报错信号。

---

## 用什么方法解决

### 第一层：`@JsonAlias` 精确兜底（已有）

在 `MatchReport` 上为每个字段声明已知的精确别名：

```java
@JsonAlias({"match_score", "score"})
int matchScore,

@JsonAlias({"matched_skills"})
List<String> matchedSkills,

@JsonAlias({"missing_skills"})
List<String> missingSkills,

@JsonAlias({"improvement_advice", "advice"})
String improvementAdvice
```

这一层处理"已知的、固定的"别名，是 Jackson 层的精确兜底。

### 第二层：`FieldNameNormalizer` 模糊归一化（新增）

新建 `src/main/java/com/jobagent/util/FieldNameNormalizer.java`，在 Jackson 反序列化**之前**，用正则把 JSON 字符串里的 key 统一映射到标准字段名。

**为什么在反序列化之前用正则，而不是解析成 JsonNode 再改 key？**

因为此时 JSON 可能还带有注释、单引号、尾逗号等非标准语法，Jackson 还没处理，不能先解析再改 key。正则直接操作字符串，不依赖 JSON 合法性，能更早介入。

**规则设计：**

```java
private static final List<NormalizeRule> RULES = List.of(

    // matchScore：覆盖 match_score / matchscore / match score / MatchScore / MATCH_SCORE
    new NormalizeRule(
        Pattern.compile("(?i)\"(match[_\\s]?score|matchscore)\"\\s*:"),
        "\"matchScore\":"
    ),

    // matchedSkills：覆盖 matched_skills / matchedskills / skills_matched / matched
    new NormalizeRule(
        Pattern.compile("(?i)\"(matched[_\\s]?skills?|skills?[_\\s]?matched|matchedskills?)\"\\s*:"),
        "\"matchedSkills\":"
    ),

    // missingSkills：覆盖 missing_skills / missingskills / skill_gaps / gaps / missing_requirements
    new NormalizeRule(
        Pattern.compile("(?i)\"(missing[_\\s]?skills?|missingskills?|skill[_\\s]?gaps?|gaps?|missing[_\\s]?requirements?)\"\\s*:"),
        "\"missingSkills\":"
    ),

    // improvementAdvice：覆盖 improvement_advice / improvementadvice / advice_text / suggestion / improvement
    new NormalizeRule(
        Pattern.compile("(?i)\"(improvement[_\\s]?advice|improvementadvice|advice[_\\s]?texts?|suggestions?|improvements?)\"\\s*:"),
        "\"improvementAdvice\":"
    )
);
```

关键设计点：
- `(?i)` 大小写不敏感，一条规则同时覆盖 `matchScore`、`MatchScore`、`MATCHSCORE`
- `[_\s]?` 覆盖有无分隔符的变体，`matchscore` 和 `match_score` 都能命中
- 正则只匹配 JSON key（被双引号包裹且后跟冒号），不会误替换 value 里的字符串

**在 Facade 层插入调用：**

```java
String json = extractJsonObject(raw);
String normalized = FieldNameNormalizer.normalize(json);  // 新增
MatchReport report = objectMapper.readValue(normalized, MatchReport.class);
```

### 两层的分工

| 层 | 处理的漂移类型 | 特点 |
|----|--------------|------|
| `FieldNameNormalizer` | 大小写变体、语义相近词、无分隔符变体 | 模糊匹配，覆盖范围广 |
| `@JsonAlias` | 已知的精确别名 | 精确匹配，作为兜底 |

## 测试情况

**新增 3 个测试用例，覆盖 `@JsonAlias` 处理不了的漂移：**

```java
@Test
void shouldNormalizeUnknownCamelVariants() {
    // matchscore（无下划线）、matchedskills（无下划线）—— @JsonAlias 不覆盖
    stubService.output = "{\"matchscore\":65,\"matchedskills\":[\"Java\"],\"missingskills\":[\"Docker\"],\"improvementadvice\":\"补充容器化经验\"}";
    MatchReport report = facadeService.evaluate("jd", "resume");
    assertEquals(65, report.matchScore());
}

@Test
void shouldNormalizeSemanticVariants() {
    // gaps（语义相近词）、skills_matched（顺序颠倒）、suggestion（同义词）
    stubService.output = "{\"matchScore\":70,\"skills_matched\":[\"Spring Boot\"],\"gaps\":[\"Kubernetes\"],\"suggestion\":\"深入学习 K8s 编排\"}";
    MatchReport report = facadeService.evaluate("jd", "resume");
    assertEquals("Spring Boot", report.matchedSkills().get(0));
    assertEquals("Kubernetes", report.missingSkills().get(0));
}

@Test
void shouldNormalizeUpperCaseVariants() {
    // MatchScore、MissingSkills 等首字母大写变体
    stubService.output = "{\"MatchScore\":88,\"MatchedSkills\":[\"MySQL\"],\"MissingSkills\":[\"Redis\"],\"ImprovementAdvice\":\"补充缓存层经验\"}";
    MatchReport report = facadeService.evaluate("jd", "resume");
    assertEquals(88, report.matchScore());
}
```

## 前后效果对比

| 漂移类型 | 改造前 | 改造后 |
|---------|--------|--------|
| `match_score`、`score` | `@JsonAlias` 覆盖，正常 | 同上 |
| `matchscore`（无下划线） | 静默丢值，`matchScore = 0` | `FieldNameNormalizer` 归一化，正常 |
| `MatchScore`（大写） | 静默丢值 | 归一化，正常 |
| `gaps`（语义相近词） | 静默丢值，`missingSkills = null` | 归一化，正常 |
| `suggestion`（同义词） | 静默丢值，`improvementAdvice = null` | 归一化，正常 |
| 新发现的未知变体 | 需改代码加 `@JsonAlias` 重新部署 | 大概率被正则覆盖，无需改代码 |

## 拓展：还有哪些方案

**方案 A：Jackson `PropertyNamingStrategy`**

Jackson 内置了 `SNAKE_CASE`、`LOWER_CAMEL_CASE` 等命名策略，可以让 Jackson 在反序列化时自动做 snake_case → camelCase 的转换。但这只能处理命名风格的转换，无法处理语义相近词（`gaps` → `missingSkills`）。

**方案 B：先解析成 `Map<String, Object>`，再手动映射**

把模型输出先解析成 `Map`，然后写一个映射函数，按业务语义把 key 归一化后再构造 `MatchReport`。比正则更灵活，可以做更复杂的逻辑（比如合并多个字段），但代码量更大。

**方案 C：模型侧 Structured Output**

如果使用支持 Structured Output 的模型（如 GPT-4o），可以在 API 层强制模型输出符合指定 JSON Schema 的内容，从源头消除字段漂移。这是最彻底的方案，但依赖模型能力，且仍需后端兜底（模型也可能偶发不遵守）。

**方案 D：记录未知字段告警日志**

当前 `FAIL_ON_UNKNOWN_PROPERTIES = false` 会静默丢弃未知字段。可以通过自定义 `DeserializationProblemHandler` 在发现未知字段时打印告警日志，让开发者感知到漂移发生，便于持续完善规则表。
