## 方向1：不同板块的分层处理——谁主导、如何实现？

### 面试官追问
> "简历包含项目经历、实习经历、技能列表等多个板块，每个板块的改写目标不同——谁来决定怎么改？是通过 Prompt 里写文字区分，还是有模块级路由？"

### 回答（确认代码实际）

> "分层处理由 `ResumeOptimizationService.optimizeFullResume()` 统一编排，通过**同一个 Writer Agent + 不同的 criticFeedback 约束文本**实现板块级差异化。不是不同的 Agent，也不是路由到不同的 Prompt 模板——就是同一个 `writerAgent.rewrite()`，靠传入的 criticFeedback 参数来区分板块约束。
>
> 具体分层：
> - **项目经历**：走完整 Actor-Critic 循环（评分引导→Writer 改写→Critic 审查），最多 2 轮
> - **实习经历**：单次 Writer 调用，criticFeedback 约束为 '仅调整句式与 JD 关键词对齐，保留所有原有技术栈和量化数据。不得改变角色定位。' + 评分引导
> - **技能列表**：单次 Writer 调用，criticFeedback 约束为 '严格保守：仅可调整技能排序和措辞，使 JD 关键词前置。严禁将'了解'升级为'熟悉'，将'熟悉'升级为'精通'。' + 评分引导
>
> 为什么实习经历不走 Actor-Critic 循环？**不是因为实习经历不能用 STAR/量化范式**——实习经历完全可以用'负责模块、实现功能、解决问题、量化效果'的结构撰写。真正的原因是：实习经历的违规类型和项目经历不同——项目经历容易捏造量化数据（QPS 数字），实习经历更容易出现角色夸大（'参与'→'主导'）。当前 Critic 的数字比对 Tool（checkClaim）对实习经历的价值有限——实习经历通常不会出现 'QPS 从 2000 改成 50000' 这种精确数字篡改。所以选择了单次调用+强约束，而非 Actor-Critic 循环。这是有意识的 trade-off，不是'实习经历不能写好'。"

### 追问预案
- "为什么不把实习经历也走 Actor-Critic 循环？" → "实习经历大部分是定性描述（'参与XX项目，负责XX模块'），不如项目经历容易捏造量化数据。Critic 审查带来的收益有限——没有具体 QPS 数字可查、没有技术栈可做差集。单次调用+强约束在这个场景下是合理的选择。但这是有意识的 trade-off——如果你问'实习经历为什么优化力度不如项目经历'，我诚实说当前 MVP 阶段重点在项目段。"
- "技能列表的严格保守约束具体是什么？" → "Writer 调用时传入的 criticFeedback 约束是：'严格保守：仅可调整技能排序和措辞，使 JD 关键词前置。严禁将'了解'升级为'熟悉'，将'熟悉'升级为'精通'。所有技能等级必须与原简历保持一致。'技能列表改写风险极大——'熟悉 Java'改成'精通 Java'会被面试官当场识破。"

## 方向2：不同板块评价标准不同——统一评分体系怎么处理？

### 面试官追问
> "项目经历用 STAR 法则评价，技能列表不需要叙事只要清晰归类，实习经历侧重工作职责——你用的三维评分（匹配度/内容质量/格式规范）对所有板块一视同仁，套在技能板块上合理吗？"

### ⚠️ 诚实回答（这是当前的设计短板）

> "这是当前架构的一个真实局限——评分系统不区分简历板块。`ResumeScoringAgent` 接收整份简历文本，用同一套 Prompt（40/35/25 权重）输出整体评分。它不会区分'这段是技能列表，不能用 STAR 标准'和'这段是项目经历，可以看量化成果'。
>
> 但这不是一个不可接受的设计缺陷——有三个原因：
>
> **第一，评分的价值在于引导，不在精确测量。** 评分的核心产出是 `missingSkills` 和 `improvements`——这两个字段对任何板块都有用。'缺失 Redis'无论出现在项目段还是技能列表，都是一个有价值的信号。'信息密度偏低'对技能列表和项目经历都同样有效。
>
> **第二，不同板块在评分 Prompt 中有隐式区分。** Scoring Agent 的 SystemMessage 定义了三个评分子维度：JD匹配度(40%) 看技能关键词覆盖和技术栈深度——技能列表和项目经历都会贡献到这一维。内容质量(35%) 看量化成果和 STAR 结构——这个维度天然侧重项目经历，因为技能列表很少包含量化数据。格式规范(25%) 看排版和信息密度——这对所有板块普适。LLM 在评分时天然会做加权：技能板块缺少量化数据→不扣分，项目板块缺少量化数据→扣分。
>
> **第三，板块级差异评分是下一步架构迭代。** 完整方案是：ResumeParser 分段后，对各段独立评分——技能列表侧重'覆盖率+归类清晰度'，项目经历侧重'STAR 完整性+量化数据'，实习经历侧重'工作职责+业务贡献'。但独立评分需要额外 API 调用 ×3，且需要设计板块级评分 Prompt——这是下一步。面试中我诚实说：当前是统一评分体系，但 LLM 在评估时会天然区分板块特性。板块级差异化评分是下一步架构迭代方向。"

### 追问预案
- "技能板块排版杂乱、表述混乱，你怎么发现？" → "Scoring Agent 的 `format.score` 和 `format.issues` 会捕捉到'信息密度偏低''排版不够清晰'这类问题。虽然评分标准没有特化到技能板块，但格式规范是普适的——技能列表如果写成'Java, Spring Boot, Redis, MySQL, Kafka, Docker, Kubernetes, Git, Maven, Jenkins, Nginx, Tomcat...'一大长串，评分一定会打出格式问题。但确实，如果技能板块分类明确只是排列顺序不贴合 JD，当前评分体系能发现的程度有限。"
- "你怎么知道评分对不同板块天然做了区分？" → "这是 LLM 的特性——不是 Prompt 里写了'请区分板块'，而是 LLM 在评估'内容质量'维度时天然给项目经历更多权重（因为项目经历通常包含更多可评估的内容）。这类似于人类 HR 审简历——'内容质量'主要看项目经历，技能列表和质量的关系不大。但我没有验证过——这是下一步要补的对照实验。"

## 方向3：ResumeParser 怎么识别段落边界？

### 面试官追问
> "简历格式千奇百怪，ResumeParser 怎么知道'教育背景'到哪为止、'项目经历'从哪开始？"

### 回答（45秒）

> "ResumeParser 基于关键词+正则匹配段落标题。预定义了四个段落模式——教育背景（'教育背景|教育经历|学历|education'）、技能（'技能|专业技能|技术栈|skill'）、项目经历（'项目经历|项目经验|project'）、实习经历（'实习经历|工作经历|experience'）。
>
> 匹配机制：逐行扫描简历文本，每行匹配标题正则——支持序号前缀（1./（一）/①）、中英文混合标题、冒号结尾。匹配到标题后，收集该标题下的所有内容行，直到遇到下一个合法标题或文本结束。
>
> 兜底：如果完全识别不出任何段落结构——比如一份纯文本无标题的简历——整份简历作为单个文本走优化管线，至少不会丢失数据。"

### 追问预案
- "无标题简历怎么办？" → "整份简历走全局 Actor-Critic 管线——Writer 改写整份简历，Critic 审查。效果不如分段处理（评分会拿到一份混杂了个人信息、教育、技能、项目的文本，评分准确度下降），但不会丢数据。这是 fallback 策略的价值所在。"

## 方向5：关键词识别完全靠 LLM？有正则兜底吗？

### 面试官追问
> "JD 匹配度里的技能关键词识别完全靠 LLM 自主判断？没有任何规则/正则辅助？LLM 漏识别了怎么办？"

### ⚠️ 诚实回答（当前无兜底）

> "当前 JD 匹配度的关键词识别确实完全依赖 LLM 自主判断——没有正则提取、没有硬匹配、没有关键词词库兜底。`ResumeScoringAgent` 的 SystemMessage 告诉 LLM '请列出匹配的技能关键词和缺失的技能关键词'，LLM 自主提取。

这是有意识的 trade-off——关键词匹配能保证不漏判（Redis 一定会被检测到），但无法处理语义等价（'分布式缓存'=Redis）和同义词（'消息队列'=RocketMQ/RabbitMQ/Kafka）。LLM 在语义等价上强于正则，但确实存在漏判风险——比如 JD 写了一个冷门技术栈（如 Seata），LLM 可能在评分时遗漏。

缓解策略（规划中，未实现）：
1. **正则关键词提取做兜底校验**——用 TextTrimmer 已有的正则能力从 JD 中提取技术名词，与 LLM 输出的 missingSkills 做交叉校验。LLM 漏了某个明显缺失的技能，正则能发现不一致。这是成本最低的改进（不需要额外 API 调用）。
2. **JD 关键词词库**——对常见技术栈（Java/Spring/Redis/Kafka/Docker 等 50+ 常见技术名词）维护一个正则提取词库，强制提取 JD 中的技术要求后再交给 LLM 做语义匹配和评分。"

### 追问预案
- "LLM 漏判你能发现吗？" → "当前不能自动化发现。只能通过人工抽查——随机取评分结果，对对比 JD 原文和 missingSkills，确认没有遗漏明显技能。但没有系统性的校验流程。"
- "这也是一个架构缺陷，打算怎么修？" → "正则兜底是最低成本的改进——不需要额外 API 调用，逻辑确定性强。但正则只能匹配'名词是否存在'，不能判断'项目经历是否真正体现了该技能的经验'。最终方案是正则提取 → LLM 语义匹配+评分 → 交叉校验，既保证覆盖率又保证语义深度。"

## 方向6：无标题简历的极端场景——只识别出项目段，其余全丢

### 面试官追问
> "如果简历完全没有标题——只是一大段纯文本——ResumeParser 只识别出了项目经历（因为有'项目'字样），实习经历、技能、教育背景全部无法归类。这些内容去哪了？会被丢掉吗？"

### 回答

> "不会丢。ResumeParser 的切分逻辑是：第一个合法标题之前的内容全部归入 `header`（个人信息），未匹配到任何标题关键词的行归入 `other`（其他）。所有未被识别为 education/skills/projects/experience 的内容都会被保留——要么在 header 里，要么在 other 里。
>
> 真正的问题是**识别精度下降**，不是丢失数据。如果一份简历只有一个'项目经历'标题被识别，其他内容都被丢进 header 和 other——评分时 LLM 拿到的是混杂了个人信息、教育、技能、实习的'header'文本和改写后的项目段，匹配度评估的准确度会下降。
>
> 这是当前架构的已知局限——ResumeParser 依赖标题关键词做段落边界识别，完全无标题的简历解析质量取决于 LLM 评分时的理解能力。下一步可以引入 LLM 辅助分段（对无标题简历用 LLM 做一次段落分类），但增加额外 API 调用。"

### 追问预案
- "other 里的内容怎么处理？" → "other 直接原样拼接到最终输出。它在拼装流程的最后一个位置（`ResumeParser.reassembleFull()` L262-264）——作为一个 catch-all 容器，确保没有任何内容被静默丢弃。"

## 方向7：固定拼接顺序无法适配不同求职者

### 面试官追问
> "有的人实习含金量高想前置展示，有的人实习内容单薄想后置——你固定顺序（教育→技能→项目→实习），不同用户诉求怎么办？"

### ⚠️ 诚实回答（当前不支持动态排序）

> "当前 `reassembleFull()` 的拼接顺序确实是硬编码的——个人信息→教育背景→技能列表→项目经历→实习经历→其他。没有实现按用户偏好动态排序的能力。这是一个真实的产品局限——系统无法判断'这个人的实习经历比项目经历更有说服力'。
>
> 解决方案（规划中）：前端增加拖拽排序控件，用户在优化前可以调整段落顺序偏好。后端 `reassembleFull` 接收一个 `List<String> sectionOrder` 参数来动态拼接。这本质上是前端交互改进+后端参数化，不涉及 Agent 链路改造。
>
> 面试中诚实说：当前是固定排序，但个性化排序在技术上就是改一个参数传入的问题，不是架构级难题。"

## 方向8：串行优化太慢，考虑过并行吗？

### 面试官追问
> "多个项目段串行调用 LLM，一份简历优化下来要多久？没考虑并行？"

### 回答（20秒）

> "当前 2 个项目段串行优化约 60-120 秒。并行在技术上是可行的——每个项目段独立，可以用 `CompletableFuture` 并行调用。但当前没做是因为 **DeepSeek API 有 RPM 限制**（每分钟请求数上限）——并发请求可能触发限流被直接拒绝，反而比串行慢。串行是当前 API 约束下的最稳妥选择。如果换成 OpenAI 或其他 RPM 更高的模型，并行化可以显著提速。"
