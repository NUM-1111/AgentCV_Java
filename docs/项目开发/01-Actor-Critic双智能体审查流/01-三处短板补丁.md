# 三处短板补丁

本次在实现 Actor-Critic 双智能体审查流的同时，修复了三处已知但未处理的工程短板。工作量小、价值高，消除了「知道有问题但没修」的明显暴露点。

---

## 补丁一：`IllegalArgumentException` → HTTP 400

### 问题

**文件**：`src/main/java/com/jobagent/exception/GlobalExceptionHandler.java`

原来 `GlobalExceptionHandler` 只处理了 `ContextWindowExceededException`（→ 400）和 `AiOutputValidationException`（→ 500），没有单独映射 `IllegalArgumentException`。

三个 Controller（`ResumeController`、`MatchController`、`JdController`）都用 `throw new IllegalArgumentException(...)` 做参数空值校验，但由于没有单独映射，这些异常会落入 `catch(Exception ex)` 的兜底逻辑，统一返回 **HTTP 500**。

**语义错误**：参数错误是调用方的问题，应该返回 400；500 表示服务内部错误，对接前端或联调时会造成误判。

### 修改内容

在 `GlobalExceptionHandler` 中，**在两个已有的 `@ExceptionHandler` 之前**插入新的处理器：

```java
@ExceptionHandler(IllegalArgumentException.class)
public ResponseEntity<ApiError> handleIllegalArgument(IllegalArgumentException ex) {
    log.warn("Bad request: {}", ex.getMessage());
    return ResponseEntity.status(HttpStatus.BAD_REQUEST)
            .body(new ApiError(400, ex.getMessage()));
}
```

### 效果

| 场景 | 修改前 | 修改后 |
|------|--------|--------|
| `jdText` 为空 | HTTP 500，"AI 分析引擎暂时开小差了" | HTTP 400，"jdText 不能为空" |
| `originalProjectText` 超长 | HTTP 500 | HTTP 400，"originalProjectText 超过 3000 字符限制" |

## 补丁二：rewrite 接口输入长度上限

### 问题

**文件**：`src/main/java/com/jobagent/controller/ResumeController.java`

`/api/v1/resume/rewrite` 接口只做了「非空」校验，没有长度上限。与 match 接口由 `TextTrimmer` + `TokenEstimator` 组成的防御体系相比，rewrite 接口对超长输入完全裸奔：

- 超长 JD 或项目经历原样透传给 LLM
- 可能导致 token 超限、API 报错或响应时间剧增

### 修改内容

在 `ResumeController.rewrite()` 的空值校验之后追加长度检查：

```java
if (request.jdText().length() > 3000) {
    throw new IllegalArgumentException("jdText 超过 3000 字符限制");
}
if (request.originalProjectText().length() > 3000) {
    throw new IllegalArgumentException("originalProjectText 超过 3000 字符限制");
}
```

配合补丁一，超长输入现在会返回 **HTTP 400** 并附上明确的错误信息，不会透传到 LLM。

### 字符限制的选择依据

3000 字符在中文场景下约等于 3000 token（1中文字 ≈ 1 token）。对于一段项目经历描述，3000 字已足够覆盖真实输入；配合 Actor-Critic 双智能体流中最多 3 轮循环，总 token 消耗仍在可控范围内。

## 补丁三：LLM 调用超时配置

### 问题

**文件**：`src/main/resources/application.yml`

原来 `langchain4j.open-ai.chat-model` 下没有配置 `timeout`。LangChain4j 默认使用底层 HTTP 客户端的默认超时，若模型侧出现慢响应，HTTP 请求可能**永久挂起**，直到操作系统或网关层超时（通常几分钟）。

Actor-Critic 双智能体流引入后，单次请求最多有 **3 轮 × 2 次 LLM 调用 = 6 次** LLM 调用，慢响应风险进一步放大。

### 修改内容

```yaml
langchain4j:
  open-ai:
    chat-model:
      timeout: 60s   # ← 新增
      log-requests: true
      log-responses: true
```

### 参数说明

60 秒的选择是一个平衡点：

- 足够覆盖单次复杂 LLM 调用（通常 10-30 秒）
- 不会让单次 HTTP 请求无限期挂起
- 面试阶段的临时方案；生产环境应配合**异步化**（202 + taskId 轮询）彻底解决响应时间问题
