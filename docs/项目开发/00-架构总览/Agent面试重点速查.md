### 标准版（约 90 秒，语速中等）

> 我做的是一个 **AI 驱动的智能简历优化系统**，Spring Boot + LangChain4j 技术栈，调用大模型 API，核心功能是根据 JD 自动匹配评分并定向重写简历。解决 纯大模型改写简历时 过度扩写简历 或 无法精准匹配JD需求 的痛点
>
> **架构上最核心的设计是 Actor-Critic 双智能体审查流**，用来解决大模型"幻觉"问题——模型重写简历时会无中生有地捏造数据，比如原文写"参与开发"，它给扩写成"主导设计，QPS 提升 30%"。我的方案是用两个 Agent 互相制约：**WriterAgent 负责扩写**但被禁止添加原文没有的数据和技术，**FactCriticAgent 以原始简历为事实边界逐条核查**，通过 RewriteCoordinatorService 串联，最多 3 轮循环——Critic 挑刺 → Writer 修改 → 再审查——直到通过或强制输出。
>
> 除了这个核心架构，工程上还做了三层横切治理：**输入层的上下文窗口防护**，防止长文本导致模型静默截断；**输出层的结构化解析 pipeline**，用四层防御处理模型 JSON 格式不稳定的问题；以及 **AOP + MDC 的全链路日志追踪**，出问题一条 grep 命令还原完整请求链路。
>
> 整个方案零侵入业务代码，所有横切逻辑集中在切面和 Filter 里。**最核心的价值是把 AI 应用的可靠性工程化了**——不是调一个 API 就完事，幻觉治理、token 管理、输出校验这些才是让系统真正可用的关键。

### 更精简版（约 60 秒，如果面试官明显赶时间）

> 我做的是一个 AI 简历优化系统，Spring Boot + LangChain4j，核心是基于 JD 智能评分和定向重写。
>
> 最核心的设计是 **Actor-Critic 双智能体审查流**——WriterAgent 负责生成，CriticAgent 以原始简历为事实边界逐条核查是否有捏造，两个 Agent 通过 3 轮循环互相制约，把幻觉率从约 15% 降到接近零。

> 工程上做了三层防御：输入层的 token 管理和智能裁剪、输出层的 JSON 容错解析 pipeline、以及全链路 AOP 日志追踪。核心思路是把 AI 应用的可靠性工程化。

### ⚠️ 练习要点

1. **不讲细节**：不展开 TextTrimmer 怎么截断、FieldNameNormalizer 有哪些规则。这些留给追问。
2. **不讲结果**：不说"幻觉率降低 15%""解析成功率 99%"。这会让面试官跳过追问直接问下一个话题。
3. **语速放缓**：在"Actor-Critic 双智能体审查流"这个词组上**刻意停顿半拍**——面试官会记住这个关键词，追问概率大幅提高。
4. **不要说第四个**：AOP 日志不要在介绍里展开成"第四个"，用"还做了"轻描淡写带过。如果面试官对前面三个不感兴趣，他会追问第四个——但如果你主动展开四个，他只能挑一个问，你的把控力就弱了。

## 🥇 P0 场景①：Actor-Critic 双智能体 — 你怎么解决 AI 幻觉？

> ← 对应 STAR 脱稿中的「第一个核心设计」。面试官听到"双智能体"后追问的内容都在这里。

| 项目 | 内容 |
|------|------|
| **你的角色** | 后端架构设计者 |
| **场景** | 简历重写时 AI 会"发明数据"（QPS 提升 30%、掌握 XX 技术） |

### 面试官核心追问链

#### Q1：「你们项目里 AI 幻觉问题怎么解决的？」

> 我用的是 **Actor-Critic 双智能体审查模式**——让两个 Agent 互相制约，但我不是停留在简单的"一个写一个审"，而是做了结构化分级判定。
>
> **WriterAgent** 负责根据 JD 偏好扩写简历要点，受两层约束：SystemMessage 明确禁止捏造数据和引入原文没有的技术栈；@Description 写死"只能使用原文已有的数据，不得推测或编造量化指标"。
>
> **FactCriticAgent** 以原始简历为唯一事实边界，输出不是简单的"过/不过"，而是结构化的 `CriticReport`：包含 `List<Violation>`，每条违规标注类型（FAKE_DATA/FAKE_TECH/EXAGGERATION/MINOR_EMBELLISHMENT）、严重程度（1-5）、以及引用原文证据的 detail。这让 Coordinator 可以做灰度决策——severity≤2 的 MINOR_EMBELLISHMENT 可以放行，只有 severity≥4 的捏造才必须重写。
>
> 两者通过 **RewriteCoordinatorService** 串联，最多 3 轮循环——Critic 反馈 → Writer 修改 → 再审查。我用 8 组测试用例跑过完整验证：1轮通过率50%，2轮到87.5%，3轮提供额外容错。3 轮后强制输出，不无限循环。

🔗 代码：`FactCriticAgent.java`、`ResumeWriterAgent.java`、`RewriteCoordinatorService.java`、`model/Violation.java`

#### Q2：「CriticAgent 怎么判断一条信息是不是幻觉？」

> 它不是简单的"过/不过"二分类，而是**结构化分级判定**，输出 `CriticReport` 包含：
>
> ```
> CriticReport {
>   approved: boolean;
>   violations: [{                          // 逐条违规详情
>     bulletIndex: 1;                       // 哪条 bullet 有问题
>     violationType: "FAKE_DATA";          // 违规类型
>     severity: 5;                          // 1-5 严重程度
>     detail: "原文QPS为2000，bullet写了50000"; // 引用原文证据
>   }];
>   feedback: "第1条的QPS数据与原文不一致"; // 修正建议汇总
> }
> ```
>
> 四种违规类型的判定依据在 System Prompt 里写成了精确规则：
> - **FAKE_DATA**（捏造数据）：数字逐字比对——原文 QPS=2000，bullet QPS=50000 → 不通过
> - **FAKE_TECH**（捏造技术栈）：技术栈逐项差集——原文只有 RocketMQ，bullet 写了 Kafka → 不通过
> - **EXAGGERATION**（夸大角色）：原文"参与/负责"→ bullet"主导/从零搭建" → severity=3
> - **MINOR_EMBELLISHMENT**（轻度润色）：severity≤2，不建议触发重写
>
> 我用 3 组刻意注入违规的 dirty draft（数字膨胀/技术替换/捏造百分比）做了验证：每组采样 3 次，共 9 次——**Critic 的命中率 100%**，且每条 detail 都引用了原文证据，可追溯。

🔗 代码：`model/CriticReport.java`、`model/Violation.java`、`FactCriticAgent.java`（精确数值审查规则）

#### Q3：「为什么是 3 轮循环？不是 2 轮或无限循环？」

> 这不是经验值，我跑了 **8 组测试用例 × 5 种循环上限的 A/B 验证实验**（约 240 次 API 调用）：
>
> | 循环上限 | 通过率 | 结论 |
> |---------|--------|------|
> | 1 轮 | 50% | 无审查兜底，不可接受 |
> | 2 轮 | 87.5% | 最小可行值 |
> | 3 轮 | 87.5%（但多了容错 buffer） | **最优质量保证值** |
> | 4-5 轮 | 持平或略高 | 边际收益为零，增成本不增量 |
>
> 3 轮的核心价值不是"通过率比 2 轮高"，而是**给 Critic 的偶发性误判留了容错空间**——实验中发现 C3-1 同一个用例在 2 轮变体中因一次误判失败，在 3 轮变体中获得了额外的修正机会后通过。
>
> 每轮只把 Critic 的 `feedback` 传给 WriterAgent，**不传历史草稿**——控制 token 消耗。如果传历史草稿，上下文窗口会指数级膨胀。

🔗 代码：`RewriteCoordinatorService.java` 的循环逻辑；`RoundOptimizationValidatorTest.java`（验证代码）；`docs/Actor-Critic双智能体审查流/04-循环次数验证报告.md`

## 🥈 P0 场景②：上下文窗口优化 — 简历太长崩了怎么办？

> ← 对应 STAR 脱稿中的「第二个核心设计」。面试官听到"三层防护"后追问的内容都在这里。

| 项目 | 内容 |
|------|------|
| **你的角色** | 排查线上 400 错误 |
| **场景** | 用户上传了一份 8000 字简历 + 5000 字 JD，API 报错 |

### 面试官核心追问链

#### Q1：「你怎么处理输入超长的问题？」

> 三层防护，每一层职责不同：
>
> **第一层 — TextTrimmer 业务裁剪**：JD 只提取"岗位职责"和"任职要求"段落，简历只提取"工作经历"和"项目经历"。单段上限 1500 字，总输出上限 4000 字。关键设计：截断时优先在句子边界（。！？）断开，保证语义完整。
>
> **第二层 — TokenEstimator 预估拦截**：裁剪后用保守规则估算 token（中文 1 字 ≈ 1 token，其他 4 字符 ≈ 1 token），叠加固定 Prompt 开销 400 token。超过 10000 阈值抛出 `ContextWindowExceededException`。
>
> **第三层 — GlobalExceptionHandler 兜底**：捕获异常后返回 HTTP 400 + 结构化错误信息——「估算 token 数 12500 超过安全阈值 10000，请精简后重试」——比框架的黑盒截断可排查得多。

🔗 代码：`TextTrimmer.java`（31 个测试用例）、`TokenEstimator.java`、`ContextWindowExceededException.java`

#### Q2：「为什么要自己估算 token，不直接用框架的截断？」

> 框架（LangChain4j）的截断是**黑盒的**，你不知道它截了什么——可能截掉了简历最关键的项目经历。自己做 token 估算 + 业务层裁剪，能做到：
> - 裁什么：只保留核心段落（岗位职责、工作经历），丢掉福利、公司介绍等噪声
> - 怎么裁：在句子边界断开，不破坏语义
> - 超了怎么办：返回明确的 400 错误而不是静默失败

#### Q3：「TextTrimmer 用正则匹配段落，遇到不规范格式怎么办？」

> 做了很多防御设计：支持"标题+内容同行"格式（`岗位职责：负责开发...`）、序号标题（`1.`、`一、`）、CRLF 换行、关键词覆盖 14 种变体。兜底策略：找不到目标模块时，过滤掉福利/公司介绍/联系方式等垃圾行后全局截断。31 个单元测试，包含 14 个极端场景。

🔗 代码：`TextTrimmerTest.java`（31 个测试用例）

## 🥉 P1 场景③：结构化输出治理 — 模型返回的 JSON 不对怎么办？

> ← 对应 STAR 脱稿中的「第三个核心设计」。面试官听到"四层 pipeline"后追问的内容都在这里。

| 项目 | 内容 |
|------|------|
| **你的角色** | 修复线上解析失败 |
| **场景** | 模型输出 JSON 里带了注释、尾逗号、snake_case 字段，解析崩溃 |

### 面试官核心追问链

#### Q1：「模型输出的 JSON 不稳定，你怎么处理的？」

> 三层 pipeline，每层各管一件事：

> **第一层 — extractJsonObject()**：模型输出经常被 Markdown 包裹（` ```json {...} ``` `）或前后带噪声文本。先正则提取 `{ ... }` 主体。
>
> **第二层 — Jackson 宽松解析 + @JsonAlias + FieldNameNormalizer**：Jackson 配置允许注释、尾逗号、单引号。`@JsonAlias` 覆盖常见的 snake_case / camelCase 别名。`FieldNameNormalizer` 用正则做模糊归一化——比如 `matched_skills` → `matchedSkills`，覆盖 `@JsonAlias` 范围外的未知变体。
>
> **第三层 — Bean Validation**：反序列化成功后，`@NotNull`、`@NotBlank`、`@Min/@Max` 做字段级校验。模型输出 `matchScore: 150` 会被拦截——不静默进入下游。

🔗 代码：`JacksonConfig.java`、`FieldNameNormalizer.java`、`MatchReport.java`（validation 注解）

#### Q2：「FieldNameNormalizer 和 @JsonAlias 有什么区别？为什么不只用 @JsonAlias？」

> `@JsonAlias` 是精确匹配——`@JsonAlias({"matched_skills", "matchedSkills"})`，你必须知道所有可能变体。FieldNameNormalizer 是**规则归一化**——把 `matched_skills`、`MatchedSkills`、`matched-skills` 统一转成 `matchedSkills`，覆盖未知变体。
>
> 两者是互补关系：@JsonAlias 兜已知，FieldNameNormalizer 兜未知。

🔗 代码：`FieldNameNormalizerTest.java`（3 个测试场景）

## 🧠 补充：Agent 项目设计的评价框架（面试官视角）

> 你没有 Agent 项目的开发经验，面试官可能会担心你"只是照猫画虎搭了个调用链路"。
> 这个框架帮你证明：**你不仅做出来了，而且知道为什么这样做是好的。**

### 面试官评判 Agent 项目的 5 个维度

| 维度 | ❌ 差的设计（面试官扣分项） | ✅ 好的设计（面试官加分项） | 你的项目做到了吗？ |
|---|---|---|---|
| **角色分工** | 一个万能 Agent 全包所有任务 | 多个 Agent 各司其职，职责边界清晰、不可互相替代 | ✅ Writer 负责生成 + Critic 负责核查，分工不重叠 |
| **通信协议** | Agent 间传自由文本（不可靠、无法程序化处理） | Agent 间传结构化对象（可校验、可追溯） | ✅ `CriticReport` 包含 `approved` 列表 + `feedback` 具体修改指令 |
| **反馈闭环** | 生成即输出，不验证不修改 | 生成 → 审查 → 修改 → 再审查，形成质量提升循环 | ✅ 最多 3 轮循环，Critic 反馈驱动 Writer 修改 |
| **终止条件** | 无限循环（浪费 token）或只跑 1 次（不保证质量） | 有明确上限 + 兜底策略，兼顾质量和成本 | ✅ 3 轮强制终止，不无限循环 |
| **约束力** | 「请尽量准确」这种软约束，模型可以忽略 | System Prompt 有明确禁令 + 可验证的核查清单 | ✅ 「禁止添加原文不存在的量化数据」+ 三条核查规则 |

> **面试话术**：当面试官问「你为什么选这个方案」时，不要说"我觉得好"，而是用这 5 个维度解释——"我评估 Agent 设计有五个维度：角色分工、通信协议、反馈闭环、终止条件、约束力。我在这五个维度上都做了针对性设计……"

### Q：你们的双智能体算工作流吗？

> **算，但不是通用 DAG 工作流引擎。**
>
> 准确说它是一个 **基于固定编排规则的 Multi-Agent 协作模式**——RewriteCoordinatorService 承担了工作流引擎的职责（串行调度、条件分支、循环计数、终止判断），但每个节点是具备自主决策能力的 LLM Agent（Critic 不是规则引擎，而是要判断"这条数据是捏造的吗"）。
>
> 和 LangGraph/CrewAI 等通用工作流框架的区别在于：这里是**为单一场景（简历重写）深度定制的工作流**，而非可配置的 DAG 编排。好处是定制化程度高（3 轮循环、feedback 传递、不传历史草稿），代价是不能通用——下一场景要重新设计。

### Q：对于一个 MVP Agent 项目，我们还缺什么？

> 以下是已知的、有意识的缺口——不是遗漏，是排列问题：

| 类别 | 缺口 | 为什么暂时没做 | 后续怎么做 |
|------|------|-------------|----------|
| **用户体验** | 异步化 + 进度反馈（SSE/WebSocket） | 先验证核心质量（幻觉治理），再优化体验 | 异步任务 + 实时推送中间状态 |
| **数据层** | 持久化 & 状态管理（无数据库） | MVP 阶段聚焦 Agent 架构，不引入外部依赖 | PostgreSQL + 历史对比功能 |
| **成本控制** | token 预算 & 调用频率限制 | 单人使用场景下成本可控 | 引入 token 预算 + 单用户限流 |
| **Agent 可观测性** | Langfuse/LangSmith 类的 Agent Trace | 已有 MDC 日志兜底，可视化为锦上添花 | 对接 Langfuse 做轨迹可视化 |
| **Prompt 外部化管理** | Prompt 硬编码在 Java 类里 | 版本少，硬编码在迭代期更直观 | 抽到外部配置，支持版本管理 + A/B |
| **反馈闭环** | 用户对重写结果没有评星/修改反馈 | 先跑通生成质量，再收集反馈做迭代 | 接入用户反馈 → Prompt 优化循环 |

> **面试话术**：当面试官问「你这个系统还缺什么」时，不要只说"还没做"，而是说"这是有意识的排列——MVP 阶段先验证核心架构（幻觉治理 → token 管理 → 输出校验 → 可观测性），这几块跑通后再补体验层、数据层、Prompt 管理。这样可以避免过早陷入非核心工程细节。"

### 你的项目在「Agent 设计质量」上的自评

> **总分：L3~L4（有明确设计理念 + 有工程落地 + 部分踩坑经验）**
>
> - 角色分工 → L3：两个 Agent 职责分明，不是简单堆砌
> - 通信协议 → L3：CriticReport 结构化输出了审查结果
> - 反馈闭环 → L3：3 轮循环有明确终止条件
> - 终止条件 → L4：有经验值依据（1~2 轮常用，3 轮兜底），且考虑了 token 消耗
> - 约束力 → L3：核查清单可验证，不是软约束
>
> **短板自知**：工作流编排是硬编码而非可配置（这是场景定制的 trade-off，不是不知道 LangGraph），Agent 间通信目前是同步阻塞（异步化是下一步）。

### 如果面试官问：「你这个跟直接用 LangGraph/CrewAI 搭一套有什么不同？」

> 三层回答：
> 1. **定位不同**：LangGraph 是通用框架，解决"如何编排任意 Agent 工作流"；我是为"简历重写审查"这一特定场景深度优化的方案——3 轮循环、feedback 传递策略、不传历史草稿这些决策都是场景驱动的。
> 2. **深度不同**：框架帮你搭骨架，但幻觉治理的核心——核查规则设计、角色边界定义、循环终止策略——这些必须自己设计。框架不能替你想"什么算幻觉"。
> 3. **认知清晰**：我知道这个方案什么时候该升级。如果未来有多个 Agent 场景（比如加上 JD 解析 Agent、面试题生成 Agent），硬编码工作流就撑不住了——那时会引入 LangGraph 做编排。**选型决策是场景驱动的，不是不知道。**

## 🔮 扩展话题：高并发 & 成本优化（面试官可能试探）

> 2026-06-03 模拟面试中此话题崩盘。**用"三维拆解框架"回答，不要直接跳进细节。**

| 维度 | 思路 | 当前状态 | 核心话术 |
|------|------|---------|---------|
| **减量** — 减少不必要的调用 | 裁剪 + Token 预估 + 缓存高频 JD | ✅ 已实现前两项，缓存规划中 | 「成本优化的第一性原理是减少不必要的 token。」 |
| **提效** — 降低单次调用成本 | 小模型做 Critic / 动态终止 / 模型量化 | 🔮 规划中 | 「审查任务是二元判断，用小模型就能做——这是成本治理的下一步。」 |
| **扩容** — 支撑高并发 | 异步线程池 + 消息队列 + SSE 推送 | 🔮 规划中 | 「LLM 推理是长耗时操作，天然适合异步化——@Async + RabbitMQ 即可支撑。」 |

> **答题框架**：「我会从**减量、提效、扩容**三个维度来思考这个问题。减量上，我们在输入层已经做了 TextTrimmer 和 TokenEstimator...；提效上，下一步可以用小模型做 Critic...；扩容上，LLM 推理天然适合异步化...」

### 追问：「为什么不现在就做？」

> 「MVP 阶段我先验证核心架构——幻觉治理、token 管理、输出校验、可观测性。这些跑通后再补高并发和成本优化，属于有意识的排列。把这些 trade-off 主动说出来本身就是工程成熟度的体现。」
