# 项目拆解方法论 · 总驾驶舱

> **目的**：不再「代码写了但说不清为什么这样做」，用一套可复用的 6 层金字塔，把任何项目从需求到面试话术完整理清。
> **活教材**：AgentCV 简历优化系统
> **使用方式**：每层 1 次对话——我提问、你回答（或反向），答不上来就是盲区。

---

## 6 层金字塔速览

```
 L6 面试层 ← 一句定调 + 关键数字 + 诚实缺陷

  ↑

## L1 场景层 — 完整拆解 ✅

### 一句话产品定义

> **简历优化工具**：用户输入 JD+简历 → AI 多维评分 → STAR 改写 → 事实核查 → 输出可导出的优化简历。

### 用户画像（MVP 阶段）

| 维度 | 结论 |
|------|------|
| 用户类型 | **单一用户**：有现成简历、需要针对特定 JD 优化的求职者 |
| 不做用户细分 | 产品需求说明书 §7 明确排除「无简历用户模板生成」，当前只验证核心链路 |
| 面试被问「有没有考虑不同用户」 | 「考虑过——不会写简历的用户需要模板生成，知道怎么写但想优化的是当前目标用户。MVP 先收敛为一种用户，验证核心链路后再分层」 |

### 用户四大痛点

| # | 痛点 | 不用这个产品的后果 |
|---|------|-------------------|
| 1 | **匹配度盲区**：用户难以判断自己的简历和 JD 的匹配程度，不知道缺什么技能 | 投出简历石沉大海，不知道是简历问题还是能力问题 |
| 2 | **改写无从下手**：知道要改但不知道改哪里、怎么改，手动改费时费力 | 花大量时间反复修改，效果靠猜 |
| 3 | **AI 改写不可信**：用通用 AI（ChatGPT 等）改写时会捏造数据、编造技术栈，用户不自知 | 简历内容失真，面试时被戳穿 |
| 4 | **多 JD 适配效率低**：同一份简历投不同公司，侧重点不同（A 公司偏业务开发、B 公司偏基础设施），用户需要为每个 JD 手动调整 | 要么一份简历海投（匹配度差），要么花大量时间逐一手动修改（效率低） |

### 用户旅程 4 步

```
第 1 步：打开页面
  → 看到标题、JD 输入区、简历输入区、两个按钮、进度条（隐藏）、结果区（隐藏）

第 2 步：输入内容
  → 粘贴或上传 JD + 完整简历（含个人信息/教育/技能/项目/实习）

第 3 步：点击操作
  ├─ 📊 快速评分：等 ~15s → 三维评分卡（综合分 + 细分维度 + 改进建议）
  └─ 🚀 完整优化：等 60-120s
      ├─ 进度条走三阶段：评分中… → 改写中… → 审查中…（SSE 阶段级推送）
      └─ 完成后一次性展示：
          · 前后评分对比（82→89）
          · 优化后完整简历（个人信息/教育/技能原样，项目经历已改写）
          · 改写说明（每个项目改了什么、为什么）
          · 复制/导出按钮

第 4 步：拿走结果
  → 复制到剪贴板或导出 MD/PDF，用于投递
```

### 关键设计决策（L1 层产出，影响下游）

| 决策 | 说明 | 影响 |
|------|------|------|
| 两按钮设计 | 「快速评分」只评分不改写，「完整优化」跑全管线 | → L2 决定了两个 API 端点 |
| 阶段级推送而非逐字流式 | 简历优化不是对话产品，用户不需要跟读 | → L4 决定了 SSE 选型而非 WebSocket |
| 评分缓存 | 先评分再点优化时复用评分结果，不重复调用 LLM | → L3 数据流中评分阶段可跳过 |
| 审查结论不暴露给用户 | 用户只需知道「审查通过」，不需要看违规细节 | → L2 输出契约中 isReliable 替代 violations |

### L1 → L2 推导链

> 用户旅程第 3 步的「粘贴 JD+简历」「输出评分卡/优化简历」→ 直接定义了 L2 的输入输出契约：输入 JD/简历各两种方式（文本+文件），输出 ScoreReport / OptimizationReport。

## L2 契约层 — 完整拆解 ✅

### 输入契约

| 字段 | 类型 | 必填 | 格式限制 | 说明 |
|------|------|:--:|------|------|
| `jdText` | String | 二选一 | 纯文本 | JD 文本，直接粘贴 |
| `jdFile` | MultipartFile | 二选一 | PDF / MD / Word（.docx） | JD 文件上传，.doc → 提示转 .docx |
| `resumeText` | String | 二选一 | 纯文本，≤10000 字符 | 简历文本，直接粘贴。10000 来自 Token 阈值反推（见 L4） |
| `resumeFile` | MultipartFile | 二选一 | PDF / MD / Word（.docx） | 简历文件上传，.doc → 提示转 .docx |

**关键设计**：JD 和简历都支持「文本粘贴 OR 文件上传」二选一——降低使用门槛，不用强制用户准备文件。

### 输出契约

**快速评分输出 — `ScoreReport`：**

```
ScoreReport {
  overallScore:   int（0-100 综合分）
  jdMatch:        { score: int, matchedSkills: [], missingSkills: [] }
  format:         { score: int, issues: [] }
  contentQuality: { score: int, highlights: [], improvements: [] }
  advice:         String（改进建议摘要）
}
```

**完整优化输出 — `OptimizationReport`：**

```
OptimizationReport {
  beforeScore:     ScoreReport        // 改写前评分
  afterScore:      ScoreReport        // 改写后评分（对比变化量）
  finalResumeText: String             // 完整优化简历文本（回填后）
  changes: [
    { projectTitle: String,           // 项目名称
      originalText: String,           // 原文
      rewrittenText: String,          // 改写后
      reason: String }                // 改写理由
  ]
  isReliable:     Boolean            // 事实核查是否通过（对用户只暴露这个布尔值）
  elapsedMs:      Long               // 总耗时
}
```

**关键设计决策**：`isReliable` 替代内部 `violations` 暴露给用户——
- 用户只需要知道"审查通过/不通过"，不需要看到 FAKE_DATA/FAKE_TECH/EXAGGERATION 这些内部判定逻辑
- 既保护了内部机制（面试时可以展开讲），也避免了用户在结果页看到一堆技术术语的困惑

### 明确不做的功能（及理由）

| # | 不做 | 理由 |
|---|------|------|
| 1 | 无简历用户模板生成 | 属于另一个产品方向，需要从零生成简历而非优化 |
| 2 | 历史记录存储 | MVP 阶段不引入数据库依赖，且与项目二（IntelliVault）的功能边界冲突 |
| 3 | 审查详情暴露给用户 | 用户只需结论，内部违规类型是工程术语 |
| 4 | 逐字/逐句流式输出 | 简历优化不是对话产品，用户不需要跟读——阶段级推送足够 |
| 5 | 多项目并发 LLM 调用 | 先串行跑通验证核心链路，避免 LLM API 限流；并发优化是 Phase 2 |

**面试重点**：「第 5 条——不是不会做并发，是主动选择串行。LLM API 有 QPS 限制（DeepSeek 免费版尤其严格），并发会触达限流。在 MVP 阶段先串行验证核心链路的正确性，并发放在第二阶段。」

> ⚠️ **文档同步检查**：产品需求说明书 §7 与复习计划6 关于「不做并发」的说法一致——都是「先串行，后续优化」。

### L2 → L3 推导链

> 输出契约中的 `OptimizationReport` 包含 `beforeScore → finalResumeText → isReliable` 这个结构，直接决定了 L3 的数据流必须经过「评分→改写→审查→回填」四个阶段才能产出这些字段。

## L3 数据流层 — 完整拆解 ✅

> **⚠️ 本章数据流基于 `ResumeOptimizationService.java`（2026-07-17 代码实际），与旧文档可能有差异。所有差异点已标注。**

### 宏观视图：一条输入 → 三阶段管线 → 一条输出

```
📥 Controller 层
  jdText + resumeText
  → TextTrimmer 裁剪核心段落（≤8000 字）
  → TokenEstimator 估算（>10000 → 400 拦截 & 放行）

🏗️ ResumeOptimizationService.optimizeFullResume()
  │
  ├─ [阶段0] ResumeParser 分段           ← 纯 Java 正则，非 LLM
  │
  ├─ [阶段1] Scoring Agent 评分          ← LLM 调用 ①
  │
  ├─ [阶段2] 逐段改写 + 事实核查          ← LLM 调用 ②③④...(每个段落 1~2 轮)
  │   ├─ projects[] → Actor-Critic 循环   ✅ 完整
  │   ├─ experience → Writer 改写         ⚠️ 无 Critic
  │   └─ skills → Writer 改写             ⚠️ 无 Critic
  │
  ├─ [阶段3] ResumeParser 回填拼接       ← 纯 Java 字符串拼接
  │
  └─ 构建 OptimizationReport            ← 评分闭环未打通 ⚠️

📤 Controller 层
  JSON 序列化 → 四层防御 Pipeline → HTTP 响应
```

### 逐阶段详解

---

#### 阶段 0：简历分段（ResumeParser）

| 项目 | 内容 |
|------|------|
| **职责** | 把用户粘贴的完整简历文本拆成结构化片段 |
| **输入** | 完整简历文本（一个 String） |
| **输出** | `ResumeSections { header, education, skills, projects[], experience, other }` |
| **技术** | 关键词 + 正则匹配中英文标题 + 序号前缀 + CRLF/LF 换行 |
| **异常处理** | 匹配不到标题 → 全文归入 other（不丢数据） |
| **是否 LLM** | ❌ 纯 Java，不消耗 Token |

> **面试一句说清**：「ResumeParser 用关键词+正则把用户的完整简历拆成个人信息/教育/技能/项目/实习六个区，不丢数据——匹配不到就归入兜底分区。」

---

#### 阶段 1：多维评分（ResumeScoringAgent）

| 项目 | 内容 |
|------|------|
| **职责** | 评估简历与 JD 的匹配度，输出三维评分 + 改进建议 |
| **输入** | JD 文本 + 完整简历文本 |
| **输出** | `ScoreResult { overallScore, jdMatch{score,matchedSkills,missingSkills}, contentQuality{score,highlights,improvements}, format{score,issues}, improvementAdvice }` |
| **技术** | LLM 调用（DeepSeek），权重写死 JD匹配40% / 内容质量35% / 格式规范25% |
| **下游用途** | `buildScoreGuidance()` 提取 missingSkills + improvements → 注入 Writer 的改写 Prompt |
| **是否 LLM** | ✅ 1 次 LLM 调用 |

> **代码证据链**：`scoringAgent.score(jdText, fullResumeText)` → line 138
> **面试一句说清**：「评分 Agent 做三维评估，J D 匹配度 40% / 内容质量 35% / 格式规范 25%，输出的缺失技能和改进方向会引导 Writer 改写。」

---

#### 阶段 2a：项目经历改写+审查（Actor-Critic 循环）✅ 完整

| 项目 | 内容 |
|------|------|
| **职责** | 对每个项目经历的 body 文本做 STAR 改写 + 事实核查 + 不通过则重写 |
| **输入** | JD + 项目原文 + 评分引导文本 |
| **输出** | `RewriteResult { bullets, reasons, rounds, approved, violations }` |
| **循环规则** | maxRounds=2，Round 0 首轮 → Round 1 修复轮，2 轮仍不通过 → 强制输出 + violations |

```
runActorCritic(jd, projectBody, scoreGuidance):
  feedback = ""
  currentInput = projectBody            ← Round 0 用原文

  Round 0:
    Writer.rewrite(jd, currentInput, scoreGuidance) → WriterDraft
    Critic.check(projectBody, draft) → CriticReport
    approved? → ✅ 返回
    不通过 → feedback = CriticReport.feedback
              currentInput = 上一轮改写结果   ← Round 1 用改写后的内容

  Round 1:
    Writer.rewrite(jd, currentInput, feedback) → WriterDraft     ← 注入 Critic 反馈
    Critic.check(projectBody, draft) → CriticReport
    approved? → ✅ 返回
    不通过 → ⚠️ 强制输出 + violations（不无限循环）
```

| 关键设计 | 说明 |
|---------|------|
| Round 0 输入 | 原始项目文本 + 评分引导（missingSkills + 改进方向） |
| Round 1 输入 | **上一轮改写后的 bullet points**（非原文） + Critic feedback |
| 不传历史草稿 | 每轮只传当前轮输入和 feedback，不堆叠历史——控制 Token |
| 2 轮终止 | 成本-质量平衡，不无限循环 |

> **代码证据链**：`runActorCritic()` → line 207-233；循环 `for (int round = 0; round < maxRounds; round++)` → line 213

---

#### 阶段 2b/2c：实习经历 + 技能改写 ⚠️ 有改写但无 Critic

| 段落 | 改写 | Critic 审查 | 约束 |
|------|:--:|:--:|------|
| projects[] | ✅ | ✅ 完整 Actor-Critic | STAR 改写，以原文为事实边界 |
| experience | ✅ | ❌ 直接调 writerAgent，不走 runActorCritic | 「仅调整句式与 JD 关键词对齐，不得改变角色定位」 |
| skills | ✅ | ❌ 直接调 writerAgent，不走 runActorCritic | 「严格保守：仅可调整排序和措辞，严禁将'了解'升级为'熟悉'」 |

> **⚠️ 已知缺口**：experience 和 skills 缺少 Critic 审查，依赖 Prompt 约束而非系统级校验。要做的改动不是技术复杂度问题——只是把 `writerAgent.rewrite()` 调用替换成 `runActorCritic()`，但需要为 experience/skills 定制不同的 Critic 审查规则（当前 Critic 的 FAKE_DATA/FAKE_TECH 规则是针对项目经历设计的）。
>
> **面试诚实话术**：「当前的 Critic 审查规则——假数据、假技术栈、角色夸大——是针对项目经历设计的。实习经历和技能的改写风险不同：实习经历主要风险是角色夸大，技能列表主要风险是等级升级。直接复用同一套规则效果不好，需要为每个段落类型定制审查策略。MVP 阶段先通过 Prompt 约束保证安全，第二个阶段再做细分。」

---

#### 阶段 3：回填拼接（ResumeParser.reassembleFull）

| 项目 | 内容 |
|------|------|
| **职责** | 把改写的部分替换回原始简历结构，其他部分原样保留 |
| **输入** | 原始 `ResumeSections` + 改写后的 projects[] / experience / skills |
| **输出** | `finalResumeText`（一条完整字符串） |
| **技术** | 纯 Java 字符串拼接 |
| **是否 LLM** | ❌ |

```

### 决策 1：10000 token 阈值

> 详细推导链见 `02-上下文窗口优化/04-Token阈值决策数据链.md`。以下是面试可脱稿版本。

**一句话定调**：「10000 不是拍脑袋，是从 TextTrimmer 的结构上限反推出来的。」

**推导链**：
```
TextTrimmer 理论最大输出 = JD 2段(3000字) + 简历 3段(4500字) = 7500字
→ 设为 8000（留 500 字 fallback 余量）
→ 全中文极端情况：8000 × 1.0(保守估算系数) + 400(Prompt模板固定开销) = 8400 token ← 阈值下限
→ 取整到 10000，留 1600 token 业务增长余量

Golden Set 9 组实测：486~604 token — 用来验证"不误杀正常用户"，不是用来推导阈值
```

**三个约束的验证**：
| 约束 | 验证内容 | 结果 |
|------|---------|------|
| 约束 A | 阈值 ≥ 8400（Trimmer 结构上限反推） | ✅ 10000 > 8400 |
| 约束 B | Golden Set 9 组实测不超阈值 | ✅ 最大 604 ≪ 10000 |
| 约束 C | 英文简历不因纯英文而估算失败 | ✅ 英文样本 577 token |

**设计哲学**：宁可高估误拦（用户收到 400 可精简重试），不可低估漏拦（被截断导致数据损坏不可逆）。

**面试话术（15 秒）**：「我的 10K 阈值是从 Trimmer 结构反推的——Trimmer 理论最大 7500 字，设 8000 留余量。全中文极端情况 8000+400=8400 token，这是阈值下限，我取整到 10000。Golden Set 9 组实测最大 604，用来验证正常用户不会被误拦。」

### 决策 2：8000 字 Trimmer 总上限

**推导链**：
```
TextTrimmer 按段落提取核心内容：
  JD 段：岗位职责(1500字) + 任职要求(1500字) = 3000字
  简历段：工作经历(1500字) + 项目经历(1500字) + 核心技能(1500字) = 4500字
  合计 = 7500字 → 设为 8000（给 fallback 路径留 500 字余量）
```

> 关联决策：如果修改 `TOTAL_CHAR_LIMIT`（8000），必须重新验证约束 A 是否仍然 ≤10000 token。

### 决策 3：1500 字单段上限

- 覆盖 99% 的 JD/简历段落长度
- 超限时在句子边界（。！？）智能截断，保证语义完整
- fallback：截断后 <50 字 → 退回原文（不丢数据）

### 决策 4：2 轮 Actor-Critic 循环

**当前状态**：`DEFAULT_MAX_ROUNDS = 2`（Round 0 首轮 + Round 1 修复轮）

**推导逻辑**：
| 轮次 | 效果 | 代价 |
|------|------|------|
| 1 轮 | 无审查兜底，无法保证质量 | — |
| 2 轮 | 有一次修复机会，覆盖绝大多数违规 | 多一次 LLM 调用 |
| 3 轮 | 边际收益很小 | 额外成本 + 死锁风险 |
| ∞ | — | 不可接受 |

> **⚠️ 历史版本注意**：复习计划6 已统一为 2 轮。`Agent面试重点速查.md`（旧版）还有 3 轮的说法——不要用。

**面试话术**：「1 轮没有审查兜底。3 轮边际收益趋零——实验中 2 轮和 3 轮的通过率基本持平，但 3 轮多一次 LLM 调用。2 轮是质量和成本的平衡拐点。如果第 2 轮仍不通过，强制输出并标记 violations，不无限循环。」

### 决策 5：40/35/25 三维权重 🔴

**当前状态**：写死在代码中，未经数据校准。

**为什么写死**：「权重需要真实数据验证才有意义，过早配置化是过度设计。」——产品需求说明书 §8

**面试被追问时的诚实回答**：
> 「40/35/25 是 MVP 占位值。JD 匹配度权重最高——因为用户的最终目的是让简历通过 JD 筛选。真正的权重校准需要标注数据——收集简历-JD 对，让多个评分员标注匹配度，做线性回归得到最优权重。这是 MVP 之后的下一步。」

**后续方案**：
1. 收集 30+ 组简历-JD 配对样本
2. 人工标注匹配度（1-5 分）
3. 调整权重，计算评分与标注的相关系数
4. 选相关系数最高的权重组合

### 决策 6：SSE 阶段级推送 vs WebSocket 逐字流式 ⚠️

**为什么选 SSE**：
- 简历优化不是对话产品——用户不需要跟读 AI 输出
- 用户只需感知进度（评分中 → 改写中 → 审查中 → 完成）
- SSE 比 WebSocket 轻量——单向推送足够，不需要双向通信
- 前端 EventSource 原生支持，重连机制简单

**为什么是阶段级而非逐字**：
- 产品决策，非技术限制
- 三阶段管线天然分段——每阶段完成才产出有意义的结果
- 逐字流式适合 ChatGPT 类对话，不适合结构化管线

**面试话术**：「SSE 是主动选型。我的场景是阶段级进度推送——评分→改写→审查→完成——服务器单向推送事件就够。WebSocket 是双向通信，我的场景不需要客户端给服务器发消息。阶段级而非逐字是产品决策——简历优化不是对话产品，用户不需要跟读 AI 逐字产出，感知进度就行。」

### 决策 10：ResumeParser 用正则而非 LLM ✅

**这是一个主动的「不做 LLM」决策。**

| 对比维度 | 正则 | LLM |
|---------|------|-----|
| Token 消耗 | 0 | 每次分段消耗 Token |
| 速度 | 毫秒级 | 秒级 |
| 准确性 | 关键词匹配，15+ 变体覆盖 | 语义理解更准 |
| 兜底 | 匹配失败归入 other，不丢数据 | — |

**关键认知**：简历分段不是语义理解任务——标题通常是「项目经历」「实习经历」「专业技能」等固定关键词。用 LLM 做分段是杀鸡用牛刀。

---

### 决策 11：Critic 有 Tool Calling / Writer 没有 ✅

**为什么不对称**：
- Critic 需要精确数值比对——「原文 QPS=2000，改写后 QPS=50000」→ 这需要 `FactCheckTool.checkClaim()` 做逐字数字比对，纯 LLM 容易漏
- Writer 只需要文本生成——在 System Prompt 里写死约束就够了

**面试话术**：「Critic 注册了 FactCheckTool——三个方法：checkClaim 做数字精确比对、checkTechStack 做技术栈差集校验、checkRoleWording 做角色措辞判断。Writer 没有 Tool，因为它的任务是在 Prompt 约束下做文本生成——不需要精确数值比对。不对称是因为职责不同。」

---

### 决策 12：3 类违规（移除了 MINOR_EMBELLISHMENT）✅

**历史版本**：4 类（含 MINOR_EMBELLISHMENT，severity 1-5 分级判定）

**当前版本**：3 类 + 任一违规即触发重写（无 severity 分级）

**简化理由**：
- 减少判定复杂度——"轻度润色"和"正常改写"的边界模糊
- 降低误判——Critic 不需要做 severity 这种主观判断
- 提高安全标准——宁可多一次重写，不放过潜在违规

**面试话术**：「从 4 类简化到 3 类。移除 MINOR_EMBELLISHMENT 是因为它的判定太主观——什么算'轻度润色'？这个边界不好定。现在策略是：任一违规即触发重写，不做 severity 灰度。宁可多一轮 Writer 调用，不让潜在问题漏过去。」

### 🔴 项面试诚实说辞（最重要的 3 个）

**① 评分→改写闭环未打通**

> 「评分引导（missingSkills + 改进方向）已经传给 Writer。但改写后的 afterScore 对比还没接上。当前 MVP 验证了安全侧——Critic 防幻觉——效果侧的评分闭环是下一步。技术上就是一次 `scoringAgent.score()` 调用。」

**② experience/skills 有改写但缺 Critic 审查**

> 「项目经历有完整的 Actor-Critic 循环。实习经历和技能列表目前通过 Prompt 约束保证安全。Critic 的审查规则——假数据/假技术栈——是针对项目经历设计的，直接复用效果不好。MVP 先验证核心链路，第二步为每个段落定制审查策略。」

**③ 模型选型无对比测试**

> 「DeepSeek V4-Flash 基于三点——1M 上下文、低价格、LangChain4j 集成。目前没有做系统对比，下一步会关注三个维度：JSON 格式正确率、中文改写自然度、单位 token 成本。」

### 决策闭环：从"这么做"到"为什么这么做是对的"

> *这部分回应了 L4 中标注 🔴 的决策——当你做出一个决策但没有验证数据支撑时，面试官追问怎么办？*

**闭环框架（适用于任何未验证决策）**：

```
1. 诚实说明当前状态：「我是基于 X/Y/Z 理由做的这个选择，但目前没有量化的对比验证」
2. 给出明确的验证方案：「我下一步会从 A/B/C 三个维度做对比」
3. 列出具体对比维度（不要泛泛说"会测试"）：
   - 模型选型 → JSON 格式正确率、中文改写自然度、单位 token 成本
   - 三维权重 → 收集标注数据 + 线性回归校准
   - 循环轮数 → 1/2/3 轮 A/B 质量对比
4. 说明为什么 MVP 阶段不做：「先验证核心架构，再优化参数——避免过早陷入非核心优化」
```

**面试中的表述模板**：

> "这个决策我是基于 [理由] 做的。目前没有做系统对比——我的下一步计划是从 [3个维度] 做 A/B 验证。MVP 阶段我的优先级是先跑通整条链路，架构稳了再精调参数。"
