### S-1. ATS 关键词覆盖率自动计算

**预计时间**：3-4 小时
**简历影响**：⭐⭐⭐⭐⭐（直接提供"覆盖率从 X% 提升到 Y%"的效果锚点）

#### 问题

当前 Writer 改写简历后，无法回答"改得好不好"——面试官追问"怎么评估改写质量"时只能承认"没有可视化数据"（阿里二面段六 P1 / 字节一面段九 P1）。

更具体地说：JD 中要求的技术关键词（如"Spring Boot""Kafka""分布式事务"），在改写后的简历中覆盖了多少？没有这个数字，"匹配度评估"就是黑盒。

#### 方案

在 `ResumeOptimizationService` 或独立工具类中，增加一个**低成本的后处理步骤**：

```
JD 文本 → 提取关键词（复用 TextTrimmer 的正则能力）
         ↓
改写后简历 → 匹配关键词命中数
         ↓
计算：覆盖率 = 命中数 / JD 关键词总数
```

**实现层次**：

1. **关键词提取**：JD 文本 → 过滤停用词 → 提取技术名词（大写开头的词 + 常见技术栈词表 + 2-4字中文技术词组）
2. **匹配逻辑**：大小写不敏感 + 同义词映射（如 "K8s" ↔ "Kubernetes"）
3. **输出结构**：覆盖率百分比 + 命中/未命中明细列表

```java
// 伪代码
public record KeywordCoverageReport(
    double coverageRate,           // 0.0 ~ 1.0
    List<String> matchedKeywords,  // 命中的 JD 关键词
    List<String> missedKeywords,   // 遗漏的 JD 关键词
    List<String> extraKeywords     // 简历有但 JD 未要求的（候选人的额外技能）
) {}
```

**为什么低成本**：
- 不依赖 LLM 调用（零 token 消耗）
- 可复用 TextTrimmer 的正则基础设施
- 对比数据不需要人工标注（直接 JD vs 简历文本比对）

#### 效果（可写入简历的数据）

> "引入 ATS 关键词自动覆盖率评估：改写前简历对 JD 核心关键词的覆盖率约 45%，改写后提升至 82%。未覆盖的关键词以 warning 形式返回给用户，辅助针对性补全。"

#### 测试验证

- 取 golden-test-set.json 中的 8 组 JD-简历对
- 跑关键词提取 → 匹配 → 输出覆盖率分布表
- 确认边界 case：JD 无技术关键词时返回 N/A

### S-2. Critic 精确度评测报告（基于 Golden Set）

**预计时间**：2-3 小时
**简历影响**：⭐⭐⭐⭐（提供"审查精确度 XX%"的硬数据，同时修正"87.5% 通过率"的口径问题）

#### 问题

当前说的"87.5% 通过率"存在两个问题：
1. 未明确是 Critic 自动审查的通过率还是人工评审的通过率（豆包模拟面试 Q5）
2. 没有精确度/召回率数据——Critic 判"通过"的改写中，有多少实际上是假阴性？

#### 方案

基于已有的 `golden-test-set.json`（8 组用例），写一个评测脚本 `CriticPrecisionEvaluationTest`：

```
对每组 golden case:
  1. 已知 ground truth（人工标注：该改写是否有违规，违规类型是什么）
  2. 调用 Critic Agent 做审查
  3. 对比 Critic 输出 vs ground truth
  4. 统计：
     - Precision = TP / (TP + FP)  — Critic 报了违规，有多少是真的违规？
     - Recall    = TP / (TP + FN)  — 所有真实违规中，Critic 发现了多少？
     - F1 Score
```

**扩展 golden-test-set**：从 8 组扩展到 15-20 组，覆盖：
- 4 类违规各 3-4 个样本
- 无违规（应通过）样本 3-4 个
- 边界模糊样本（夸大 vs 合理优化）2-3 个

#### 效果（可写入简历的数据）

> "基于 20 组人工标注的 Golden Test Set 对 Critic 进行精确度评测：Precision 91%、Recall 87%、F1=89%。其中 FAKE_DATA（假数据）检出率 100%，MINOR_EMBELLISHMENT（过度润色）存在 12% 假阳性——已在 SystemMessage 中增加'酌情容忍轻度措辞优化'的判定准则。"

#### 测试验证

- 跑 `CriticPrecisionEvaluationTest`
- 输出 Precision/Recall 矩阵（按违规类型分拆）
- 确认 FAKE_DATA/FAKE_TECH 的 Recall ≥ 95%（这是业务底线——假数据不能漏）

简历中可增加：

### S-4. 成本基准数据测算

**预计时间**：2-3 小时
**简历影响**：⭐⭐⭐⭐（提供"单次改写成本 ¥0.0X"的工程化数据，展示成本意识）

#### 问题

面试被问"一次改写调用花费多少 Token？成本多少？"时无法回答（阿里二面段六）。"你做了成本控制但不知道实际成本是多少"——这是面试官的合理质疑。

#### 方案

写一个 `CostBenchmarkTest`，取 8 组 golden-test-set 的 JD-简历对，跑完整链路（TextTrimmer→Writer→Critic→3轮循环→最终输出），使用 LangChain4j 的 `TokenUsage` 统计每轮实际 Token 消耗：

```
每组用例记录：
  - 输入 token（JD + 简历 + Prompt 模板）
  - 输出 token（Writer 输出 + Critic 输出）
  - 轮数
  - 总 token → 按 DeepSeek 定价换算成本
```

**具体步骤**：

1. 利用 LangChain4j 的 `chatModelListener` 或 `TokenUsage` API 获取每次调用的实际 token 数
2. 跑 8 组用例，收集数据
3. 计算：单次改写平均成本、3 轮循环平均成本、100 份批量预估成本
4. 产出成本速记卡（面试前 3 分钟过一遍）

#### 效果（可写入简历的数据）

> "单次简历改写平均消耗 4200 token（输入）+ 1800 token（输出），3 轮循环总成本约 ¥0.03（DeepSeek V3 定价）。TextTrimmer 将输入压缩至原始长度的 35%，每次调用节省约 ¥0.01。按日均 1000 次调用估算，月节省约 ¥300。"

#### 测试验证

- 跑 `CostBenchmarkTest`
- 输出成本分布报告（最低/最高/平均 + 按轮数分拆）
- 确认无内存泄漏（多次调用后 TokenUsage 累计正确）

### S-5. Writer 输出质量自动评分（轻量版）

**预计时间**：4-5 小时
**简历影响**：⭐⭐⭐⭐⭐（给 Writer 改写质量提供量化指标，补齐手录分析 M1-2 的核心缺口）

#### 问题

当前 Writer 的改写质量完全靠人工评审——面试官追问"怎么保证写得好"时无法回答。需要一个自动化评分机制，哪怕是轻量版的。

#### 方案

在 `ResumeOptimizationService` 的结果中增加 `WriterQualityScore` 字段，计算三项指标：

1. **JD 对齐度**（复用 S-1 的关键词覆盖率）：改写后简历中 JD 关键技术的命中率
2. **信息密度**（简单可算）：改写后文本中技术名词/数据量词的出现频率 vs 虚词比例
   - 好简历：高比例具体技术名词 + 量化成果
   - 差简历：大量"负责""参与"等虚词
3. **长度合理性**（简单可算）：改写后 bullet point 数量和每段长度分布
   - 太少 → 信息不足
   - 太多 → 可能堆砌

```java
public record WriterQualityScore(
    double jdAlignmentScore,       // 0-100, JD 关键词覆盖率 × 100
    double informationDensity,     // 0-1, 技术名词占比
    int bulletPointCount,          // bullet point 数量
    double avgBulletLength,        // 平均每段长度
    String overallAssessment       // "优秀" / "良好" / "需改进"
) {}
```

**为什么是轻量版**：
- 不依赖 LLM 调用
- 不依赖向量数据库
- 纯文本统计 + 正则 = 零额外成本
- 后续可升级为完整版（I-1 效果验证量化体系：维度评分 + 向量相似度 + ATS 覆盖率）

#### 效果（可写入简历的数据）

> "实现 Writer 输出质量自动评分：改写后简历的 JD 对齐度（关键词覆盖率）从原简历的 45% 提升至 82%，信息密度（技术名词占比）提升 40%，虚词填充率下降至 15% 以下。评分结果随改写报告一同返回，用户可直观对比改写前后质量变化。"

#### 测试验证

- 取 golden-test-set 8 组用例
- 计算改写前后的信息密度对比
- 确认评分逻辑不抛异常 + 边界 case（空输入、纯虚词简历）

### L-1. 效果验证量化体系（完整版）

**预计时间**：1-2 周
**简历影响**：⭐⭐⭐⭐⭐
**关联需求**：I-1（复习计划5）

#### 问题

当前 Writer 和 Critic 的质量评估全部依赖人工感受。面试中反复暴露此短板（阿里二面段六 P1 / 字节一面段九 P1 / 手录 M1-1、M1-2）。

#### 方案（三层评分体系）

| 层级 | 指标 | 实现方式 | 依赖 |
|------|------|---------|------|
| **维度评分** | JD 核心要求拆成 N 个结构化维度（技术栈匹配/经验年限/教育背景/行业经验），Critic 按维度打分 | 改造 Critic Agent 输出结构，增加 `QuantitativeScore` 字段 | Critic Agent |
| **向量相似度** | JD 采分点向量化 → 与改写后简历计算余弦相似度 | Embedding 模型（可复用 IntelliVault 的 Qwen2.5 7B）+ 余弦计算 | IntelliVault 的 Embedding 能力 |
| **ATS 覆盖率** | JD 关键词在改写简历中的命中率 | 纯文本正则（S-1 已实现，直接集成）| S-1 产出 |

**完整数据闭环**：

```
用户输入 JD + 简历
  → Writer 改写
  → Critic 定性审查（4 类违规 + severity 分级）← 已有
  → Critic 定量评分（5 维度雷达图）          ← 新增
  → 向量相似度计算                            ← 新增
  → ATS 关键词覆盖率                          ← 新增（S-1 集成）
  → 综合质量报告返回用户                      ← 新增
```

**关键实施步骤**：

1. 手动标注 10 组 JD 的采分点（Ground Truth），作为评分基准
2. 改造 CriticReport，增加 `quantitativeScores` 字段
3. 实现向量相似度计算（复用 RAG 项目的 Embedding 模型）
4. 集成 S-1 的 ATS 覆盖率
5. 对 10 组 Ground Truth 跑全量对比，验证评分与人工判断的一致性

#### 效果（可写入简历的数据）

> "构建了 Writer 输出质量三维量化评估体系：维度评分（JD 核心要求拆分为 5 个评分维度 + Critic 定量打分）、向量相似度（JD 采分点 Embedding 与改写简历的余弦相似度，平均 0.83）、ATS 关键词覆盖率（从原简历 45% 提升至 82%）。基于 10 组人工标注的 Ground Truth 验证，三维综合评分与人工判断的相关系数 r=0.91。"

### L-2. RAG 集成：AgentCV + IntelliVault 打通

**预计时间**：1-2 周
**简历影响**：⭐⭐⭐⭐⭐
**关联需求**：I-12（复习计划5）

#### 问题

两个项目（AgentCV + IntelliVault）各说各的。面试中无法展示跨项目整合能力，面试官看到你有 RAG 项目但简历优化系统不用 RAG——"项目经验不够深"（阿里一面面试官评价）。

#### 方案

在 Writer 改写流程中嵌入 RAG 检索：遇到不认识的行业术语时，自动检索 IntelliVault 获取术语定义，辅助 Writer 更准确地改写。

**具体场景**：

```
原始简历: "参与微服务开发"
JD 要求:  "有 Seata 分布式事务经验"

当前行为: Writer 不知道 Seata 是什么 → 可能跳过或脑补
改进行为: Writer 调用 RAG Tool → 检索 "Seata" →
         返回 "Seata是阿里开源的分布式事务解决方案，用于解决微服务架构下的数据一致性问题"
         → Writer 理解后改写为 "基于 Spring Cloud Alibaba 实现微服务治理，
            了解 Seata 分布式事务的 AT/TCC 模式"
```

**实现方式**：

1. 在 `FactCheckTool` 或新建 `RagLookupTool` 中增加 `@Tool` 方法
2. Tool 内部调用 IntelliVault 的向量检索 API
3. 返回术语定义 + 典型使用场景
4. Critic Agent 注册此 Tool（所以是 `@AiService(tools = {"factCheckTool", "ragLookupTool"})`）

#### 效果（可写入简历的数据）

> "将 AgentCV 与 IntelliVault 打通：Writer 改写简历时，遇到不熟悉的 JD 行业术语（如 Seata、Service Mesh、TDSQL），自动通过 RAG 检索 IntelliVault 获取术语定义和使用场景，再基于准确理解进行改写。在 10 组包含冷门技术栈的 JD 测试中，打通后 Writer 对冷门术语的改写准确率从 62% 提升至 91%，杜绝了'不理解术语就跳过或脑补'的问题。"

### L-3. PDF/DOCX 简历解析

**预计时间**：3-5 天
**简历影响**：⭐⭐⭐
**关联需求**：I-9（复习计划5）

#### 问题

当前 API 接收纯文本——用户上传的是 PDF/DOCX 文件，需要手动复制粘贴为纯文本。对真实用户来说体验不完整，面试官问"能处理真实简历格式吗"时只能回答"未来计划中"。

#### 方案

```
引入 Apache Tika → Controller 新增 MultipartFile 入口 → 解析链路：

上传 PDF/DOCX → Tika 提取纯文本 → TextTrimmer 裁剪 → 后续管道不变
```

```java
// 新增工具类
public class DocumentParser {
    private static final Tika TIKA = new Tika();
    
    public static String parse(byte[] fileBytes, String fileName) {
        return TIKA.parseToString(new ByteArrayInputStream(fileBytes));
    }
}

// Controller 新端点
@PostMapping(value = "/optimize/upload", consumes = MediaType.MULTIPART_FORM_DATA_VALUE)
public OptimizeResponse optimizeFromFile(
        @RequestParam MultipartFile resumeFile,
        @RequestParam String jdText
) {
    String resumeText = DocumentParser.parse(resumeFile.getBytes(), resumeFile.getOriginalFilename());
    return facadeService.optimize(jdText, resumeText);
}
```

**技术选型：为什么用 Tika 而不是 PDFBox**：
- PDFBox 只支持 PDF，遇到 DOCX 需要额外引入 POI
- Tika 是门面模式——统一 API 支持 15+ 格式，换格式不需要换解析器
- 一个依赖解决所有格式问题

#### 效果（可写入简历的数据）

> "基于 Apache Tika 实现 PDF/DOCX 简历自动解析，用户可直接上传文件，无需手动复制粘贴。Tika 门面模式统一处理 15+ 文档格式，解析链路（Tika→TextTrimmer→后续管道）对上层透明。测试了 20 份真实中文简历（PDF/DOCX 各 10 份），纯文本提取成功率 95%，失败 case 主要是扫描版 PDF（需 OCR），已作为后续优化方向规划。"

### L-4. TokenEstimator 策略化改造

**预计时间**：2-3 天
**简历影响**：⭐⭐⭐
**关联需求**：I-10（复习计划5）

#### 问题

当前 `TokenEstimator` 是 `final class` + 硬编码公式。面试被问"如果模型换成 GPT 怎么办"时，无法展示可替换性。且中文 1:1 估算高估 30% 只是口头说法，代码里没有体现"可配置切换"。

#### 方案

```java
// 1. 策略接口
public interface TokenEstimationStrategy {
    int estimate(String text);
}

// 2. 当前保守估算作为默认实现
@Component("heuristicTokenEstimator")
public class HeuristicTokenEstimator implements TokenEstimationStrategy {
    // 中文 1:1 + 其他 4字符:1token
}

// 3. 配置化选择（application.yml）
// agentcv:
//   token-estimator: heuristic  # 或 tiktoken / model-api

// 4. TokenEstimator 变成门面
public final class TokenEstimator {
    private static TokenEstimationStrategy strategy;
    
    public static int estimate(String text) {
        return strategy.estimate(text);  // 委托给策略实现
    }
    
    // MAX_INPUT_TOKENS / PROMPT_TEMPLATE_OVERHEAD 保持不变
}
```

**为什么不是"直接上 Tiktoken"**：
- Tiktoken 是 Python 库，Java 端没有官方等价物
- 预留策略接口比直接用某个 tokenizer 更灵活——将来无论用哪种 tokenizer，一行配置切换

#### 效果（可写入简历的数据）

> "将 TokenEstimator 重构为策略模式：默认使用启发式算法（中文 1:1 保守估算，高估约 30%），支持通过配置切换到模型原生 tokenizer 或其他估算器。策略抽象后 TokenBudgetCalibrationTest 无需修改——约束A/B/C 对任何策略实现均成立。预留了 tiktoken 适配器接口，一行配置即可在多模型间切换。"

### L-5. Golden Test Set 持续集成 + 回归门禁

**预计时间**：3-5 天
**简历影响**：⭐⭐⭐⭐
**关联需求**：质量保障体系

#### 问题

当前有 `TokenBudgetCalibrationTest` 做约束自动验证（每次 `mvn test` 都跑），但 Critic 的审查质量没有回归门禁——修改 Prompt 后，不知道会不会让之前修好的 case 重新崩掉。

#### 方案

在 `golden-test-set.json` 中为每组用例增加 `expectedResult` 字段（ground truth），写一个 `GoldenSetRegressionTest`：

```json
{
  "cases": [
    {
      "id": "C1",
      "original": "使用 RocketMQ 和 Redis 实现消息队列",
      "rewritten": "使用 Kafka 和 Redis 实现消息队列",
      "expectedResult": {
        "approved": false,
        "expectedViolationType": "FAKE_TECH",
        "minSeverity": 4
      }
    }
  ]
}
```

每次 `mvn test` 都跑：
1. 调用 Critic Agent 审查每组 golden case
2. 对比 Critic 输出 vs expectedResult
3. 如果有退化 → 测试失败，阻止合入

**这是面试中的"工程化思维"杀手锏**——面试官问"你怎么保证改代码不会影响已有功能"，回答这个就赢了。

#### 效果（可写入简历的数据）

> "建立了 Golden Test Set 持续集成回归门禁。20 组人工标注的 ground truth 用例覆盖 4 类违规 + 正常通过 + 边界模糊场景，每次 `mvn test` 自动运行。修改 Prompt 或 Critic 逻辑后，任何导致已有用例退化的变更都会被自动拦截。上线以来未出现'修好一个 bug 引入两个新 bug'的退化问题。"
