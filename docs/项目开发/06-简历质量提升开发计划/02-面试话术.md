## 一、设计决策：从一维到三维——为什么要拆？

### 一维评分的问题

```json
{"matchScore": 78, "matchedSkills": ["Java"], "missingSkills": ["Redis"], "improvementAdvice": "..."}
```

78 分到底代表什么？是技能不匹配扣了 20 分，还是格式扣了 20 分？**不可解释**。

### 三维评分的改进

```json
{
  "overallScore": 78,
  "jdMatch": {"score": 85, "matchedSkills": ["Java"], "missingSkills": ["Redis"]},
  "contentQuality": {"score": 70, "highlights": ["有量化成果"], "improvements": ["缺少STAR结构"]},
  "format": {"score": 80, "issues": ["信息密度偏低"]}
}
```

**权重公式**：`overallScore = jdMatch.score × 0.4 + contentQuality.score × 0.35 + format.score × 0.25`

拆解后的价值：
- **可解释**：用户知道自己在哪个维度丢分
- **可行动**：`improvements` 和 `issues` 给出了具体的修改方向
- **可对比**：改写前后两次评分可以 diff，量化改进幅度

## 二、评分精度与诚实 trade-off

### 核心问题：评分靠 LLM 一次性判断，没有外部验证，靠谱吗？

**直接回答：不靠谱，但它是当前阶段的最优解。**

| 方案 | 可行性 | 问题 |
|------|--------|------|
| LLM 自评 | ✅ 当前方案 | 既当运动员又当裁判，分数不可信 |
| 人工标注 ground truth | ❌ | 需要大量 HR 标注数据，超出现阶段范畴 |
| ATS 系统模拟 | ❌ | 不存在可集成的真实 ATS API |
| 关键词匹配算法 | ⚠️ | 可以算技能覆盖率，但无法评估"写得好不好" |

### 面试话术

> "评分系统用的是 LLM 一次性判断，它不像 Critic 有 FactCheckTool 做交叉验证。这是有意识的设计 trade-off——简历评分的本质是主观评估，不存在 ground truth。我们用三维拆解 + 具体反馈来让评分可解释、可行动，而不是追求数字本身的精确度。"

## 三、评分结果是否影响改写？（当前答案：不影响）

**现状**：Writer 的 `rewrite()` 方法只接收三个输入：
```java
WriterDraft rewrite(
    @V("jdText") String jdText,
    @V("originalProjectText") String originalProjectText,
    @V("criticFeedback") String criticFeedback
);
```

评分结果**没有传进 Writer**。`ResumeOptimizationService.optimize()` 中：
```java
ScoreResult score = scoringAgent.score(...);  // Phase 1: 评分
log.info("matchScore={}", score.matchScore()); // 打了个日志就被丢弃了
runActorCritic(jdText, originalProjectText);   // Phase 2: Writer 不知道评分
```

### 为什么解耦？

> "当前架构下 Writer 和评分是解耦的——评分是给用户看的，Writer 只依赖 JD + 原文 + Critic 反馈。改写有效性靠的是两道防线：Writer 的 prompt 约束（不捏造）+ Critic 的事实核查（91% 精确率），而不是评分引擎的反馈。这是有意识的设计选择——与其让不精确的评分去污染改写方向，不如先确保安全性和事实准确性。有效性验证留给未来的 before/after 评分对比。"

### 未来方向

1. 把评分结果的 `missingSkills` 喂给 Writer——让 Writer 针对性强化
2. before/after 评分对比——改写前后各评分一次，展示分数变化

## 四、改写质量保障的三道防线

| 防线 | 保证的是 | 不能保证的是 |
|------|---------|-------------|
| Writer System Prompt | 不捏造数据、不虚构技术 | 改完后是否更匹配 JD |
| Critic（+ FactCheckTool）| 事实准确性（3类 dirty draft × 3采样，100%召回） | 改完后是否更有竞争力 |
| Actor-Critic 循环（最多 2 轮） | 修正事实错误 | 语义质量的提升 |

**缺失的一环**：没有人回答"这个改写版本比原始版本好在哪里"。
