### 🥇 FAQ-1：只要 MDC.put()，logback 就自动把 traceId 写到日志里了吗？

**是的，全自动。三步走：**

```
① TraceIdFilter: MDC.put("traceId", "a1b2c3d4")
     ↓ 数据写入当前线程的 ThreadLocal<Map<String,String>>
② 业务代码任何位置: log.info("xxx")
     ↓ SLF4J → Logback 的 appender 开始拼日志行
③ Logback 看到 logback-spring.xml 里的 pattern 占位符 %X{traceId}
     ↓ 从当前线程的 MDC Map 里取 "traceId" 的值 → 替换
输出: 12:34:56 INFO [a1b2c3d4] c.j.a.WebLogAspect : [WEB] POST /api/...
```

> **关键**：不需要在每个 `log.info()` 里手动传 traceId，不需要改任何业务代码。Filter 里 `MDC.put()` 一次，logback 的 `%X{traceId}` 会自动从当前线程的 MDC 里取值。这就是「透明透传」。
>
> **补充**：如果 MDC 里没有 traceId（比如非 HTTP 请求的线程），`%X{traceId:-no-trace}` 会显示默认值 `no-trace`，不会空白。

---

### 🥇 FAQ-2：MDC 要和 SLF4J 配合使用吗？不是单独的库吧？

**MDC 就是 SLF4J 的一部分，不是独立库。**

看 `TraceIdFilter.java` 的 import：
```java
import org.slf4j.MDC;  // ← 包名就是 org.slf4j
```

层级关系：
```
你的代码
  ↓ 调用                      示例
SLF4J API 层           Logger.info() / MDC.put() / MDC.get()
  ↓ 实现（引入哪个日志框架）
Logback                Spring Boot 默认，解析 %X{traceId} 占位符
（也可以是 Log4j2）      Log4j2 用 %X{traceId} 或 %MDC{traceId}
```

> **SLF4J = 门面（Facade）**，定义统一 API。
> **Logback = 实现**，真正写日志、解析 pattern。
> **MDC 是 SLF4J 规范里定义的类**，任何 SLF4J 的实现（Logback、Log4j2）都支持。

**面试时这么说**：
> 「MDC 是 SLF4J 规范的一部分，不是独立依赖。SLF4J 是日志门面，Logback 是 Spring Boot 默认的实现。`%X{traceId}` 是 Logback 的 pattern 语法，底层从 SLF4J MDC 维护的 ThreadLocal Map 里取值。」

---

### 🥇 FAQ-3：每个线程只有一个 ThreadLocal？traceId 怎么存的？

**精确答案：每个线程只有一个 MDC 的 ThreadLocal，但里面是一个 Map，可以存多个 key-value。**

```
单个线程的 MDC 内部结构：

┌─────────────────────────────────────────┐
│ ThreadLocal<Map<String, String>>        │  ← 只有 1 个 ThreadLocal
│                                         │
│   Map 里面可以有多个 key：              │
│   {                                     │
│     "traceId":    "a1b2c3d4",           │  ← traceId 是 Map 里的一对 key-value
│     "userId":     "user_123",           │  ← 业务代码也可以放自己的字段
│     "requestUri": "/api/v1/match"       │
│   }                                     │
└─────────────────────────────────────────┘
```

**三个 API 的区别：**

| API | 作用 | 影响范围 |
|-----|------|---------|
| `MDC.put("traceId", "xxx")` | 往 Map 里放一对 key-value | 只影响当前线程 |
| `MDC.remove("traceId")` | 从 Map 里删掉 traceId 这个 key | 不影响同一个 Map 里的 userId |
| `MDC.clear()` | 清空整个 Map | **所有 key 都没了** |

**关键结论：**
> - **一个线程 = 一个 ThreadLocal = 一个 MDC Map = 里面可以存多个 key**
> - **traceId 只是这个 Map 里的一个 key，不是独立 ThreadLocal**
> - **remove("traceId") 只删 traceId 这个 key，如果 Map 里还有 "userId"，它还在**
> - **clear() 清空整个 Map → 这才是最安全的清理方式**

**面试时怎么说：**
> 「MDC 底层是每个线程维护一个 `ThreadLocal<Map<String,String>>`，traceId 只是这个 Map 里的一个 key。我在 finally 里用 `MDC.clear()` 而不是 `remove("traceId")`，因为 clear 清空整个 Map，防止其他业务代码放进来的 key（比如 userId、requestUri）残留到下一个请求。」

### 🥇 FAQ-4：新线程也有 MDC 啊，为什么说 traceId "丢失"了？

**"丢失"不是指旧线程的数据没了，而是指新线程从来没拿到过。**

你的困惑很精准：新线程确实有自己的 MDC，但它是**空的** `{}`。

**完整流程：**

```
请求进入 Tomcat，被分配给线程 T-5
  → TraceIdFilter（跑在 T-5 上）
  → MDC.put("traceId", "a1b2c3d4")        ← 只有 T-5 执行了这行代码！
  → MDC 内部：T-5.ThreadLocal.Map = {"traceId": "a1b2c3d4"}  ✓

T-5 的 Controller 调用了一个 @Async 方法
  → Spring 把任务提交到异步线程池
  → 线程池分配了一个全新线程 T-99 来跑这个任务
  → T-99 的 MDC：T-99.ThreadLocal.Map = {}  ← 空的！什么都没有！
  → T-99 里调用 log.info(...) → %X{traceId} 取到的值是 null → 输出 [no-trace]
```

**关键是：`MDC.put("traceId", "a1b2c3d4")` 这行代码只在线程 T-5 上执行过。T-99 从出生到死亡，从来没有人对它执行过 `MDC.put("traceId", ...)`。**

**类比：工卡不会自动复印**

> 你在公司前台刷卡进了大门（T-5 有了 traceId）。然后你打电话让快递员去你工位取包裹。快递员进大楼——他进了同一栋楼，但他的工卡是空白的，没人给他刷过。大楼的系统不知道他是帮谁取件的。

**TaskDecorator 做的事情就是「复印工卡」：**

```java
executor.setTaskDecorator(task -> () -> {
    // ① 从 T-5 的 MDC 里复印所有信息
    Map<String, String> context = MDC.getCopyOfContextMap();
    //    context = {"traceId": "a1b2c3d4"}

    try {
        // ② 粘贴到 T-99 的 MDC 里
        MDC.setContextMap(context);   // 现在 T-99 的 Map = {"traceId": "a1b2c3d4"}
        task.run();                   // T-99 里的日志现在带 traceId 了 ✓
    } finally {
        MDC.clear();
    }
});
```

**一句话纠正术语**：不要说"异步丢 traceId"，要说"**子线程不会自动继承父线程的 MDC 上下文，需要手动传递**"。Spring 默认不做这件事，所以你需要 TaskDecorator。

### 🥈 FAQ-5：异步一定和多线程相关吗？

**不一定，但在 Java 生态里 99% 是。**

| 实现方式 | 是否多线程 | 典型场景 |
|---------|-----------|---------|
| `new Thread()` / 线程池 / `@Async` | ✅ 是 | Java 后端的异步处理 |
| `CompletableFuture.supplyAsync()` | ✅ 是（默认用 `ForkJoinPool`） | Java 异步编排 |
| JS 的 `Promise` / `async/await` | ❌ 不是 | 浏览器/Node.js 事件循环 |
| Netty 的 EventLoop | ❌ 不是 | 单线程 + IO 多路复用 |

> **关键结论**：MDC 会丢不是因为「异步」，而是因为 **MDC 底层是 `ThreadLocal`，数据存在线程 A 上，线程 B 拿不到**。不管是真多线程还是事件循环，只要执行上下文从线程 A 换到了线程 B，MDC 就丢了。

### 🥈 FAQ-6：我这个项目里有线程池设计吗？

**代码里显式的没有，隐式的无处不在。**

我在整个 `src` 目录搜索了 `ThreadPool`、`@Async`、`Executor`、`CompletableFuture`——**结果全为零**。你的代码没有任何显式的多线程设计。

但隐式的线程池一直在运行：

| 隐式线程池 | 来源 | 规模 |
|-----------|------|------|
| **Tomcat 工作线程池** | Spring Boot 内嵌 Tomcat | 默认 200 线程 |
| **LangChain4j HTTP 客户端** | 框架内部调用 AI API | 不定 |

> **Tomcat 线程池就是 `TraceIdFilter` 必须清理 MDC 的根因**：
> HTTP 请求 A → Tomcat 从池里分配线程 T-5 → MDC.put("traceId", "aaa") → 处理完返回池
> HTTP 请求 B → Tomcat 复用线程 T-5 → 如果没清理，T-5 的 MDC 里还有 "aaa"！

**面试时怎么说：**

> 「当前项目体量不大，没有显式使用 `@Async` 或自定义线程池。但我理解异步丢 traceId 的根因——MDC 基于 ThreadLocal，不跨线程。如果未来需要异步发通知或异步统计，我知道要用 `TaskDecorator` 把父线程的 MDC 上下文 copy 到子线程，并且我会在 `finally` 里 `MDC.clear()`。这个设计是架构预留的。」

### 🥈 FAQ-7：@Async 和线程池到底是什么关系？Runnable 又是什么？

**核心纠正：Tomcat 线程池 和 @Async 线程池是两套完全独立的东西。**

| | Tomcat 线程池 | @Async 异步线程池 |
|---|---|---|
| 谁管的 | Servlet 容器（Tomcat） | Spring 容器 |
| 做什么 | 接收 HTTP 请求，调用你的 Controller | 执行业务层 `@Async` 方法 |
| 何时创建 | Spring Boot 启动时 Tomcat 就建好了 | `@EnableAsync` 开启后，调用时从池里取 |
| 默认实现 | Tomcat 内嵌线程池（`server.tomcat.threads.max=200`） | `SimpleAsyncTaskExecutor`（每次新建线程，不复用！） |

**@Async 的完整执行链（一张图看懂）：**

```
Tomcat 线程 T-5 在处理 Controller 请求
  → Controller 调用了 service.asyncMethod()   ← 此方法有 @Async 注解
  → Spring AOP 代理拦截到这个调用
  → 代理把 asyncMethod() 包装成一个任务，提交给 Spring 的异步线程池
  → 异步线程池从自己的池子里分配线程 T-99 来执行
  → T-5（Tomcat 线程）立刻返回，不等待 T-99
```

**为什么 T-5 的 MDC traceId 传不到 T-99？**
> T-5 和 T-99 是两个完全独立的线程，各自有自己的 `ThreadLocal<Map>`。T-5 的 MDC 里 `{traceId: "aaa111"}`，但 T-99 的 MDC 是空的 `{}`。这就是需要 `TaskDecorator` 把父线程的 MDC 上下文拷贝到子线程的原因。

**Runnable 是什么？**
> `Runnable` 是一个接口，只有一个 `run()` 方法，代表「一段可以被线程执行的代码」。线程池（不管 Tomcat 还是 @Async）内部就是把你要执行的逻辑包装成 `Runnable`，然后交给池子里的空闲线程去调用 `run()`。你写 @Async 方法时看不到 Runnable，但 Spring 底层帮你做了这件事：
> ```java
> // Spring 底层伪代码（你看不到，但它在发生）
> Runnable task = () -> asyncMethod();  // 包装
> asyncThreadPool.execute(task);        // 提交给线程池
> ```

**⚠️ 重要：Spring 默认异步线程池的坑**

Spring 的 `@EnableAsync` 如果不配线程池，默认用 `SimpleAsyncTaskExecutor`：
- 它**每次调用都新建一个线程**，不复用
- 高并发下会疯狂创建线程直到 OOM
- **生产必须替换成 `ThreadPoolTaskExecutor`**，配置核心线程数、最大线程数、队列容量

### 🥈 FAQ-8：TaskDecorator 是继承接口重写方法吗？CompletableFuture 怎么处理？

**TaskDecorator 不是"继承接口"，而是给线程池加一个包装器（装饰器）。**

线程池本身不改、不继承，只是通过 `setTaskDecorator()` 注入一个 lambda：

```java
// TaskDecorator 是一个函数式接口（只有一个方法）
@FunctionalInterface
public interface TaskDecorator {
    Runnable decorate(Runnable task);  // 输入一个任务，返回一个包装后的任务
}

// 使用：不继承任何类，只是传一个 lambda
executor.setTaskDecorator(task -> () -> {
    // 这个 lambda 实现了 TaskDecorator.decorate()
    // "task -> () -> {}" 的意思：拿到原始 task，返回一个新的 Runnable
    // 新 Runnable 在执行 task.run() 之前，先拷贝父线程的 MDC

    Map<String, String> context = MDC.getCopyOfContextMap();  // ① 在读（父线程）
    try {
        MDC.setContextMap(context);  // ② 粘贴到子线程
        task.run();                  // ③ 执行原始任务（MDC 已生效）
    } finally {
        MDC.clear();
    }
});
```

**关键点**：`setTaskDecorator` 设置了之后，这个线程池执行的**每一个**任务都会自动经过装饰器。一次配置，全局生效。不需要每个 `@Async` 方法手动处理。

---

**CompletableFuture 的情况更复杂，分三种：**

| 场景 | MDC 是否有 traceId | 原因 |
|------|-------------------|------|
| `CompletableFuture.supplyAsync(() -> {...})` 不传线程池 | ❌ 没有 | 默认用 `ForkJoinPool.commonPool()`，不受 Spring 管理，TaskDecorator 无效 |
| `CompletableFuture.supplyAsync(() -> {...}, myExecutor)` 传自定义池 | ✅ 有（如果 myExecutor 配了 TaskDecorator） | 线程池经过了装饰器 |
| 手动 `MDC.setContextMap(...)` 在 lambda 开头 | ✅ 有 | 临时方案，每次都要手动写 |

**推荐方案**：

```java
// 方案一：传配置了 TaskDecorator 的线程池（推荐）
CompletableFuture.supplyAsync(() -> {
    log.info("异步处理");  // ← traceId 在！因为 myExecutor 配了 TaskDecorator
    return result;
}, myExecutor);

// 方案二：不传线程池，手动处理（不推荐，容易忘）
CompletableFuture.supplyAsync(() -> {
    Map<String, String> ctx = MDC.getCopyOfContextMap();
    try {
        MDC.setContextMap(ctx);
        log.info("异步处理");
        return result;
    } finally {
        MDC.clear();
    }
});  // 默认用 ForkJoinPool.commonPool()
```

**面试时怎么说：**

> 「`@Async` 的场景，通过 `ThreadPoolTaskExecutor.setTaskDecorator()` 一次性配置，所有异步任务自动继承父线程 MDC。TaskDecorator 不是继承接口，它是一个函数式接口，lambda 实现即可——本质是把原始任务包了一层代理。」
>
> 「`CompletableFuture` 如果传了自定义线程池，同样受益于 TaskDecorator。但如果用默认的 `ForkJoinPool.commonPool()`，TaskDecorator 管不到，只能在 lambda 开头手动拷贝 MDC。所以我们的规范是所有异步任务必须用自定义线程池。」
