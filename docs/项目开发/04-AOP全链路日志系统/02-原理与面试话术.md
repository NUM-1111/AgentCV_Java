# 02 — 原理与面试话术

本文从「为什么这么做」的角度，逐一拆解日志系统的技术选型，并给出面试中可以直接使用的表达方式。

---

## 一、为什么要用 AOP，而不是直接在方法里写日志？

### 原理

AOP（面向切面编程）的核心思想是「横切关注点分离」。

日志、监控、权限校验这类逻辑，和业务逻辑（匹配评分、简历改写）本质上是两类不同的关注点。如果把日志代码直接写进 `MatchEvaluationFacadeService`，会导致：

1. 业务代码被日志代码污染，可读性下降
2. 每个 Controller 方法都要手动加日志，重复代码多
3. 日志格式想统一修改时，要改几十个地方

AOP 的做法是：把日志逻辑写在「切面」里，通过「切点表达式」声明要拦截哪些方法，Spring 在运行时用动态代理自动织入，业务代码完全不感知。

### 面试怎么说

> 我没有直接在 Controller 或 Service 里写日志，而是用 Spring AOP 做了两个切面。
> 原因是日志属于横切关注点，和业务逻辑应该分离。用 AOP 的好处是零侵入——Controller 和 Service 的代码完全不需要修改，日志逻辑集中在切面里统一维护。
> 如果以后要改日志格式或者加监控指标，只改切面一个地方就够了。

## 二、Spring AOP 的核心概念

### 五个术语，一张图理解

```
目标方法（Target）
    ↑
切点（Pointcut）— 描述「拦截哪些方法」的表达式
    ↑
通知（Advice）  — 拦截后「做什么」的逻辑
    ↑
切面（Aspect）  — 切点 + 通知的组合，就是我们写的 @Aspect 类
    ↑
织入（Weaving） — Spring 在运行时把切面逻辑「插入」目标方法的过程
```

### `@Around` 环绕通知的执行流程

```java
@Around("restControllerMethods()")
public Object logAround(ProceedingJoinPoint joinPoint) throws Throwable {
    // ① 目标方法执行前：记录开始时间、入参
    long start = System.currentTimeMillis();

    try {
        Object result = joinPoint.proceed(); // ② 真正执行目标方法
        // ③ 目标方法执行后（成功）：记录耗时、返回值摘要
        return result;
    } catch (Throwable ex) {
        // ④ 目标方法执行后（异常）：记录异常信息，重新抛出
        throw ex;
    }
}
```

关键点：`joinPoint.proceed()` 是「放行」，不调用它目标方法就不会执行。这也是 `@Around` 比 `@Before`/`@After` 更强大的原因——它可以控制目标方法是否执行、修改入参、修改返回值。

### 面试怎么说

> Spring AOP 底层是动态代理。对于实现了接口的类用 JDK 动态代理，没有接口的类用 CGLIB 字节码代理。
> 我用的是 `@Around` 环绕通知，因为它可以同时拿到方法执行前后的状态，还能捕获异常。
> `ProceedingJoinPoint.proceed()` 才是真正执行目标方法的地方，在它前后插入日志逻辑，就实现了无侵入的全链路记录。

## 三、切点表达式怎么写，为什么这么选？

### 两种切点的对比

| 切面 | 切点表达式 | 选择理由 |
|------|-----------|---------|
| `WebLogAspect` | `@within(RestController)` | 拦截所有 Controller 类的所有方法，新增接口自动覆盖，不用改切面 |
| `AiCallLogAspect` | `execution(* ...MatchEvaluationFacadeService.evaluate(..))` | 精准切入 AI 调用唯一入口，避免切到工具类产生噪音日志 |

### `execution` 表达式语法拆解

```
execution(* com.jobagent.service.MatchEvaluationFacadeService.evaluate(..))
          ↑  ↑                                                            ↑
          |  完整类名.方法名                                              任意参数
          任意返回类型
```

常见写法：
- `execution(* com.jobagent.service.*.*(..))` — service 包下所有类的所有方法
- `execution(* com.jobagent..*.*(..))` — jobagent 包及子包下所有方法（`..` 表示任意层级）
- `@within(Service)` — 所有被 `@Service` 注解的类的所有方法

### 面试怎么说

> 我用了两种切点策略，原因不同。
> HTTP 层用 `@within(RestController)`，因为我希望所有 Controller 方法都被覆盖，以后新增接口不需要改切面。
> AI 调用层用精准的 `execution` 表达式，只切 `MatchEvaluationFacadeService.evaluate()`，原因是 AI 调用是整个系统最核心的可观测点，我不想把日志混进 TextTrimmer、TokenEstimator 这些工具方法里，那样日志会很噪。精准切点 = 精准可观测。

## 四、MDC 是什么，为什么要用它？

### 原理

MDC（Mapped Diagnostic Context）是 SLF4J 提供的「线程本地存储」，本质是一个 `ThreadLocal<Map<String, String>>`。

你往里面 put 一个 key-value，这个线程后续打出的所有日志都会自动携带这个值。在 logback 的 pattern 里用 `%X{key}` 就能读取出来。

```
TraceIdFilter.doFilter()
    ↓ MDC.put("traceId", "a1b2c3d4")
    ↓
Controller.evaluate()          → 日志自动带 [a1b2c3d4]
    ↓
MatchEvaluationFacadeService   → 日志自动带 [a1b2c3d4]
    ↓
AiCallLogAspect                → 日志自动带 [a1b2c3d4]
    ↓ MDC.remove("traceId")    ← finally 块清理，防止线程复用污染
```

### 为什么要在 `finally` 里清理？

Spring Boot 使用线程池（Tomcat 默认 200 个线程）处理请求。线程处理完请求 A 后，会被复用去处理请求 B。如果不清理 MDC，请求 B 的日志会带着请求 A 的 traceId，导致日志串号，排查问题时会被误导。

### 面试怎么说

> 我用 MDC 实现了请求级别的 traceId 透传。
> MDC 是 SLF4J 的线程本地存储，在 Filter 里把 traceId 放进去，这个线程后续所有日志都会自动携带，不需要每个方法手动传参。
> 有一个细节：必须在 `finally` 块里清理 MDC。因为 Tomcat 用线程池，线程会被复用，不清理的话上一个请求的 traceId 会污染下一个请求的日志。这是生产环境里很容易踩的坑。

## 五、为什么 AI 调用层的日志不打印完整 Prompt？

### 原因

1. **日志文件大小**：一次 AI 调用的 Prompt 可能有 2000+ 字，如果每次都打印全文，日志文件会以极快的速度增长，磁盘很快被打满。

2. **信息密度**：排查问题时，我们最关心的是「这次调用花了多久」「评分是多少」「有没有异常」，而不是 Prompt 全文。Prompt 全文由 LangChain4j 的 `log-requests: true` 在 DEBUG 级别输出，需要时打开即可。

3. **敏感信息**：简历内容可能包含个人信息，不应该无差别地写入日志文件。

### 实际做法

- `AiCallLogAspect` 只记录字符数（`jdLen`、`resumeLen`），不记录全文
- `WebLogAspect` 对入参 JSON 做 200 字符截断
- LangChain4j 的完整 Prompt/Response 由 `dev.langchain4j: DEBUG` 控制，默认不输出

### 面试怎么说

> 我在 AI 调用切面里没有打印完整的 Prompt，只记录了字符数和关键指标。
> 原因有三：一是防止日志文件爆炸，一次 Prompt 可能 2000 字，高并发下磁盘很快被打满；二是简历内容涉及个人信息，不应无差别写入日志；三是完整 Prompt 由 LangChain4j 框架在 DEBUG 级别输出，需要深度排查时打开就行，平时不需要。
> 这体现了日志设计的一个原则：INFO 级别记关键指标，DEBUG 级别记详细内容，分层控制信息密度。

## 六、这套日志系统能解决什么问题？（面试总结话术）

> 原来系统出问题只能靠猜——不知道是哪个请求触发的，不知道 AI 调用花了多久，不知道是 token 超限还是解析失败。
>
> 我用 Spring AOP 做了两个切面：一个切 HTTP 层，记录每个接口的入参摘要、耗时、状态；一个精准切 AI 调用入口，记录 JD/简历字符数、AI 耗时、评分结果、异常类型。
>
> 配合 MDC 的 traceId，每个请求产生的所有日志都带同一个 ID，出问题时一条 grep 命令就能过滤出完整链路。
>
> 整套方案零侵入——Controller 和 Service 的代码完全没有改动，日志逻辑全部在切面里，符合开闭原则。
