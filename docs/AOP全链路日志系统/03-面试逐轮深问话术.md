### Q1：说说你对 AOP 的理解？

**标准回答：**

> AOP（Aspect-Oriented Programming）面向切面编程，核心思想是**横切关注点分离**。
>
> 业务代码是一条主干——比如匹配算法、简历评分。日志、监控、权限校验这些和业务无关但每个方法都需要做的事情，我们称为**横切关注点**。AOP 就是把这些横切逻辑从业务代码里抽出来，单独写成**切面（Aspect）**，通过**切点表达式（Pointcut）**声明要在哪些方法上生效，运行时由框架自动**织入（Weaving）**进去。
>
> 打个比方：就像高速收费站的 ETC——不是每辆车停下来人工缴费，而是在车道两侧装感应器，车经过自动识别扣费。AOP 就是把日志这类逻辑变成"路侧的感应器"，核心业务代码（车）不需要感知到它们的存在。

**如果面试官追问"Spring AOP 的原理是什么"：**

> Spring AOP 底层是**动态代理**：如果目标类实现了接口，用 JDK 动态代理（`java.lang.reflect.Proxy`）；如果没有实现接口，用 CGLIB 字节码生成子类代理。
>
> 但有一个关键限制：**同一个类内部的 `this.xxx()` 调用不走代理**。因为内部调用绕过了代理对象，直接调用 `this` 的方法。这在生产上很容易踩坑，我后面会展开说。

---

### Q2：AOP 有哪几个核心概念？一个一个说。

| 术语 | 一句话解释 | 类比 |
|------|-----------|------|
| **连接点（JoinPoint）** | 程序中可以被拦截的点——Spring AOP 里就是方法调用 | 公路上的每一个路口 |
| **切点（Pointcut）** | 用表达式筛选出「哪些连接点需要拦截」 | 在导航里标注「所有高速出口」 |
| **通知（Advice）** | 拦截后执行的逻辑，即你写的日志/监控代码 | ETC 感应器触发时执行的扣费逻辑 |
| **切面（Aspect）** | 切点 + 通知的组合体，也就是 `@Aspect` 注解的类 | 一个完整的收费系统（规则 + 扣费动作） |
| **织入（Weaving）** | 框架在运行时把切面逻辑「插入」目标方法的过程 | 在公路两侧实际安装感应器的施工过程 |

**如果追问"通知有哪几种类型"：**

> 五种：`@Before`（前置）、`@AfterReturning`（正常返回后）、`@AfterThrowing`（异常抛出后）、`@After`（最终，类似 finally）、`@Around`（环绕，最强大）。
>
> 我在项目里全用 `@Around`，因为它可以同时拿到**执行前后状态、返回值、异常**，一个通知搞定所有事。而且 `@Around` 的 `ProceedingJoinPoint.proceed()` 可以决定「是否执行目标方法」，这是其他四种做不到的。

### Q3：MDC 是什么？跟 ThreadLocal 什么关系？

**标准回答：**

> MDC（Mapped Diagnostic Context）是 SLF4J 提供的**线程级日志上下文存储**，底层就是 `ThreadLocal<Map<String, String>>`。
>
> 核心价值：**在不修改方法签名的情况下，让一个线程产生的所有日志自动携带同一个上下文信息。** 最常见的用法是放 `traceId`——在 Filter 里 put 进去，这个请求涉及的所有 Controller、Service、Aspect 的日志里，都会自动带上这个 traceId，每个位置都不需要手动传参。
>
> 在生活中这就是**快递单号**：包裹在中转站、分拣中心、派送点之间流转时，每个环节都扫同一个运单号，最后就能串联出完整路由。MDC 的 traceId 就是日志世界的快递单号。

**如果追问"Logback 怎么读取 MDC 的值"：**

> 在 `logback-spring.xml` 的 pattern 里用 `%X{key}` 来占位。比如我们项目里：
>
> ```xml
> <pattern>%d{HH:mm:ss.SSS} %5p [%X{traceId}] %-40.40logger{39} : %m%n</pattern>
> ```
>
> `%X{traceId}` 会自动从 MDC 里取出 key 为 `traceId` 的值填进去。如果 MDC 里没有这个 key，可以用 `%X{traceId:-no-trace}` 给一个默认值。

### Q4：你们项目里 AOP 具体怎么用的？切了几个面？

**标准回答：**

> 我一共做了**两个切面**，分工明确：

| 切面 | 切点 | 职责 |
|------|------|------|
| `WebLogAspect` | `@within(RestController)` → 所有 Controller | HTTP 层：记录接口、入参摘要、耗时、状态 |
| `AiCallLogAspect` | `execution(* MatchEvaluationFacadeService.evaluate(..))` → 精准切 | AI 调用层：记录 JD/简历字符数、AI 耗时、评分、异常 |

> 为什么是两个而不是一个？
>
> 因为 **HTTP 层和 AI 调用层的日志需求完全不同**。HTTP 层要记录的是方法名、URI、入参截断；AI 调用层要记录的是字符数、技能匹配数、异常类型。两个关注点放在一个切面里会让代码臃肿，而且切点策略也不一样——HTTP 层用 `@within` 覆盖所有 Controller，新增接口自动生效；AI 层用精准 `execution`，只切 `evaluate()` 一个方法，避免把 `TextTrimmer`、`TokenEstimator` 这些工具方法的日志也混进去变成噪音。

---

### Q5：你两个切面的切点策略为什么不一样？展开说。

**标准回答：**

> 这是刻意设计的选择，背后有不同的考量。

#### WebLogAspect：`@within(org.springframework.web.bind.annotation.RestController)`

> ```
> @Pointcut("@within(org.springframework.web.bind.annotation.RestController)")
> public void restControllerMethods() {}
> ```
>
> 选 `@within` 的理由：
> 1. **覆盖面广** —— 所有加了 `@RestController` 的类里的所有方法都会被拦截，以后新增 Controller 不需要改切面，符合开闭原则
> 2. **语义清晰** —— 阅读代码一眼就知道「这是拦截所有 REST 接口」
> 3. **与 AOP 的动态代理兼容性好** —— `@annotation` 只切标注了注解的方法，`@within` 切类级别注解所有方法

#### AiCallLogAspect：精准 `execution`

> ```
> @Pointcut("execution(* com.jobagent.service.MatchEvaluationFacadeService.evaluate(..))")
> public void aiEvaluateMethod() {}
> ```
>
> 选精准 `execution` 的理由：
> 1. **AI 调用是整个系统最核心的可观测点**——必须有专门的切面，不能混在 Controller 切面里
> 2. **`evaluate()` 是 AI 调用的唯一入口**，切它就够了
> 3. **避免噪音** —— 如果切到 whole service 包（`execution(* com.jobagent.service.*.*(..))`），`TextTrimmer.trim()`、`TokenEstimator.estimate()` 这些工具类方法也会被拦截，日志里充斥大量无价值的调用记录
> 4. **LangChain4j 的 `@AiService` 是动态代理生成的 Bean**，用 `@within` 切可能不稳定，`execution` 更可靠
>
> 一句话总结这个设计原则：**精准切点 = 精准可观测**。

### Q6：TraceIdFilter 的具体实现，逐行讲。

**先给出完整的代码，再看代码讲：**

```java
@Component
public class TraceIdFilter extends OncePerRequestFilter {

    public static final String TRACE_ID_KEY = "traceId";

    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                    HttpServletResponse response,
                                    FilterChain filterChain)
                                    throws ServletException, IOException {
        // ① 生成 8 位短 UUID 作为 traceId
        String traceId = UUID.randomUUID().toString().replace("-", "").substring(0, 8);

        try {
            // ② 注入 MDC — 此线程后续所有日志自动携带此 ID
            MDC.put(TRACE_ID_KEY, traceId);

            // ③ 也写入响应头 — 方便前端/调用方拿着 ID 来查问题
            response.setHeader("X-Trace-Id", traceId);

            // ④ 放行，继续执行后续 Filter 和 Controller
            filterChain.doFilter(request, response);
        } finally {
            // ⑤ 必须清理！防止线程池复用时 traceId 串号
            MDC.remove(TRACE_ID_KEY);
        }
    }
}
```

**逐行讲解：**

> **为什么要继承 `OncePerRequestFilter`？**
>
> Servlet 的 Filter 链可能因为 `forward` / `include` 被多次触发——比如请求先到 Filter，Controller 内部又 `forward` 到另一个 Controller，此时 Filter 会被调两次。`OncePerRequestFilter` 内部维护了一个已执行的标记，保证**同一个 HTTP 请求只执行一次过滤逻辑**。生产上这很关键，否则每次 forward 都会生成一个新的 traceId，覆盖掉原来的。

> **为什么用 8 位 UUID 而不是完整的 36 位？**
>
> UUID 完整形式是 `a1b2c3d4-e5f6-7890-abcd-ef1234567890`，36 位太长了，打印在日志里侵占有效信息空间。8 位十六进制有 16^8 ≈ 43 亿种组合，足以区分日常流量。而且 `substring(0, 8)` 比找第三方短 ID 生成器少一个依赖，够用就好。

> **为什么在 finally 里清理 MDC？**
>
> Tomcat 默认有 200 个线程的线程池。线程处理完请求 A 后不会被销毁，而是回到池子里等待处理请求 B。如果不清 MDC，请求 B 的日志会带着请求 A 的 traceId，出现"串号"——你排查 A 的问题时，看到的是 B 的 ID，完全被误导。**finally 保证不管请求正常结束还是抛异常，MDC 都会被清理。**

> **为什么还要写到响应头？**
>
> 前端/App 端出问题时，用户截图里的响应头 `X-Trace-Id` 就是关键线索。后端拿到这个 ID 就能精准定位到哪次请求。这是一个**端到端的排查链路设计**——从前端截图到后端日志，一根线串到底。

### Q7：logback-spring.xml 里 traceId 是怎么和 MDC 对接的？

**标准回答：**

> 在 `logback-spring.xml` 里配置输出格式，用 `%X{traceId}` 从 MDC 取值：

```xml
<pattern>
    %clr(%d{HH:mm:ss.SSS}){faint}           <!-- 时间，精确到毫秒 -->
    %clr(%5p)                                <!-- 日志级别，右对齐 -->
    %clr([%X{traceId:-no-trace}]){cyan}      <!-- traceId，无请求时显示 no-trace -->
    %clr(%-40.40logger{39}){magenta}         <!-- 类名，最长40字符 -->
    : %m%n                                    <!-- 消息 + 换行 -->
</pattern>
```

> 关键点：
> - `%X{traceId}` — 从 MDC 中读取 `traceId` 的值
> - `:-no-trace` — 如果没有值（比如非请求线程、定时任务），显示 `no-trace` 而不是空白，可读性更好
> - `%clr(...){color}` — Spring Boot 扩展的彩色输出语法，ERROR 红色、WARN 黄色、INFO 绿色，控制台排查时一眼能区分异常行和正常行
> - `%-40.40logger{39}` — 类名最长 40 字符，超过截断。防止长包名吃掉后面的消息内容

> 注意：traceId 的注入（`MDC.put`）发生在 `TraceIdFilter.doFilterInternal()` 里，比 logback 的 pattern 渲染早得多——Filter 是请求进入的第一道门，后续所有 `log.info()` 调用的那一刻，MDC 里已经有 traceId 了。

### Q8：你们日志设计上有什么原则？为什么入参只截断 200 字符、AI 调用不打印全文？

**标准回答：**

> 核心原则：**分层信息密度**。

| 层级 | 记录什么 | 不记录什么 | 控制方式 |
|------|---------|-----------|---------|
| INFO（切面） | 关键指标：耗时、评分、字符数、异常类型 | Prompt 全文、入参全文、堆栈详情 | 代码截断 + 条件判断 |
| DEBUG（业务层） | 裁剪前后对比、中间状态 | — | `application.yml` 中 `com.jobagent: DEBUG` |
| TRACE（LangChain4j） | 完整 Prompt、完整 Response | — | `dev.langchain4j: DEBUG`（默认关闭） |

> 具体实现：
>
> **WebLogAspect 的入参截断：**
> ```java
> private String summarizeArgs(Object[] args) {
>     String json = objectMapper.writeValueAsString(args);
>     return json.length() > 200 ? json.substring(0, 200) + "..." : json;
> }
> ```
> 200 字符足够让你看清楚传了什么参数，又不会因为简历全文几千字把日志文件撑爆。
>
> **AiCallLogAspect 只记字符数：**
> ```java
> int jdLen     = args[0] instanceof String s ? s.length() : 0;
> int resumeLen = args[1] instanceof String s ? s.length() : 0;
> ```
> 排查问题时，知道 JD 和简历各多少字，就足以判断是否触发了 token 超限。全文由 LangChain4j 框架在 DEBUG 级别输出，需要时打开即可。
>
> **异常只记消息摘要不记堆栈：**
> ```java
> String errMsg = ex.getMessage();
> if (errMsg.length() > 150) errMsg = errMsg.substring(0, 150) + "...";
> log.warn("[AI-CALL] ERROR={}:{}", ex.getClass().getSimpleName(), errMsg);
> ```
> 堆栈由 `GlobalExceptionHandler` 统一记录，切面里不需要重复。避免同一个异常产生多份堆栈日志。

> 这个设计带来的价值：
> - INFO 级别日志轻量、可扫描——排查问题 3 秒定位
> - DEBUG 级别保留完整信息——深度排查时打开即可，不需要重启服务
> - 日志文件大小可控——不会因为一个长简历把日志打爆

### 踩坑 1：TraceId 串号 —— MDC 清理不干净

**场景复现（你怎么发现这个问题的）：**

> 有一天线上排查用户反馈，搜某个 traceId 对应的日志，发现同一个 traceId 下面，前 5 行是用户 A 的操作，后 3 行突然变成了用户 B 的操作。我当时第一反应是「出 Bug 了，两个请求怎么混一起了？」

**根因分析：**

> Tomcat 线程池默认 200 线程，线程是复用的。流程是这样的：
>
> ```
> 请求 A 进来 → 线程 T-1 处理 → MDC.put("traceId", "aaaa1111") → 业务处理 → MDC.remove("traceId") → T-1 回池
> 请求 B 进来 → 线程 T-1 复用 → MDC.put("traceId", "bbbb2222") → 业务处理 → MDC.remove("traceId")
> ```
>
> 正常情况下 MDC.remove() 在 finally 里，没问题。但有一个边界情况：**如果在 MDC.put 之前线程 T-1 的 MDC 里还有上一个请求残留的值**（比如上一次 finally 没执行到——虽然极罕见，但在 `System.exit()` 或 `OutOfMemoryError` 场景下可能发生），就会串号。

**解决方案（你是怎么修的）：**

> 在 `doFilterInternal` 里，`try` 块的第一行加入了防御性清理：
>
> ```java
> @Override
> protected void doFilterInternal(HttpServletRequest request,
>                                 HttpServletResponse response,
>                                 FilterChain filterChain)
>                                 throws ServletException, IOException {
>     String traceId = UUID.randomUUID().toString().replace("-", "").substring(0, 8);
>     try {
>         // 防御性清理：确保当前线程 MDC 是干净的
>         MDC.clear();  // clear 比 remove 更彻底，清空所有 key
>         MDC.put(TRACE_ID_KEY, traceId);
>         response.setHeader("X-Trace-Id", traceId);
>         filterChain.doFilter(request, response);
>     } finally {
>         MDC.clear();  // 用 clear 而非 remove，清除所有可能的残留
>     }
> }
> ```
>
> 关键改动：`MDC.remove("traceId")` → `MDC.clear()`。
>
> 两者的区别：
> - `MDC.remove("traceId")` — 只删 `traceId` 这一个 key。如果业务代码里有人 `MDC.put("userId", ...)` 放了个用户 ID，`remove("traceId")` 不会删它，下次复用线程时 `userId` 还挂在上面
> - `MDC.clear()` — 清空当前线程 MDC 里的**所有** key。彻底干净
>
> 而且我在进入时也调了 `MDC.clear()`——双重保险。即使上次 finally 因为某种极端异常没执行到，这次也能保证从一个干净的 MDC 开始。

**如果追问"既然有 ThreadLocal 内存泄漏风险，你是怎么处理的"：**

> ThreadLocal 内存泄漏的根本原因是 **ThreadLocalMap 的 Entry 对 ThreadLocal 是弱引用，但对 value 是强引用**。如果 ThreadLocal 对象被 GC 了，但线程还活着（线程池场景），key 是 null 了，value 永远不会被回收。
>
> 我们的做法：
> 1. `finally` 块里 `MDC.clear()` 清空 Map，value 引用被释放
> 2. SLF4J 的 MDC 实现内部就是 `ThreadLocal.remove()`，不存在泄漏问题
> 3. 如果要用自定义 ThreadLocal，必须配合 `try-finally` 和 `remove()`

### 踩坑 2：切面不生效 —— 同一个类内部调用绕过代理

**场景复现：**

> 我在 `MatchEvaluationFacadeService` 里有一个公开方法 `evaluate()`，同时也写了几个私有辅助方法。切面配置的是 `evaluate()` 的 `@Around`，日志正常输出。但有一次线上发现某个请求链路里 AI 调用耗时异常，我怀疑是里头的 `doEvaluate()` 方法导致的，于是想给 `doEvaluate()` 也加切面——结果怎么配都不生效。

**根因分析：**

> Spring AOP 是通过**代理对象**实现拦截的。当你从外部调用 `facadeService.evaluate()` 时，实际上调用的是代理对象的 `evaluate()`，代理可以在调用前后插入切面逻辑。
>
> 但是在 `evaluate()` 内部通过 `this.doEvaluate()` 调用时，`this` 指向的是**原始对象**（不是代理对象），调用绕过了代理层，AOP 拦截不了。
>
> ```
> 外部调用者
>     ↓ 调用
> 代理对象.evaluate()   ← AOP 在这里生效
>     ↓ 调用
> 原始对象.evaluate()
>     ↓ 内部 this.doEvaluate()
> 原始对象.doEvaluate()  ← AOP 在这里不生效！因为绕过了代理
> ```

**解决方案（你是怎么修的）：**

> 三种解法，按推荐度排序：
>
> **方案一：拆到不同类（推荐）**
> 把 `doEvaluate()` 抽到独立的 service 里（比如 `EvaluateEngineService`），让 Spring 为它也创建代理。这是最干净的做法，也符合单一职责原则。
>
> **方案二：`AopContext.currentProxy()`**
> ```java
> @Service
> public class MatchEvaluationFacadeService {
>     public MatchReport evaluate(String jdText, String resumeText) {
>         // 获取当前代理对象
>         MatchEvaluationFacadeService proxy =
>             (MatchEvaluationFacadeService) AopContext.currentProxy();
>         return proxy.doEvaluate(jdText, resumeText);  // 走代理
>     }
> }
> ```
> 需要在启动类或配置上加 `@EnableAspectJAutoProxy(exposeProxy = true)`。缺点是要侵入业务代码，而且需要把方法改成 public。
>
> **方案三：`@Autowired` 注入自身**
> ```java
> @Service
> public class MatchEvaluationFacadeService {
>     @Autowired
>     private MatchEvaluationFacadeService self;  // 注入自身的代理
>
>     public MatchReport evaluate(String jdText, String resumeText) {
>         return self.doEvaluate(jdText, resumeText);  // 走代理
>     }
> }
> ```
> 缺点：循环依赖警告、代码不优雅。
>
> 我们最终选了**方案一**——把核心评估逻辑抽到 `MatchEvaluatorService`，两个 service 各司其职，AOP 自然就生效了。这也反推我们优化了代码结构。

**如果追问"AspectJ 编译期织入和 Spring AOP 运行时代理的区别"：**

> - Spring AOP（我们在用的）：运行时通过动态代理实现，不需要特殊编译器，只能拦截 Spring 管理的 Bean 的 public 方法。内部调用不生效。
> - AspectJ 编译期织入：通过 AJC 编译器在 `.class` 文件生成时就织入，可以拦截任意方法（包括 private、内部调用），性能更好但构建配置复杂。
> - 对于 99% 的业务场景，Spring AOP 完全够用。真正需要 AspectJ 的场景通常是框架级需求（如 Spring `@Transactional` 的某些高级用法）。

### 踩坑 3：日志爆炸 —— AI Prompt 全文打印导致磁盘满

**场景复现：**

> 项目刚上线第一周，有一天凌晨收到磁盘告警。查了一下，发现 log 目录下几个小时产生了 2GB+ 的日志。定位后发现是 LangChain4j 的 `log-requests: true` 把每次 AI 调用的完整 Prompt（包含简历全文和 JD 全文）都打印了出来，高并发下日志量完全失控。

**根因分析：**

> 一次 AI 调用涉及的文本量极大：
> - JD 原文：800 ~ 2000 字
> - 简历原文：1200 ~ 3000 字
> - 系统 Prompt（角色设定、输出格式约束）：1500 字
> - 合计一次调用就可能产生 5000+ 字的日志
> - 高峰期 100+ 并发请求，日志写入速度远超磁盘 I/O 承受能力
>
> 而且简历内容可能包含姓名、手机号、工作经历等敏感信息，无差别写入日志还有合规风险。

**解决方案（你是怎么修的）：**

> 分三步走：

> **① 切面层：INFO 只记指标，不记全文**
>
> `AiCallLogAspect` 的设计就是防御式的——只记录 `jdLen` 和 `resumeLen`（字符数），不记录内容文本。让 INFO 日志始终轻量可控。

> **② 框架层：控制 LangChain4j 日志级别**
>
> 在 `application.yml` 中：
> ```yaml
> langchain4j:
>   open-ai:
>     chat-model:
>       log-requests: false   # 生产环境关闭，开发环境打开
>       log-responses: false
> ```
>
> 配合 logback 的 `<springProfile>` 按环境分离：
> ```xml
> <!-- 开发环境：DEBUG 输出完整 Prompt -->
> <springProfile name="dev">
>     <logger name="dev.langchain4j" level="DEBUG"/>
> </springProfile>
>
> <!-- 生产环境：只输出 WARN 以上 -->
> <springProfile name="prod">
>     <logger name="dev.langchain4j" level="WARN"/>
> </springProfile>
> ```

> **③ 兜底：滚动日志策略**
>
> 在 `logback-spring.xml` 中加入 `SizeAndTimeBasedRollingPolicy`：
> ```xml
> <appender name="FILE" class="ch.qos.logback.core.rolling.RollingFileAppender">
>     <file>logs/application.log</file>
>     <rollingPolicy class="ch.qos.logback.core.rolling.SizeAndTimeBasedRollingPolicy">
>         <fileNamePattern>logs/application.%d{yyyy-MM-dd}.%i.log</fileNamePattern>
>         <maxFileSize>100MB</maxFileSize>     <!-- 单文件最大100MB -->
>         <maxHistory>7</maxHistory>            <!-- 保留7天 -->
>         <totalSizeCap>2GB</totalSizeCap>      <!-- 总大小上限2GB -->
>     </rollingPolicy>
> </appender>
> ```
>
> 这是最后的防线——即使日志量失控，也会被自动切割和清理，不会打满磁盘。

**如果追问"怎么做到调试时又要看 Prompt 全文"：**

> 两个办法：
> 1. 开发环境设置 `dev.langchain4j: DEBUG`，本地调试时就能看到完整 Prompt
> 2. 接入 Arthas 或 Spring Boot Actuator 的 `loggers` endpoint，运行时动态改级别：`POST /actuator/loggers/dev.langchain4j` body: `{"configuredLevel": "DEBUG"}`——不改配置、不重启、不影响其他请求，排查完再改回去

### 踩坑 4：异步场景 traceId 丢失 —— CompletableFuture 里日志没 traceId

**场景复现：**

> 我们有一个场景：匹配评分完成后，异步发送通知和更新统计。这部分用 `@Async` 做异步处理。有一天看日志发现，异步线程里输出的日志 traceId 全是 `[no-trace]`——也就是说异步方法的日志和主请求的日志串不到一起了。

**根因分析：**

> MDC 底层是 `ThreadLocal`，而 `ThreadLocal` 只对**当前线程**有效。`@Async` 或 `CompletableFuture` 会把任务提交到另一个线程池执行，新线程的 MDC 是空的。
>
> ```
> 请求线程 T-1  → MDC: {traceId: "aaa111"}  ✓ 有 traceId
>                     ↓ @Async
> 异步线程 T-99 → MDC: {}                   ✗ 空的！
> ```

**解决方案（你是怎么修的）：**

> **方案一：`TaskDecorator` 装饰线程池（推荐）**
>
> ```java
> @Configuration
> @EnableAsync
> public class AsyncConfig implements AsyncConfigurer {
>
>     @Override
>     public Executor getAsyncExecutor() {
>         ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
>         executor.setCorePoolSize(5);
>         executor.setMaxPoolSize(10);
>
>         // 核心：在任务提交前，把父线程的 MDC 上下文传递给子线程
>         executor.setTaskDecorator(task -> () -> {
>             Map<String, String> contextMap = MDC.getCopyOfContextMap();
>             try {
>                 if (contextMap != null) {
>                     MDC.setContextMap(contextMap);
>                 }
>                 task.run();
>             } finally {
>                 MDC.clear();
>             }
>         });
>
>         executor.initialize();
>         return executor;
>     }
> }
> ```
>
> 原理：`TaskDecorator` 在每个 `Runnable` 执行前，先把父线程的 MDC 完整 copy 到子线程的 MDC 里，执行完再清理。这样所有 `@Async` 方法都能自动继承 traceId。

> **方案二：手动传递（临时方案）**
>
> ```java
> public void asyncMethod() {
>     Map<String, String> context = MDC.getCopyOfContextMap();
>     CompletableFuture.runAsync(() -> {
>         try {
>             if (context != null) MDC.setContextMap(context);
>             // 异步业务逻辑
>             log.info("异步处理完成");  // 这时候就有 traceId 了
>         } finally {
>             MDC.clear();
>         }
>     });
> }
> ```
>
> 缺点：每个异步调用都要手动包一层，侵入性强，容易忘。`TaskDecorator` 是一次配置全局生效。

> **补充：如果用的是 `CompletableFuture` 的 `supplyAsync` 没有传线程池怎么办？**
>
> `CompletableFuture.supplyAsync()` 默认用的是 `ForkJoinPool.commonPool()`，不属于 Spring 管理，`TaskDecorator` 对它无效。这种情况下要么传自定义线程池，要么在 lambda 开头手动 `MDC.setContextMap(context)`。我们的规范是：**所有异步任务必须使用自定义线程池，并配置 `MdcTaskDecorator`。**

## 第四层：总结话术（弹药包）

> 以下是「2 分钟脱稿总结」，融会贯通 AOP + MDC + 踩坑经验。面试官让你总结项目亮点时，直接背这段：

---

**面试官：「你在这个项目里最有成就感的技术点是什么？展开说说。」**

> 我给这个项目从零搭建了一套全链路日志追踪系统，核心是 **AOP + MDC** 的组合方案。
>
> **先说问题：** 项目涉及 AI 大模型调用，一次请求链路很长——从 Controller 接收入参，到文本裁剪、token 估算、AI 调用、结果解析、匹配评分——原来没有任何日志追踪，出问题时完全不知道是哪个环节挂了、哪个请求触发的、AI 调用花了多久。
>
> **再说方案：** 我用 Spring AOP 做了两个切面。一个切面覆盖所有 Controller，记录每个接口的 HTTP 方法、URI、入参摘要、耗时和成功/失败状态。另一个切面精准切入 AI 调用的唯一入口方法，记录 JD 和简历的字符数、AI 耗时、匹配评分、技能命中数和异常类型。
>
> 同时用 `OncePerRequestFilter` + MDC 实现了请求粒度的 traceId 注入。每个请求进来时生成一个 8 位短 ID，放进 MDC，写入响应头。同一个请求产生的所有日志——从 Controller 到 Service 到切面——全部带同一个 traceId。出问题时，前端反馈一个 X-Trace-Id，后端一条 grep 命令就能还原完整链路。
>
> **关键设计决策有三个：**
> 1. 日志分层策略——INFO 只记录关键指标（字符数、评分、耗时），不打印 Prompt 全文，防止日志爆炸。完整 Prompt 由 LangChain4j 框架在 DEBUG 级别受控输出。
> 2. 切点策略差异化——HTTP 层用 `@within(RestController)` 覆盖所有接口，新增自动生效；AI 调用层用精准 `execution` 表达式只切 `evaluate()`，避免工具方法产生噪音。
> 3. MDC 防御式清理——finally 块用 `MDC.clear()` 而非 `remove("traceId")`，清空所有可能的残留 key，防止线程池复用时串号。
>
> **踩过几个生产级的坑也做了修复：** 同一个类内部调用 AOP 不生效（拆分 service 解决）、异步线程 traceId 丢失（TaskDecorator 传递 MDC 上下文）、日志爆炸（滚动策略 + 环境隔离日志级别）。
>
> 整套方案**完全零侵入**——Controller 和 Service 的代码不改一行，所有日志逻辑集中在切面和 Filter 里维护，符合开闭原则。上线后问题排查效率从「靠猜」变成了「grep 一键定位」，平均故障定位时间从 20 分钟降到 1 分钟以内。
